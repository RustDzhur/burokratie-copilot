# 1. Твоя роль и основная задача

Ты выступаешь как команда senior-разработчиков, архитектор ПО, специалист по информационной безопасности, UX/UI-дизайнер, инженер по автоматизации бизнес-процессов, специалист по обработке документов и AI-инженер.

Твоя задача — разработать полноценное, современное, безопасное и расширяемое приложение Bürokratie-Copilot.

Не ограничивайся демонстрационным прототипом, статическим интерфейсом или набором несвязанных CRUD-страниц. Создай работающее приложение с реальной базой данных, backend API, аутентификацией, разграничением прав, обработкой документов, задачами, бизнес-процессами, интеграционными интерфейсами, автоматизацией и тестами.

Приложение должно стать единой системой для управления административными процессами частных лиц, семей и предприятий в Германии.

## 1.1. Главная концепция

Каждый входящий документ должен приводить к одному из понятных результатов:

1. Документ автоматически обработан и сохранён.
2. Документ связан с существующим делом, договором, человеком, организацией или финансовой операцией.
3. Создана задача с ответственным лицом и сроком, если действительно требуется действие.
4. Подготовлен проект ответа, платежа, заявления или другого действия.
5. Пользователь подтвердил выполнение действия, если это необходимо.
6. Результат проверен, доказательства сохранены, дело закрыто.
7. Если система не уверена, документ направлен человеку с объяснением причины.

Документ не должен просто исчезать в архиве, а задача не должна автоматически считаться выполненной только потому, что пользователь отправил письмо.

## 1.2. Обязательные правила разработки

- Не создавать фиктивный функционал вместо настоящей реализации.
- Не подменять backend моковыми данными после подключения базы данных.
- Не хранить бизнес-данные только в браузере.
- Не использовать локальные массивы вместо PostgreSQL в рабочих модулях.
- Не оставлять неработающие кнопки, формы и ссылки.
- Не выдавать успешный результат операции, если backend не подтвердил её выполнение.
- Не придумывать немецкие налоговые ставки, бухгалтерские проводки, юридические сроки и обязательные процедуры.
- Не считать ответ языковой модели юридически достоверным только потому, что модель его сформировала.
- Не выполнять необратимые, финансовые и юридически значимые действия без соответствующих полномочий и необходимых подтверждений.
- Не отключать проверку сертификатов, авторизацию, валидацию входных данных или контроль доступа ради упрощения разработки.
- Не добавлять реальные секреты, API-ключи и пароли в исходный код.
- Не объявлять модуль завершённым без автоматизированных тестов и проверки его сценариев.

Если для настоящей реализации требуется внешний сервис, API-ключ, аппаратное устройство или договор с провайдером, реализуй полноценный адаптер, конфигурацию, обработку ошибок и инструкции подключения. Явно укажи, что именно ещё требуется от владельца системы.

## 1.3. Обязательный порядок работы

Перед написанием основного кода:

1. Проанализируй требования целиком.
2. Составь карту модулей и зависимостей.
3. Спроектируй архитектуру, структуру репозитория и схему PostgreSQL.
4. Определи API-контракты и правила безопасности.
5. Создай матрицу соответствия требований и реализуемых компонентов.
6. Подготовь план реализации с контрольными точками.
7. Начни реализацию, не ожидая отдельного подтверждения каждого модуля.

Не задавай вопросы по каждой мелочи. Принимай обоснованные технические решения самостоятельно. Если отсутствует критически важное бизнес-правило, создай конфигурируемый параметр или статус «требуется настройка», а не придумывай значение.

# 2. Архитектура продукта

Продукт должен состоять из единой платформы с общим ядром и специализированными функциональными модулями.

## 2.1. Общая архитектура

Используй следующую архитектуру:

- Frontend: Next.js, React, TypeScript.
- Backend: Java 21 или актуальная поддерживаемая LTS-версия, Spring Boot.
- API: REST API с OpenAPI/Swagger.
- Основная база данных: PostgreSQL.
- Миграции БД: Flyway.
- Доступ к БД: Spring Data JPA и Hibernate; при необходимости для сложных запросов использовать специализированный SQL.
- Обработка фоновых заданий: отдельные worker-компоненты.
- Очереди и события: абстракция Event Bus с поддержкой PostgreSQL outbox pattern; внешний брокер подключается при необходимости.
- Файловое хранилище: S3-compatible object storage с поддержкой MinIO для локальной разработки.
- Поиск: PostgreSQL Full-Text Search на первом этапе, с возможностью подключения специализированного поискового движка.
- Семантический поиск: pgvector либо отдельный адаптер векторного хранилища.
- Авторизация: Spring Security, OAuth 2.0 / OpenID Connect, поддержка MFA.
- Контейнеризация: Docker.
- Локальное развёртывание: Docker Compose.
- CI/CD: автоматическая сборка, тесты, проверка безопасности и миграций.
- Мониторинг: структурированные логи, метрики, трассировка и health checks.
- Документация: архитектура, установка, API, конфигурация и эксплуатация.

Не создавай микросервис на каждый экран. Начни с модульного монолита с чёткими границами модулей. Выделяй отдельные сервисы только тогда, когда есть обоснованная необходимость: например, тяжёлая OCR-обработка, AI-worker или изолированный интеграционный сервис.

## 2.2. Структура репозитория

Предусмотри понятную структуру проекта, например:

- `apps/web` — Next.js frontend.
- `apps/desktop-bridge` — при необходимости локальный компонент для работы со сканерами.
- `services/api` — Java Spring Boot backend.
- `services/document-worker` — асинхронная обработка документов.
- `services/ai-worker` — AI-задачи и обработка больших документов.
- `infra` — Docker, локальная инфраструктура и конфигурации развёртывания.
- `docs` — архитектура, API, модель данных и руководства.
- `tests` — интеграционные, end-to-end и нагрузочные тесты.

Допускается другая структура, если она лучше соответствует выбранной реализации. Главное — логические границы модулей должны быть чёткими.

# 3. Мультипользовательская модель

Приложение должно поддерживать несколько типов клиентов в рамках одной платформы.

## 3.1. Типы аккаунтов

- Частное лицо.
- Семья или домохозяйство.
- Самозанятый / Freiberufler.
- Компания.
- Команда или подразделение компании.
- Внешний профессиональный представитель.
- Организация с повышенными требованиями к безопасности.

Тип аккаунта определяет доступные модули, настройки, роли и ограничения.

## 3.2. Multi-tenancy

Обязательно реализуй изоляцию данных между организациями и частными аккаунтами.

Каждая запись должна иметь корректный контекст владельца и, где необходимо, организации или рабочего пространства.

Требования:

- Невозможно получить документы другого клиента изменением ID в URL или API-запросе.
- Контроль доступа выполняется на backend.
- Tenant-контекст определяется по авторизованной сессии, а не принимается без проверки из тела запроса.
- Критичные сущности проверяются на принадлежность текущему tenant.
- Используй PostgreSQL Row-Level Security там, где это оправдано архитектурой, дополнительно к серверной авторизации.
- Добавь автоматические тесты на попытки межпользовательского доступа.
- Все фоновые задания выполняются в правильном tenant-контексте.
- Кэширование не должно приводить к смешению данных разных клиентов.

Для корпоративных клиентов предусмотрите возможность отдельного окружения и отдельных ключей шифрования.

# 4. Пользователи, роли и права доступа

Реализуй RBAC с возможностью дальнейшего расширения до ABAC.

Базовые роли:

- `OWNER` — владелец рабочего пространства.
- `ADMIN` — администратор.
- `MANAGER` — руководитель.
- `EMPLOYEE` — сотрудник.
- `ACCOUNTANT` — бухгалтер.
- `LEGAL_ADVISOR` — юридический консультант.
- `EXTERNAL_ADVISOR` — внешний специалист.
- `READ_ONLY` — чтение без изменений.
- `FAMILY_MEMBER` — член семьи с ограниченными правами.
- `AUDITOR` — доступ к журналам и разрешённым аудиторским данным.

Права должны назначаться отдельно для документов, финансов, договоров, задач, сотрудников, интеграций и административных настроек.

Обязательно реализуй:

- приглашения пользователей;
- подтверждение приглашений;
- отзыв доступа;
- временный доступ;
- доступ к конкретным делам;
- разделение личных и корпоративных документов;
- права на просмотр, редактирование, экспорт, удаление и утверждение;
- правила согласования действий;
- журнал выдачи и изменения прав.

Для семейного аккаунта один член семьи не должен автоматически получать доступ ко всем личным документам другого члена семьи.

# 6. Универсальная модель документа

Документ — центральный объект системы.

Любой документ должен иметь единую базовую модель независимо от его исходного формата и назначения.

## 6.1. Поддерживаемые форматы

Минимально:

- PDF.
- PDF/A.
- JPG, JPEG, PNG, TIFF.
- DOCX.
- XLSX.
- CSV.
- TXT.
- EML.
- MSG, если выбранный парсер поддерживает формат.
- XML.
- XRechnung.
- ZUGFeRD.
- Архивные форматы — только через безопасный процесс проверки содержимого.
- E-mail с вложениями.
- Документы, полученные со сканера.
- Фотографии с мобильного устройства.

Система должна корректно обрабатывать PDF с текстовым слоем и сканированные PDF, требующие OCR.

Для неподдерживаемого формата нужно показывать понятную причину и предлагать допустимый способ импорта.

## 6.2. Карточка документа

Храни следующие поля, где они применимы:

- ID документа.
- Tenant ID.
- Исходное имя файла.
- Безопасное внутреннее имя.
- MIME type.
- Размер.
- Хеш содержимого.
- Ссылка на оригинальный объект.
- Версия документа.
- Дата получения.
- Источник получения.
- Отправитель.
- Получатель.
- Дата документа.
- Номер документа.
- Тип документа.
- Язык.
- Краткое описание.
- Извлечённый текст.
- Структурированные данные.
- Статус обработки.
- Уверенность классификации.
- Связанные дела.
- Связанные люди.
- Связанные компании.
- Связанные договоры.
- Связанные счета и платежи.
- Связанные задачи.
- Обнаруженные даты и сроки.
- Метки конфиденциальности.
- Статус проверки человеком.
- История изменений.
- Политика хранения.
- Правовой статус оригинала, если применимо.

Не дублируй большие бинарные файлы в PostgreSQL. В базе храни метаданные, связи и ссылки на защищённое объектное хранилище.

## 6.3. Статусы обработки

Предусмотри как минимум:

`RECEIVED` → `QUARANTINED` → `OCR_PENDING` → `EXTRACTING` → `CLASSIFYING` → `MATCHING` → `REVIEW_REQUIRED` → `READY` → `ACTION_PENDING` → `COMPLETED`.

Дополнительные статусы:

- `FAILED`.
- `DUPLICATE`.
- `UNSUPPORTED`.
- `CANCELLED`.
- `ARCHIVED`.
- `LEGAL_HOLD`.

Переходы должны контролироваться backend. Нельзя разрешать произвольное изменение статуса из интерфейса.

- подозрительные сообщения.

Система не должна автоматически отправлять ответы только на основании того, что получила письмо.

## 7.3. Мобильное приложение и фотографии

- сфотографировать документ;
- отсканировать несколько страниц;

- улучшить контраст;
- объединить страницы в PDF;
- добавить комментарий;

- загрузить документ в общий Inbox.

Предусмотри возможность дальнейшего создания нативных мобильных приложений.

## 7.4. Импорт через API и внешние системы

Реализуй документированный API для приёма документов из внешних приложений.

Предусмотри:

# 8. Сканеры, МФУ и принтеры

Интеграция с физическими устройствами должна быть предусмотрена в архитектуре с самого начала.

Важно: браузер не предоставляет универсального прямого доступа ко всем сканерам и драйверам. Поэтому используй несколько каналов интеграции, а не рассчитывай только на Web API.

## 8.1. Способы подключения

Поддержи следующие сценарии:

1. Сканирование в PDF на компьютере с последующей загрузкой в приложение.
2. Сканирование в настроенную папку с автоматическим импортом.
3. Сканирование на e-mail, который подключён к приложению.
4. Сканирование в сетевую папку организации.
5. Прямое сканирование через локальный Desktop Bridge.
6. Импорт файлов через REST API.
7. Интеграция с сетевыми МФУ через доступные протоколы и API конкретного производителя.

## 8.2. Desktop Bridge

Спроектируй отдельный локальный компонент, который пользователь сможет установить на компьютер с подключённым сканером.

Возможные технологии:

- Java или другой поддерживаемый runtime;
- TWAIN и WIA в Windows;
- SANE в Linux;
- поддерживаемые производителем SDK;
- локальная защищённая очередь файлов.

Не утверждай, что все драйверы и модели поддерживаются одинаково.

Desktop Bridge должен:

- регистрироваться в пользовательском аккаунте;
- иметь собственный идентификатор устройства;
- связываться с сервером через защищённое соединение;
- принимать разрешённые задания сканирования;
- отображать статус устройства;
- поддерживать выбор разрешения и цветности;
- поддерживать автоматическую подачу документов, если устройство позволяет;
- объединять многостраничные документы;
- передавать результат в Inbox;
- обрабатывать прерванное сканирование;
- возобновлять передачу после временных сбоев;
- не открывать произвольные порты для внешнего доступа;
- не выполнять команды, полученные от неавторизованных пользователей.

Если Desktop Bridge нельзя полностью реализовать в текущем окружении, создай отдельный пакет проекта с работающим минимальным сценарием, интерфейсом конфигурации, документацией и проверенными тестами. Не имитируй прямое управление устройством в основном приложении.

## 8.3. Печать

Предусмотри:

- печать документов;
- печать пакетных документов;
- печать писем и заявлений;
- генерацию PDF для печати;
- печать с корректными полями и разрывами страниц;
- печать реестров и отчётов;
- возможность печати штрихкодов или QR-кодов для связывания бумажного оригинала с электронным делом, если это нужно клиенту.

Для обычной печати используй системный диалог браузера. Прямую отправку на принтер реализуй только при наличии поддерживаемого локального компонента или интеграции.

# 9. OCR и интеллектуальная обработка документов

После приёма документа должна автоматически запускаться конвейер обработки.

## 9.1. Конвейер

1. Проверить безопасность файла.
2. Вычислить хеш.
3. Проверить возможный дубликат.
4. Определить формат.
5. Извлечь текст из цифрового документа.
6. Выполнить OCR для сканированных страниц.
7. Сохранить исходный текст и результаты OCR.
8. Определить язык.
9. Определить тип документа.
10. Извлечь структурированные поля.
11. Определить участников, даты, суммы и ссылки.
12. Найти связанные дела и существующие документы.
13. Проверить наличие противоречий.
14. Определить необходимые действия.
15. Определить уровень риска.
16. При необходимости передать на ручную проверку.
17. Сохранить результаты и историю обработки.

Каждый этап должен иметь отдельный статус, диагностические данные и механизм повторного выполнения.

## 9.2. OCR

Предусмотри адаптеры для OCR-движков.

Выбор конкретного движка должен быть конфигурируемым. Для локального OCR можно рассмотреть Tesseract, для более сложных документов — специализированные OCR-сервисы.

Поддерживай немецкий язык и другие языки, встречающиеся в документах пользователя.

Для каждой страницы сохраняй:

- распознанный текст;
- номера страниц;
- координаты текстовых блоков, если доступны;
- уверенность распознавания, если движок её предоставляет;
- ошибки;
- информацию об использованном OCR-движке.

Для критичных полей показывай пользователю исходный фрагмент документа, из которого получено значение.

# 10. AI-слой и модельный провайдер

ИИ — это один из компонентов системы, а не единственный источник истины.

## 10.1. Абстракция провайдеров

Создай общий интерфейс AI Provider, чтобы можно было подключать разные модели и сервисы без изменения бизнес-логики.

Предусмотри:

- облачные языковые модели;
- локальные модели при необходимости;
- разные модели для классификации, извлечения данных и генерации текста;
- конфигурацию допустимых провайдеров по tenant;
- лимиты расходов;
- таймауты;
- повторные попытки;
- обработку ошибок;
- журналирование без утечки персональных данных;
- измерение качества;
- возможность отключения внешнего AI-провайдера.

API-ключи храни только на backend в защищённой конфигурации или секрет-хранилище.

## 10.2. Структурированные ответы

Для задач извлечения данных используй структурированный JSON-ответ, проверяемый по схеме.

Каждый результат должен содержать:

- тип результата;
- извлечённые поля;
- уверенность, если её можно корректно оценить;
- источник каждого важного значения;
- предупреждения;
- неразрешённые вопросы;
- необходимость ручной проверки.

Не считай самооценку модели статистически откалиброванной вероятностью. Порог автоматизации должен проверяться на реальных размеченных данных.

## 10.3. Защита от prompt injection

Содержимое документов и писем считается недоверенными данными.

Система не должна выполнять инструкции, найденные внутри PDF, изображения, письма или веб-страницы, если они пытаются изменить системные правила, раскрыть данные или вызвать неразрешённые действия.

Обязательно:

- разделять инструкции системы и содержимое документа;
- проверять доступ инструмента перед вызовом;
- применять allowlist инструментов;
- ограничивать доступ AI-агента к данным;
- проверять параметры операций;
- подтверждать действия с высоким риском;
- регистрировать вызовы инструментов;
- тестировать попытки извлечения секретов и межпользовательских данных.

## 10.4. AI-ассистент

Создай чат-ассистент, который работает не только как общий чат, но и как интерфейс управления приложением.

Примеры запросов:

- «Найди все счета от этого поставщика».
- «Покажи договоры, которые могут продлиться в ближайшие три месяца».
- «Каких документов не хватает для этого дела?»
- «Сравни две версии договора».
- «Подготовь ответ на это письмо».
- «Создай задачу бухгалтеру проверить этот счёт».
- «Найди подтверждение оплаты».
- «Собери документы для налогового консультанта».
- «Покажи просроченные задачи моей команды».
- «Подготовь заявление по данным из выбранного дела».

Ассистент должен работать только в пределах разрешённых пользователю данных.

Перед изменением данных показывай, что именно будет изменено. Перед отправкой, подписанием, платежом, расторжением договора или другим значимым действием требуй соответствующее подтверждение.

## 10.5. RAG и поиск по документам

Реализуй retrieval-augmented generation для поиска по документам и делам.

Требования:

- поиск по полному тексту;
- поиск по метаданным;
- поиск по связям между объектами;
- семантический поиск;
- фильтрация по tenant, правам, датам и типам документов;
- ссылки на исходные документы;
- ссылки на конкретные страницы или фрагменты;
- отсутствие ответов, основанных только на нерелевантных совпадениях.

Если ответа нет в документах, ассистент должен сказать об этом, а не создавать правдоподобный вымысел.

Если правила не настроены или данных недостаточно, показывай «требуется проверка», а не выдуманный крайний срок.

## 12.4. Ответственные

- роли;
- типа задачи;
- подразделения;
- доступности;
- рабочей нагрузки;
- связанных дел;
- правил организации.

Если назначение не определено, направляй задачу в очередь ручного распределения.

- назначение ответственного;
- создание платёжной задачи;
- сверка с банковской операцией;
- сохранение доказательства оплаты.

Проверка формальных данных не должна автоматически означать, что счёт юридически или налогово корректен.

## 14.2. Исходящие счета

Для бизнеса предусмотрите:

- создание клиента;
- создание счёта;
- нумерацию счетов по настраиваемой последовательности;
- позиции;
- скидки;
- сроки оплаты;
- генерацию PDF;
- формирование структурированных электронных счетов;
- отправку клиенту;
- контроль оплаты;
- частичные оплаты;
- корректировки;
- кредит-ноты;
- экспорт бухгалтеру.

Не придумывай налоговые ставки и бухгалтерские правила. Они должны быть параметрами, проверяемыми пользователем или его консультантом.

## 14.3. E-Rechnung

Поддержи:

- XRechnung;
- ZUGFeRD;
- импорт структурированных XML-данных;
- извлечение вложенного XML;
- валидацию формата;
- отображение счета для человека;
- сохранение исходного структурированного файла;
- проверку согласованности данных;
- хранение результатов валидации.

Обычный PDF не должен автоматически считаться структурированной E-Rechnung.

Правила должны быть версионируемыми и обновляемыми. Не зашивай правовые требования в код без возможности обновления.

## 14.4. Банковские интеграции

Создай интерфейс для подключения банковских данных через разрешённых провайдеров и поддерживаемые банковские протоколы.

Предусмотри:

- импорт выписок;
- импорт CAMT/CSV и других поддерживаемых форматов;
- сопоставление платежей со счетами;
- обнаружение возможных дубликатов;
- обработку частичных оплат;
- ручное подтверждение неоднозначного сопоставления.

Нельзя хранить банковские логины и TAN в открытом виде.

Не выполняй банковские платежи автоматически в базовой конфигурации. Подготовка платежа и его подтверждение должны быть разделены.

# 16. Универсальный workflow engine

Создай движок бизнес-процессов, который позволяет автоматизировать действия без изменения Java-кода для каждого нового сценария.

## 16.1. Возможности

- триггеры;
- условия;
- действия;
- ожидание события;
- задержки;
- тайм-ауты;
- повторные попытки;
- ветвления;
- ручное согласование;
- назначение исполнителя;
- уведомления;
- создание задач;
- вызов интеграций;
- проверка результата;
- эскалация;
- обработка ошибок;
- журнал выполнения;
- версии workflow;
- отключение и повторный запуск.

## 16.2. Примеры процессов

### Обработка входящего счета

1. Получить документ.
2. Проверить безопасность.
3. Определить, является ли документ счётом.
4. Извлечь реквизиты.
5. Найти возможный дубликат.
6. Найти договор, заказ и поставщика.
7. Проверить сумму и реквизиты.
8. При сомнении отправить на проверку.
9. Назначить согласующего.
10. После согласования создать платёжную задачу.
11. После подтверждения платежа связать операцию со счётом.
12. Сохранить доказательства и завершить процесс.

### Получение письма от ведомства

1. Импортировать письмо.
2. Определить ведомство и вид документа.
3. Найти соответствующее дело.
4. Извлечь требуемые документы и указанные даты.
5. Сопоставить запрос с уже имеющимися материалами.
6. Показать, чего не хватает.
7. Создать задачу и предложить срок после проверки правил.
8. Подготовить ответ или комплект документов.
9. Получить подтверждение пользователя.
10. Отправить через разрешённый канал.
11. Сохранить доказательства отправки.
12. Отслеживать дальнейший ответ.

### Контроль договора

1. Найти договор и его условия.
2. Определить ближайшие обязательства.
3. Создать напоминание.
4. Подготовить возможные варианты действий.
5. Получить решение пользователя.
6. При необходимости подготовить уведомление.
7. Отправить только после согласования.
8. Контролировать подтверждение.
9. Закрыть процесс после достижения результата.

## 16.3. Надёжность

Workflow должен быть устойчив к перезапуску сервера и повторной доставке событий.

Используй:

- idempotency;
- устойчивое хранение состояния;
- outbox pattern;
- контроль повторных действий;
- транзакционные границы;
- компенсационные действия там, где они возможны.

Не допускай повторной отправки письма или повторного создания платёжной операции из-за повторного запуска фонового задания.

# 32. Границы автоматизации

Приложение должно различать четыре уровня действий.

**Уровень 1 — автоматическая обработка:** извлечение текста, классификация, поиск дубликатов, связывание объектов с объяснением.

**Уровень 2 — рекомендация:** предложение приоритета, срока, ответственного и следующего действия.

**Уровень 3 — подготовка:** создание черновика письма, заявления, платёжной задачи или пакета документов.

**Уровень 4 — исполнение:** отправка, изменение внешних данных, подписание, платёж, расторжение или другое юридически значимое действие.

Для уровней 3 и 4 настройка полномочий должна определять допустимый способ исполнения. Для высокорисковых операций необходимо явное подтверждение уполномоченного пользователя.

Для каждого AI-решения храни:

- использованные данные;
- версию модели или провайдера, если доступно;
- версию инструкции;
- результат;
- источник фактов;
- подтверждение пользователя, если оно было;
- выполненное действие;
- итог операции.

Не утверждай, что автоматическое решение юридически корректно только потому, что оно записано в журнал.

# 37. Финальная инструкция

Начни с анализа требований и проектирования целостной архитектуры. Затем приступай к реализации.

Не ограничивайся красивым интерфейсом. Главная ценность Bürokratie-Copilot заключается в том, что система связывает документы, людей, организации, дела, задачи, сроки, финансовые операции и внешние процессы в единый управляемый контур.

Не пытайся реализовать весь продукт в одном огромном файле или одним неструктурированным набором компонентов.

При этом не упрощай исходную архитектуру до обычного файлового менеджера, списка задач или чат-бота.

Все модули должны использовать единые сущности, права доступа, аудит, интеграционные контракты и механизм автоматизации.

Если конкретный сервис невозможно подключить без ключа, подписки, аппаратного устройства или согласования со сторонним поставщиком, подготовь полноценный адаптер и документацию, но не выдавай его за работающую интеграцию.

Если юридическое, налоговое или отраслевое правило не определено, предусмотрите настройку, версионирование и проверку специалистом.

**Главный критерий успеха:** пользователь загружает документ, а система не просто распознаёт его текст. Она понимает, к какому делу он относится, какие данные уже известны, что ещё требуется, какое действие необходимо, кто должен его выполнить и как проверить достижение результата — с учётом прав доступа, безопасности и необходимости человеческого подтверждения.

Создай продукт, который может стать полноценной административной операционной системой для частных лиц, семей и бизнеса в Германии.
