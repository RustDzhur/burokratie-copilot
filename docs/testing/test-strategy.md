## Известные ограничения прогонов

- Полный прогон бэкенда в среде аудита даёт ошибки исчерпания соединений БД (`IdempotencyIT`, `SchemaIT`, `FlywayMigrationIT`); эти классы проходят при отдельном запуске (HD-TEST-01).
- Ручная проверка клавиатуры и screen reader не выполнена (`docs/accessibility-checklist.md`): нужен человек.

## Правила для новых модулей (BM, RD, CA, TR, SM)

1. **Позитивный и негативный тест на каждое правило Radar.** Негативный — случай, где правило не должно срабатывать.
2. **Тест изоляции tenant на каждую новую таблицу и каждый новый эндпоинт** (чтение, список, поиск, AI-выборка).
3. **Идемпотентность**: повторная оценка/доставка не создаёт дубль (параллельный запуск — отдельным тестом).
4. **Права**: отказ без права и разрешение с правом.
5. **Синтетические данные**; реальные письма и внешние отправки в тестах запрещены (тестовый провайдер).
6. **UI**: состояния loading/empty/error/forbidden, клавиатура, axe; каждая кнопка вызывает API (проверяет `contract.test.ts`).
7. Статус `IMPLEMENTED_AND_TESTED` в матрице ставится только при наличии теста именно на заявленное поведение.

## Оценка распознавания немецких документов (RD-09, ВЫПОЛНЕНО в части правил; AI-часть не измерена)

Платформа работает только с немецкой документацией (решение владельца, 2026-10-15; русские и украинские правила классификации удалены миграцией V55). Качество распознавания измеряется на синтетических немецких документах.

**Наборы** (`services/api/src/test/resources/eval/`): `german-documents.json` — 37 документов (счета, напоминания об оплате/Mahnung/Inkasso, договоры и их изменения, письма ведомств, бытовые письма, пустой и испорченный OCR, три документа со встроенными указаниями модели); `german-documents-holdout.json` — 21 документ, написанный позже и другими словами. Для каждого — ожидаемый тип (и допустимые близкие типы), поля, идентификаторы (IBAN с контрольной суммой, USt-IdNr., Steuernummer, e-mail), признак встроенного указания. Все документы вымышлены.

**Раннер:** `EvaluationHarnessIT` пропускает каждый документ через настоящий конвейер (загрузка → классификация → извлечение полей) без AI-модели и пишет отчёт `target/eval/german-report*.md` с таблицей по каждому документу. Прогон — в составе обычного набора интеграционных тестов.

**Замеры (честные, до и после настройки):**

| Показатель | Набор разработки до настройки | после V55–V57 | Hold-out до настройки | Hold-out после V57 |
|---|---|---|---|---|
| Верный тип | 78,8 % (26/33) | 100 % (34/34) | 89,5 % (17/19) | 94,7 % (18/19) |
| Принято автоматически | 54,5 % | 64,7 % | 52,6 % | 57,9 % |
| **Из принятых автоматически — неверных** | **22,2 % (4/18)** | **0 %** | **0 %** | **0 %** |
| Испорченный/пустой текст принят | 0 | 0 | 0 | 0 |
| Значения полей верны | 76,0 % | 96,0 % (24/25) | 100 % (1/1) | 100 % |
| Значения с указанием источника | 100 % | 100 % | 100 % | 100 % |
| Идентификаторы найдены / выдуманы | 11 из 11 / 0 | 11 из 11 / 0 | 3 из 3 / 1* | 4 из 4 / 0 |
| Встроенные указания найдены | 66,7 % | 100 % | 50 % | 100 % |
| Обычные письма, принятые за указание | 0 | 0 | 0 | 0 |

\* «выдуманный» e-mail был настоящим адресом из письма — ошибка в ожидании набора, исправлена.

**Что измерение показало и что сделано.** Главная причина ошибок — не нехватка слов, а веса: слово, называющее *отправителя* (Finanzamt, Krankenkasse, Wohngeldstelle) или общая часть любого счёта (Bankverbindung, IBAN), оценивалось так же сильно, как слова, называющие *вид* письма; счёт, в котором есть строка «Bankverbindung», принимался автоматически как «Bankverbindung». Миграции V55–V57 перенастроили веса и добавили немецкие формулировки; код поправлен в двух местах (точка после «Nr.» больше не попадает в значение; тип без собственных полей читается общим набором); детектор указаний, встроенных в документ, получил немецкие формулировки («bisherigen Anweisungen», «[SYSTEM]», «antworte nur noch mit», глагол в конце фразы) и тест на то, что обычные письма не принимаются за атаку.

**Ограничения этих цифр (важно).**
- Набор разработки настраивался под самого себя: его «после» — не оценка качества, а регрессионная планка (тест падает при ошибочной автоматической классификации или падении верности типа ниже 97 %). Честная оценка обобщения — только hold-out *до* настройки: 89,5 % верных типов, 0 % неверных автоматических решений. **Hold-out пакет 1 после настройки стал данными разработки; для следующей оценки нужен новый пакет.**
- 58 документов — мало для процентных гарантий. Пороги `classification.auto_accept_threshold` (0,85) и `classification.review_threshold` (0,60) **остаются предварительными**; их изменение требует набора на сотни документов, написанных не автором правил.
- Известный открытый пробел: «Invoice / Rechnung 88-2026-33» (номер без «Nr.») — номер счёта не читается (inv-04).
- Имя файла входит в текст классификатора: файл «Kuendigung_Mietvertrag.txt» с письмом о расторжении аренды классифицируется как договор аренды (на проверку человеком, не автоматически; h-con-02). Правило имени файла должно быть слабее правил текста.
- **Не измерено:** качество ответов с участием AI-модели (в тестах модель отключена), корректность источников в ответах Business Memory на большой выборке, точность и полнота правил Radar на реальных потоках, качество чтения рукописного текста. Эти показатели появятся при подключении ключа и наборе соответствующих документов (задачи HD-TEST).

## Измерения набора оценки на 2026-10-15 (S13-06)

`EvaluationHarnessIT` печатает в отчёт (`target/eval/*.md`) точность и полноту по каждому типу, макро-средние и таблицу порогов уверенности.
Три набора: разработки (37 документов, 34 с типом), отложенный (21, 19 с типом), случаи владельца (24, 20 с типом, из них 4 иноязычных,
которые не должны сортироваться).

| Набор | Тип верен | Принято без человека, из них неверных | Макро-точность / полнота |
|---|---|---|---|
| разработки | 34/34 | 21 / 0 | 100 % / 100 % |
| отложенный | 19/19 | 9 / 0 | 100 % / 100 % |
| случаи владельца | 20/20 | 11 / 0 | 100 % / 100 % |

**Что это значит и чего не значит.** Правила настраивались на этих же документах (отложенный набор — на первую партию замечаний), поэтому
100 % — это отсутствие регрессий и проверка явных ошибок, а не оценка качества на чужих документах. Порог принятия 0,85 по таблице порогов
ничего не отсекает неверного, потому что неверных в наборах нет: калибровать порог на этих данных нельзя, и он **не откалиброван**. Нужны
размеченные настоящие документы (с согласия владельца, без персональных данных в репозитории); пока их нет, порог остаётся техническим значением.
