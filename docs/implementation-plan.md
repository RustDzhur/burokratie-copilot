# Bürokratie-Copilot — Implementation Plan (микрозадачи)

**Источник требований:** [`docs/task.md`](task.md) (ТЗ v1.0, 2281 строка).
**Назначение файла:** единственный план работ и журнал прогресса. Обновляется после каждой завершённой микрозадачи.

## Как читать этот файл

- `ID` — стабильный идентификатор задачи (`<ЭТАП>-<номер>`). ID не переиспользуется.
- `Статус` — `TODO` | `IN_PROGRESS` | `BLOCKED` | `DONE`.
- `DONE` ставится **только** после успешного прохождения указанных тестов/проверок. Факт проверки фиксируется в разделе «Журнал прогресса».
- `BLOCKED` означает внешнюю зависимость (ключ, подписка, устройство, договор). Всё, что можно реализовать без неё, реализуется; причина блокировки пишется в задаче.

| ADR-05 | Аутентификация: серверные сессии (httpOnly cookie) для web + API-токены (PAT) для интеграций; OIDC-адаптер подключаемый | ТЗ §7.4, §21.3 |
| ADR-06 | Объектное хранилище: интерфейс `BlobStore` с реализациями S3/MinIO (prod) и LocalFs (dev/offline) | ТЗ §2.1, §30 |
| ADR-07 | Event Bus: transactional outbox в PostgreSQL + диспетчер; внешний брокер — подключаемый адаптер | ТЗ §2.1, §16.3 |
| ADR-08 | Frontend: Next.js (App Router) + TypeScript strict + собственная дизайн-система на CSS-переменных (токены) | ТЗ §2.1, §5, §33 |
| ADR-09 | Конфигурируемые бизнес-правила (налоги, сроки хранения, правовые сроки, таксономия) — данные в БД с версионированием, а не константы в коде | ТЗ §1.2, §12.3, §22, §31 |
| ADR-10 | Локализация: `de` (основной, наиболее полный), `en`, `ru`; ICU MessageFormat с pluralization | ТЗ §24 |

## Противоречия, ограничения и внешние зависимости (обязательный раздел по требованию задания)

| № | Пункт ТЗ | Проблема | Принятое решение |
|---|----------|----------|------------------|
| Q-01 | §28.1 Testcontainers | В текущем окружении **нет Docker**, Testcontainers физически не запускается | Интеграционные тесты выполняются против **реального локального PostgreSQL 17** (не H2/in-memory). Конфигурация Testcontainers добавлена как профиль `testcontainers` для окружений с Docker |
| Q-02 | §8.2 Desktop Bridge | TWAIN/WIA требуют Windows SDK и драйверов; SANE требует Linux-устройства. Полная поддержка всех драйверов невозможна | Отдельный модуль `apps/desktop-bridge` с рабочим сценарием (SANE `scanimage` + импорт из папки), конфигурацией, документацией и тестами. TWAIN/WIA — документированный внешний блокер |
| Q-03 | §7.2 M365/Gmail OAuth | Требуются client_id/secret от владельца системы (регистрация приложения в Azure AD / Google Cloud) | Полноценные OAuth-адаптеры + IMAP-адаптер, работающий без внешней регистрации приложения. Статус подключения честно отображается в UI |
| Q-04 | §14.4 Банки | Прямой доступ к PSD2/FinTS требует лицензии/договора с провайдером | Адаптер + офлайн-импорт CAMT.053/MT940/CSV, который работает без провайдера |
| Q-05 | §9.2 OCR | Качество/наличие Tesseract и языковых пакетов зависит от окружения | Адаптер OCR с проверкой доступности движка и честным статусом `OCR_UNAVAILABLE`, не фальсифицируем результат |
| Q-06 | §10.5 pgvector | Расширение `pgvector` может отсутствовать в целевом PostgreSQL | Миграция создаёт расширение при наличии; при отсутствии — деградация до FTS с явным флагом, семантический поиск помечается как недоступный |
| Q-07 | §6.1 MSG/архивы | Парсер MSG и безопасная распаковка архивов — отдельные внешние зависимости | MSG помечается `UNSUPPORTED` с понятным сообщением, пока не подключён парсер; архивы — безопасный процесс с лимитами |
| Q-08 | §12.3, §14.2, §22 | Юридические сроки, налоговые ставки, сроки хранения **не определены** в ТЗ | Не выдумываются. Реализуется конфигурируемый версионируемый реестр правил со статусом `REQUIRES_VERIFICATION` и обязательным подтверждением специалистом |
| Q-09 | §17.4 Public Sector | Правовые ограничения на автоматические решения | Реализуется как архитектурная конфигурация без автоматических юридически значимых решений |
| Q-10 | §34 «E2E-тесты проходят» | Без Docker полный контейнерный E2E невозможен | E2E-прогон выполняется против локально запущенных api+web+PostgreSQL; результаты фиксируются в отчёте тестирования |

## Легенда этапов

- **Этап A** — фундамент (репозиторий, PostgreSQL, безопасность, ядро, дизайн-система).
- **Этап B** — документы (приём, OCR, извлечение, классификация, проверка, поиск).
- **Этап C** — дела, задачи, сроки, уведомления.
- **Этап D** — договоры, финансы, E-Rechnung, банк, отчёты.
- **Этап E** — коммуникации, шаблоны, AI-слой, RAG.
- **Этап F** — workflow engine и автоматизации.
- **Этап G** — устройства, сканеры, интеграции.
- **Этап H** — специализированные режимы.
- **Этап I** — проверка, hardening, выпуск.

### A-010 · Event Bus: transactional outbox + диспетчер
- **Результат:** запись доменных событий в `outbox_events` в одной транзакции с бизнес-изменением; диспетчер с at-least-once, ретраями и идемпотентностью потребителей.
- **Зависимости:** A-004
- **Действия:** `DomainEvent`/`OutboxWriter`/`OutboxDispatcher`; блокировка `FOR UPDATE SKIP LOCKED`; dead-letter.
- **Приёмка:** событие не теряется при откате транзакции; повторная доставка не дублирует эффект.
- **Тесты:** `OutboxAtomicityIT`, `OutboxRedeliveryIT`.
- **Статус:** DONE

### Дефекты, найденные и исправленные в этой сессии

1. jsonb-литералы из `VALUES`-подзапросов требовали явного приведения типа (V12).
2. RLS-политика падала на `''::uuid` — PostgreSQL не гарантирует short-circuit; введена функция `current_tenant_id()`.
3. 30 таблиц не имели tenant-индекса — миграция `V15`.
4. `inet`-колонки нельзя мапить как `String` — используется `@JdbcTypeCode(SqlTypes.INET)`.
5. `DefaultEmailSender` с самоссылающимся `@ConditionalOnMissingBean` не регистрировался.
6. **Фильтр сессий нельзя делать `@Component`**: Spring Boot регистрирует `Filter`-бин ещё и в сервлет-цепочке, и `OncePerRequestFilter` пропускает второе выполнение — авторизация молча не работала.
7. **Фильтр должен идти ПОСЛЕ `SecurityContextHolderFilter`**, иначе контекст безопасности перезаписывается пустым.
8. **Проверка пароля и учёт неудачных попыток должны быть в разных транзакциях**: исключение откатывало счётчик блокировки.
9. **V14 падала на чистой БД при установленном pgvector**: колонка `vector` без размерности + HNSW-индекс → ошибка и откат всей миграции. Индекс теперь не создаётся до выбора модели, размерность не выдумывается.
10. **`GET /api/v1/auth/csrf` не отдавал cookie** (204 без `Set-Cookie`) → SPA не могла выполнить ни одного изменяющего запроса. Токен теперь выпускается явно через `CsrfTokenRepository`.
11. **Профиль `worker` не стартовал**: `SecurityConfiguration` требовала `HttpSecurity`, а `PasswordEncoder` и `CsrfTokenRepository` жили в web-зависимой конфигурации. Разделено на `PasswordEncoderConfiguration`, web-условную `SecurityConfiguration` и web-условный `AuthController`.
12. `apps/web/next.config.ts` не содержал `output: "standalone"`, который требует контейнер web.

- **доставка**: событие доходит до потребителя, статус становится `PUBLISHED`;
- **ровно один эффект**: повторная доставка того же события не вызывает потребителя второй раз

- **ретраи и dead letter**: временный сбой приводит к `FAILED` с экспоненциальной задержкой и

- **событие без потребителя** парковкой в `DEAD_LETTER`, а не бесконечными ретраями;
- **tenant-контекст**: потребитель выполняется внутри tenant события (проверено захватом

- **захват батча** через `FOR UPDATE SKIP LOCKED` — несколько worker-инстансов работают параллельно;
- **восстановление после сбоя**: зависшие блокировки старше 10 минут освобождаются планировщиком.

Побочный эффект: у профиля `worker` появился реальный цикл работы. Раньше он стартовал и сразу
завершался, потому что нечего было выполнять.

### A-011 · Идемпотентность небезопасных операций — DONE

Реализовано: `IdempotencyFilter` (заголовок `Idempotency-Key`), `IdempotencyService`,
`IdempotencyRecord`, `CachedBodyRequest`.

Поведение и что именно проверено (`IdempotencyIT` — **5 тестов, зелёные**):
- повтор с тем же ключом и тем же телом **не выполняет операцию второй раз** и возвращает
  сохранённый ответ (проверяется счётчик фактических вызовов эндпоинта, а не только HTTP-статус);
- тот же ключ с другим телом → **409**, а не воспроизведение чужого результата;
- без заголовка каждый запрос выполняется — идемпотентность включается осознанно;
- **неудачная попытка освобождает ключ**, поэтому клиент может исправить ввод и повторить;
- некорректный ключ → 400 с понятным сообщением.

Ключевые решения:
- захват ключа — атомарный `INSERT ... ON CONFLICT DO NOTHING` по уникальному индексу
  `(tenant_id, idempotency_key)`, поэтому двойной клик физически не может создать два объекта;
- каждый шаг (claim/complete/release) — в **отдельной транзакции**: иначе откат бизнес-транзакции
  либо навсегда блокировал бы ключ, либо допускал дубликат при повторе;
- «зависший» захват старше 2 минут перехватывается, чтобы умерший запрос не блокировал клиента;
- область действия осознанно ограничена: аутентифицированные запросы с небольшим (до 1 МиБ)
  не-multipart телом. Буферизовать 100 МиБ загрузку ради отпечатка нарушило бы требование
  потоковой обработки §27, а дубликаты документов решаются хешем содержимого (задача B-004).

### Дополнительно исправлено: миграция V16

`ddl-auto: validate` выявил реальное расхождение: колонки с фиксированной длиной `character(n)`
(например `idempotency_records.request_hash`) против `varchar` в сущностях. PostgreSQL дополняет
`char(n)` пробелами, что даёт скрытые различия при сравнении строк. Миграция `V16` переводит все
такие колонки в `varchar(n)`; CHECK-ограничения на формат хешей, кодов стран и валют сохраняются.

1. **`lower(bytea) does not exist`**: Hibernate биндит `null` в строковый параметр как `bytea`, и

2. **`cached plan must not change result type`**: тесты миграций пересоздавали схему в той же базе,

   выглядящие как ошибка продукта. Миграционные тесты переведены на отдельную базу, создаваемую
   автоматически (`MigrationTestDatabase`).
3. Фиксированный e-mail в `AuditServiceIT` конфликтовал с предыдущим запуском на переиспользуемой
   базе — заменён на уникальный.

### B-003 · Безопасность загружаемых файлов — DONE

Что проверяется:
- **формат по содержимому, а не по заявлению**: тип определяется по magic bytes и сравнивается с

- **отсутствующий обработчик не имитируется**: если для следующего шага нет реализации, конвейер
  останавливается и сообщает, на каком шаге и почему. Шаг остаётся `PENDING` («ждёт реализации»), а

- **идемпотентность**: повторный запуск ничего не меняет, завершённый шаг не выполняется второй раз
  (проверяется счётчиком попыток) — это то, что делает вызов из фонового worker безопасным после
  перезапуска;
- **повтор только для упавшего шага**: `retryStep` отказывает, если шаг не в состоянии `FAILED`, —
  перезапуск не может переиграть уже успешные этапы;
- **загрузка документа сама записывает три шага**, которые реально выполнила (`SECURITY_SCAN`,
  `HASH`, `DUPLICATE_CHECK`), поэтому история конвейера начинается с правды, а не с пробела.

Обработчик `FORMAT_DETECT` — настоящий: он сверяет записанный при проверке безопасности тип
содержимого с метаданными, убеждается, что блоб допущен к обработке, и фиксирует, какой парсер
понадобится на следующем этапе (`pdfbox`, `poi-docx`, `ocr-required`, …). Документ переходит
`RECEIVED → QUARANTINED` — единственный разрешённый переход в этой точке.

### B-006 · Извлечение текста (digital-first) — DONE

Реализовано: `TextExtractor` + шесть реализаций (`PdfTextExtractor`, `DocxTextExtractor`,
`SpreadsheetTextExtractor`, `PlainTextExtractor`, `EmlTextExtractor`, `XmlTextExtractor`),
`ExtractedText` с постраничной моделью, `TextExtractionService`, `TextExtractStepHandler`
(встроен в конвейер B-005), сущность `DocumentPage` с репозиторием.

Ключевые решения:
- **постраничность не для красоты**: §9.4 требует указывать страницу и фрагмент для каждого
  извлечённого значения, а проверяющему нужно перейти к нужному месту;
- **смешанные документы**: страницы без текстового слоя считаются отдельно, документ с цифровым
  письмом и сканированным приложением помечается как частично требующий OCR, а не как «текст есть»;
- **DOCX**: одна секция (в DOCX нет страниц до рендеринга), но таблицы разбираются — в немецких
  письмах именно в таблицах лежат сроки, суммы и перечень требуемых документов;
- **кодировки**: BOM → строгий UTF-8 → windows-1252; иначе умляуты превращают название поставщика
  в строку, которая ни с чем не сопоставится;
- **XML**: DTD, внешние сущности и внешние схемы отключены. Без этого подделанный счёт мог бы
  прочитать файлы сервера (XXE) — проверено тестом с `<!ENTITY xxe SYSTEM "file:///etc/passwd">`;
- **никаких частичных результатов**: неудачный разбор не сохраняет половину страниц, шаг помечается
  `FAILED` и может быть повторён; страницы текущей версии заменяются целиком.

Проверено `TextExtractorTest` — **10 тестов** (PDF постранично, сканированный PDF → `needsOcr`,
частично сканированный, DOCX с таблицей, XLSX, две кодировки, EML с вложениями, HTML-письмо,
XXE-атака, объявление форматов) и `DocumentPipelineIT` — конвейер теперь проходит
`FORMAT_DETECT → TEXT_EXTRACT` и останавливается на `OCR`.

**Найденный дефект:** интеграционные тесты использовали «PDF», который лишь начинался с `%PDF-`.
Пока файл никто не парсил, это сходило с рук; как только появилось извлечение текста, PDFBox
ответил `Missing root object specification in trailer`. Введён `TestDocuments`, генерирующий

### B-007 · OCR-адаптер (Tesseract) и ручной запуск — DONE

Реализовано: `OcrEngine` (+ `NoOpOcrEngine`, `TesseractOcrEngine`), `PdfPageRenderer`,
`OcrStepHandler` (встроен в конвейер), `OcrConfiguration`.

Ключевые решения:
- **TSV-вывод вместо простого текста**: в нём есть то, что требует §9.2 — координаты текстовых
  блоков и уверенность по каждому слову. Без них нельзя показать проверяющему фрагмент, из
  которого взято значение, и нельзя отличить уверенное распознавание от сомнительного;
- **уверенность приводится к доле в одном месте**: движок отдаёт проценты (0…100), платформа
  хранит долю (0…1). Смешение единиц переполнило бы колонку `numeric(5,4)` и сломало бы все пороги;
- **распознаются только страницы без текстового слоя**: в цифровом письме со сканированным
  приложением это одна страница вместо пятидесяти;
- **страница без текста ≠ страница не прочитана**: если движка нет, шаг помечается `SKIPPED` с
  причиной и документ уходит на ручную проверку. Пустой результат превратил бы нечитаемый скан в
  «пустой документ», и следующая стадия классифицировала бы его как «неизвестный» вместо
  «не прочитан»;
- **движок конфигурируемый**: `none` — допустимая конфигурация, `tesseract` проверяется при старте,

### B-008 · Таксономия и классификация — DONE

- **битое регулярное выражение не роняет обработку**: ошибка конфигурации логируется, правило

### B-009 · Извлечение полей с провенансом — DONE

Реализовано: миграция V18 (правила извлечения для 37 уже засеянных полей), `DocumentTypeField` и

Схема под это уже была в V3: `document_type_fields` (что извлекается из типа) и
`document_extractions` (значение + провенанс). Не хватало главного — **как** искать.

Ключевые решения:
- **провенанс не опционален**: каждое значение несёт страницу и строку, из которой оно прочитано.
  Административное решение должно быть проверяемо по оригиналу документа, а не по выдержке из него;
- **формат подсказки намеренно примитивен**: `Ярлык1|Ярлык2|…`. Извлекатель ищет первый ярлык,
  берёт остаток строки и проверяет его по типу поля. Это можно объяснить пользователю и править без
  релиза;
- **грамматика немецких чисел решается позицией, а не догадкой**: `1.190,00` и `1,190.00`
  разбираются одинаково верно (последний разделитель — десятичный); при одном разделителе три цифры
  после него означают разряды, одна-две — копейки;
- **даты — день вперёд** (немецкая конвенция), и **несуществующая дата отвергается**, а не
  переносится: `31.02.2026` не превращается в 3 марта, иначе молча сдвинулся бы срок;
- **IBAN проверяется по контрольной сумме MOD-97** (ISO 13616) — это ловит самую частую ошибку,
  перестановку цифр, до того как номер попадёт в платёж;
- **периоды конвертируются только при точной единице**: «24 Monate» → 24, «2 Jahre» → 24, но
  «2 Wochen» остаётся текстом, потому что у недель нет точного выражения в месяцах;
- **значение, не прошедшее проверку типа, не сохраняется**: неверно разобранная сумма выглядит как
  факт, а отсутствующая — как отсутствующие данные. Честно только второе;
- **поле без подсказки — это не «пусто», а «заполняется человеком»**: центр проверки должен видеть
  разницу;
- **несколько кандидатов — берётся первый**, а не «наиболее вероятный»: выбор «похожего» был бы
  догадкой, которую платформа не может обосновать.

**Проверено:** `FieldValueParserTest` — **32 теста** (немецкие и английские суммы, валюта рядом с
числом, даты четырёх форматов, невозможные даты, IBAN с ошибкой в одной цифре, BIC, валюты,
периоды, различие NUMBER/AMOUNT, отметка проверяемых типов) и `FieldExtractionIT` — **5 сценариев**

- **чужое дело отвечает «не найдено», а не «запрещено»**: ответ «запрещено» подтвердил бы само
  существование дела, которое пользователю видеть нельзя;
- **фильтр доступа внутри запроса, а не после**: страница результатов физически не может содержать
  дело, которое пользователю не положено, и по количеству страниц нельзя оценить объём чужих дел;
- **отзыв доступа не удаляет запись**: строка остаётся с `revoked_at`, потому что вопрос «кто мог это
  видеть в марте» должен оставаться отвечаемым; удалять участника мог бы только владелец, и владельца
  удалить нельзя — только передать владение;
- **участник — либо пользователь тенанта, либо внешний контакт**: адвокат или контрагент
  записывается без выдумывания учётной записи;
- **административное право `cases.assign` даёт обзор всех дел тенанта**: нельзя распределять то, чего
  не видишь. Это осознанное исключение из правила участников, и оно привязано к существующему
  праву, а не к новой выдуманной роли.

**Найденные дефекты:**
1. сущность `CaseEvent` не совпадала со схемой (`payload`/`summary` вместо `title`/`description`/
   `metadata` и ссылок на документ, задачу, контакт) — контекст приложения не поднимался;
2. запрос требований к документам обращался к несуществующей колонке `document_type_code`;
3. нарушение инварианта «участник — либо пользователь, либо контакт» возвращало 500 вместо 400;
4. **тест доступа был бы бессмысленным**: тестовый коллега получал все роли владельца, включая
   `cases.assign`, то есть видел все дела тенанта, и правило участников не проверялось вовсе. Роль
   заменена на обычного сотрудника (`EMPLOYEE`).

**Проверено:** `CaseModelIT` — **6 сценариев** (номер дела, владелец и первая запись истории; тип дела
и его требования; документы в деле; последовательность номеров; статистика только по видимым делам;
отказ создать дело без названия) и `CaseAccessIT` — **8 сценариев** (коллега без доступа не видит
ничего; владелец видит своё; READ не даёт выдавать доступ; WRITE даёт; отзыв действительно отзывает,
а запись остаётся; чужой тенант не видит; владельца нельзя удалить; дубликат участника отклонён;
внешний контакт без учётной записи).

**Итог:** `./mvnw -B clean verify` → **BUILD SUCCESS**, тестов **182** (89 unit + 93 integration).

### C-002 · Жизненный цикл дела — DONE

Реализовано: `CaseStatusMachine`, `CaseLifecycleService`, эндпоинты
`POST /api/v1/cases/{id}/status` и `GET /api/v1/cases/{id}/lifecycle`.

Ключевое правило: **дело не закрывается случайно**. Закрытие означает, что вопрос решён, и платформа
отказывается это утверждать, пока работа открыта — незавершённая задача или обязательная по типу дела
 Unterlage, которую никто не приложил.

Что именно проверяется при закрытии:
- **ложное утверждение отклоняется безусловно**: закрыть дело с причиной «результат достигнут», когда
  обязательства открыты, нельзя ни при каком подтверждении. Платформа видит, что это неправда, и
  записывать это в историю нельзя — иначе история дела начнёт лгать;
- **молчаливое закрытие отклоняется**: при открытых обязательствах нужно явное подтверждение;
- **подтверждение без объяснения — не решение**: нужна заметка словами, иначе через три месяца никто
  не сможет разобрать, почему дело закрыли;
- **подтверждение и заметка попадают в историю**: вопрос «кто закрыл это вопреки открытой работе и
  почему» задаётся именно после.

Переходы выписаны явно, а не выведены из названий состояний: новое дело нельзя перевести сразу в
`COMPLETED` (не было работы), к ожиданию согласования нельзя перейти из `NEW`, а из `CLOSED` есть
ровно один выход — `REOPENED`. Повторное открытие требует причины и **очищает дату закрытия**: схема
связывает `closed_at` с закрытыми состояниями, и дата закрытия, которую можно снять молча, ничего не
значит.

**Найденные дефекты:**
1. сущность `CaseEvent` была приведена к схеме в C-001, но ответ API отдавал метаданные под именем
   `payload`, а история — под `summary`; имена приведены к смыслу (`metadata`, `title`, `description`);
2. тест истории опирался на позицию записи в списке, а два события одной транзакции могут иметь
   одинаковое время — проверка переведена на выбор по типу записи.

**Проверено:** `CaseLifecycleTest` — **8 тестов** (новое дело не перепрыгивает работу; ожидающие
состояния взаимозаменяемы; из закрытого только переоткрытие; классификация состояний; отказ называет
оба состояния; переход в то же состояние отклонён; разбор причин закрытия; из каждого состояния есть
выход) и `CaseLifecycleIT` — **8 сценариев** (ложное «достигнуто» отклонено; молчаливое закрытие
отклонено; подтверждение без заметки отклонено; осознанное закрытие проходит и попадает в историю
вместе с пояснением; незавершённая задача блокирует закрытие так же, как документ; переоткрытие
требует причины и очищает дату; невозможный переход отклонён с указанием состояний; обзор жизненного
цикла предлагает только достижимые состояния).

**Итог:** `./mvnw -B clean verify` → **BUILD SUCCESS**, тестов **198** (97 unit + 101 integration).

### C-003 · Задачи: поля, исполнители, чек-листы, комментарии — DONE

Реализовано: `Task`, `TaskAssignee`, `TaskChecklistItem`, `TaskComment` с репозиториями, `TaskService`,
`TaskController` (`/api/v1/tasks`, `/assignment-queue`, `/statistics`, назначение, чек-лист,
комментарии, завершение, согласование, статусы).

Два правила несут основную смысловую нагрузку:
- **задача без исполнителя — не «ничья» задача**: она сохраняет `assignment_pending` и попадает в
  очередь ручного распределения, отсортированную по сроку. Работа, которая молча никому не
  принадлежит, обнаруживается слишком поздно — приёмка выполнена буквально, очередь стала отдельным
  эндпоинтом, а не фильтром, о котором клиент должен догадываться;
- **«готово» означает одно и то же для всех**: задача завершается только тогда, когда сформулирован
  критерий завершения и отмечены обязательные пункты чек-листа. Иначе статус был бы мнением, а
  история дела записывала бы мнения как факты.

Отдельные решения:
- **наблюдатель не делает задачу назначенной**: роль WATCHER не снимает `assignment_pending`, иначе
  задача выглядела бы назначенной, оставаясь ничьей;
- **снятие последнего исполнителя возвращает задачу в очередь**;
- **блокировка без причины отклоняется** — заблокированную задачу иначе никто не сможет разблокировать;
- **отмена требует причины**;
- **завершение при открытых обязательных пунктах возможно только с подтверждением и заметкой** —
  тот же шлюз, что и в жизненном цикле дела (C-002), и он так же записывается в метаданные задачи;
- **задача с согласованием не завершается до согласования** — отдельное право `tasks.approve`;
- **комментарии различают внутренние и внешние**: одна лента сделала бы это решение неявным, а
  неверная догадка отправила бы внутреннюю заметку контрагенту; удаление комментария помечает его,
  а не вырывает из ветки.

**Найденные дефекты:**
1. `startedAt` не отдавался в ответе API, хотя назначается при передаче задачи исполнителю;
2. `TaskService.complete` собирал метаданные, теряя уже сохранённые другой стадией — запись о
   завершении теперь вливается в существующие метаданные, а не заменяет их;
3. тест очереди передавал `null` вместо идентификатора коллеги: вспомогательный метод возвращал
   созданного пользователя, а тест его игнорировал — на этом и выяснилось, что 500 вместо 201
   приходит из `UUID.fromString("null")`.

**Проверено:** `TaskCrudIT` — **10 сценариев** (поля задачи; назначение снимает из очереди и
запускает работу; наблюдатель не снимает; чек-лист можно отметить и снять; без критерия завершения
завершить нельзя; открытый обязательный пункт блокирует и требует заметки; согласование обязательно,
если настроено; блокировка без причины отклонена; комментарии различают внутренние; без названия
задача не создаётся) и `TaskAssignmentQueueIT` — **6 сценариев** (задача без исполнителя в очереди;
очередь упорядочена по сроку, задачи без срока — в конце; назначение убирает из очереди; снятие
последнего исполнителя возвращает; без права `tasks.assign` очередь недоступна; отменённая задача
не ждёт распределения).

**Итог:** `./mvnw -B clean verify` → **BUILD SUCCESS**, тестов **214** (97 unit + 117 integration).

### C-004 · Типизированные сроки и реестр правовых правил — DONE

Реализовано: `DeadlineCalculator`, `DeadlineRule` + репозиторий, `TaskDeadline` + репозиторий,
`DeadlineService`, `DeadlineController`.

**Главное решение — реестр правил поставляется пустым.** Срок — юридическое утверждение, и платформа,
которая привозит с собой придуманные периоды, выдаёт даты, выглядящие авторитетно и не являющиеся
такими. Правила вносит тот, кто эксплуатирует платформу, из своего источника, и подтверждает их. Это
прямая реализация требования «не выдумывать юридические правила»: у платформы их просто нет.

Из этого следует разделение, которое схема уже предусматривала (`ASSUMED_LEGAL` / `CONFIRMED_LEGAL`):
- срок, посчитанный от **проверенного** правила → `CONFIRMED_LEGAL`;
- срок от **непроверенного** правила → `ASSUMED_LEGAL` с `requires_verification`, и пояснение прямо
  говорит, что дата не подтверждена.

Отказаться считать вовсе было бы хуже: пользователь, которому нельзя записать предварительную дату,
не записывает ничего, а дело без даты — это пропущенный срок. Недопустимо другое — чтобы
предварительная дата выглядела подтверждённой.

Ещё решения:
- **внесение и подтверждение правила — два разных действия**: правило никогда не создаётся проверенным,
  иначе флаг проверки ничего не значит;
- **правило без указанного источника нельзя подтвердить** — подтверждать нечего, и «проверено»
  означало бы лишь «кто-то нажал»;
- **вычислитель не знает юридических правил**: он только считает. Календарные дни — арифметика;
  рабочие дни пропускают выходные и записанные праздники; месяцы и годы — календарные единицы, и
  режим счёта их не меняет (иначе «два месяца» тихо превратились бы в другой период);
- **начальная дата не считается частью периода**; начинает ли счёт следующий день — решает правило
  через `start_event`, а не код;
- **срок всегда принадлежит задаче**: сроки дела — это сроки его задач, и схема это фиксирует
  (`task_deadlines.task_id NOT NULL`).

**Найденные дефекты:**
1. `deadline_rules.valid_from` и `task_deadlines.task_id` — NOT NULL, а код их не заполнял; второе
   вскрыло содержательную ошибку: срок «на дело» без задачи — это дата, к которой никто не работает.
   Сроки дела теперь собираются через его задачи;
2. эндпоинты были защищены правами `deadlines.view/verify/manage`, **которых в сиде нет** — то есть
   API был бы недоступен никому. Привязано к существующим `settings.manage_rules`, `cases.*`,
   `tasks.*`;
3. две ошибки в моих собственных ожиданиях в тестах вычислителя: я забыл праздник в наборе и неверно
   посчитал десять рабочих дней. Код был прав — исправлены тесты, и оба случая теперь описаны
   комментарием, потому что они неочевидны.

**Проверено:** `DeadlineCalculatorTest` — **11 тестов** (календарные дни; рабочие дни; праздник
сдвигает срок ровно на день; начальная дата не считается; месяцы и годы как календарные единицы;
недели в рабочих днях; распознавание нерабочих дней; счёт рабочих дней между датами; отказ при
невозможном периоде; завершаемость длинного периода; календарные дни без календаря праздников) и
`DeadlineRuleIT` — **9 сценариев** (реестр пуст; непроверенное правило даёт предположение;
проверенное — подтверждённый срок; правило без источника не подтверждается; правило без периода
отклонено; непроверенные даты попадают в список; ручной срок внутренний и без юридических притязаний;
неизвестное правило — not found; без начальной даты срок не считается).

### C-005 · Календарь и производственный календарь — DONE

Реализовано: `EasterCalculator`, `HolidayCalendar`, `Holiday` с репозиториями,
`HolidayCalendarService`, `HolidayCalendarController`, миграция V20 (RLS).

Ключевое решение: **платформа не утверждает, какие дни являются праздниками.** Это решается законом,
различается по странам и регионам и меняется; встроенный список был бы неверен где-то с момента
написания и молча неверен везде, где его не проверили. Календарь — контейнер, который наполняет
оператор из своего источника.

Единственное, что платформа считает сама, — **дата Пасхи** (алгоритм Meeus/Jones/Butcher) и смещения
подвижных праздников от неё. Это арифметика, а не право: даты проверяемы по любому календарю.
Поэтому подвижные даты отдаются как **кандидаты** с указанием смещения и прямым текстом «Rechenergebnis,
kein gesetzlicher Feiertag» — какие из них соблюдаются в регионе, решает человек, а не платформа.

Уточнение по факту: в сиде **уже был** системный календарь `de-national` с пятью общенациональными
праздниками за 2026–2027 (Neujahr, Tag der Arbeit, Tag der Deutschen Einheit, beide Weihnachtstage),
и он же — календарь по умолчанию. Подвижных праздников в нём нет — это согласуется с решением выше.
Данные покрывают два года, то есть устаревают, и обновлять их — работа оператора.

**Второй найденный дефект — запись в общие справочные данные.** Создание своего календаря по
умолчанию снимало флаг `is_default` **у системного календаря**, то есть один тенант менял справочные
данные всем остальным. Теперь свой календарь тенанта **перекрывает** системный, а не выключает его:
`findByTenantIdAndDefaultCalendarTrue` для своих, `findByTenantIdIsNullAndDefaultCalendarTrue` как
запасной вариант. Тенант без своего календаря получает системный — это разница между учётом
праздников и молчаливым их игнорированием.

Этот дефект нашёлся только на CI: локальная тестовая база была испорчена предыдущими прогонами
(системный календарь уже потерял флаг), поэтому локально тест «проходил». Свежая база в CI показала
истинное поведение.

**Найденный дефект — дыра в изоляции тенантов.** `holiday_calendars` и `holidays` **не были под RLS**,
в отличие от всех остальных таблиц тенанта, которые V13 закрыла с `FORCE ROW LEVEL SECURITY`. Без

Граница, ради которой эта задача существует, — между **обнаруженным текстом** и **юридической

- платформа **вправе** прочитать условие из документа и сохранить его слова вместе со страницей и

Поэтому условие без фрагмента **отклоняется**: условие, которое нельзя проверить, придётся принимать
на веру. А интерпретация хранится только с указанием основания, и API **не подставляет основание по
умолчанию** — именно эта тишина и есть путь к тому, чтобы платформа начала высказывать собственные
юридические выводы.

нужное правило:

  строки, которые база отклоняет;

- `CHECK (interpretation IS NULL OR interpretation_verified_at IS NOT NULL OR interpretation_source = 'RULE')`

  интерпретация правила**. Код приведён к этому правилу: вывод человека записывается как его
  собственный и подтверждается тем же действием, вывод правила ждёт проверки. Это и есть состояние,
  ради которого существует список на проверку.

### D-002 · Обязательства, продления и сравнение версий — DONE

Реализовано: миграция V21 (`contract_clauses.version_id`), `ContractDiff`, `ContractVersion`,

**Изменение условия в новой версии видно пользователю.** Сравнение — чистая функция над двумя
наборами формулировок, и это осознанно: интересен не вопрос «файл изменился», а «какое условие
изменилось и с чего на что». Сравнение идёт **по ключу пункта**, поэтому переименованный заголовок —
это смена заголовка, а не исчезновение одного пункта и появление другого (что скрыло бы ровно то
изменение, которое человек ищет). Переформатированный текст не считается изменением: документ,
пересохранённый с другой разметкой, не менял условий, и сообщать об этом значило бы похоронить
настоящее изменение под шумом.

Значимость изменения платформа помечает **только по критичности самого пункта**, никогда по
юридической оценке: она не читает закон.

его дело. Напоминание становится **задачей** через модуль задач, поэтому оно появляется в списке и в
очереди распределения, если ответственный не назван. Обязательство без ответственного **не назначается
наугад**: задача уходит в ручное распределение. Просроченное обязательство помечается `MISSED`,

### D-003 · Входящие счета и проверка — DONE

Реализовано: `InvoiceValidation` (чистый движок), `Invoice`, `InvoiceLine`, `Supplier` с
репозиториями, `InvoiceService`.

Ключевые решения — два разных по последствиям вида находок:

- **арифметика**: если позиции не сходятся с указанным итогом, счёт помечается `BLOCKED`.
  Платформа **не исправляет** счёт: исправленный счёт — документ, отличающийся от бумаги, а платят
  по бумаге. Оба числа показываются рядом, решение принимает человек;
- **банковские реквизиты**: если счёт просит перевести деньги на счёт, которого у поставщика раньше
  не было, это **блокирует автопроведение**, а не просто отмечается. Это самый распространённый способ
  мошенничества со счетами, и предупреждение, которое можно закрыть кликом, — не контроль;
- **первый счёт поставщика не подозрителен**: `IBAN_FIRST_SEEN` уровня `INFO`, потому что сравнивать
  не с чем. Выдумывать подозрение там, где нет предмета сравнения, значит приучать пользователя
  игнорировать предупреждение, которое важно;
- **подтверждение снимает тревогу**: только человек, подтвердивший новый счёт, делает его известным —
  иначе предупреждение никогда не снимется, и его перестанут читать;
- **одна и та же запись реквизитов в разном формате — не изменение**: пробелы и регистр это то, как
  банки печатают IBAN;
- **дубликат по поставщику и номеру отклоняется**;
- **ни одно налоговое правило не применяется**: платформа складывает написанное на счёте и сравнивает
  с тем, что на счёте указано. Допуск на округление — настройка арендатора, а не выдуманная величина.

**Найденные дефекты:**
1. `suppliers.email` — тип `citext`, Hibernate отказывался валидировать строковое поле; поле убрано
   из сущности (адрес доступен через контакт);
2. `findByTenantIdAndValidationStateContaining` **не работает на jsonb** — производный запрос не может
   заглянуть внутрь документа; заменён на нативный с `validation_state ->> 'state'`;
3. `suppliers.default_currency` обязателен, и Hibernate включает колонку в INSERT, поэтому умолчание
   базы не применяется — третий раз за два раунда один и тот же класс ошибки;
4. **мой тест использовал вымышленный тенант** — внешний ключ справедливо отклонил вставку;
5. **мой тест «расхождение сумм» ничего не проверял**: помощник ставил одну и ту же сумму и в позицию,
   и в итог, поэтому расхождения не возникало. Исправлено явным запросом, и это уже четвёртый случай

### D-004 · Согласования и платёжные задачи — DONE

Реализовано: `Approval`, `Payment`, `PaymentApproval`, `PaymentApprovalRule` с репозиториями,
`PaymentApprovalService`.

**Платёж не исполняется без подтверждения уполномоченной персоны.** Подготовка и подтверждение — два
разных действия по замыслу: платформа может посчитать, что следует оплатить, а человек решает,
оплачивать ли. Пути от подготовленного платежа к исполненному минуя человека **нет**, и это покрыто
тестом. Решающий обязан обладать ролью или правом, которые называет правило: кнопка «одобрить»,
которую может нажать любой, — не контроль.

**Повторное подтверждение не дублирует операцию.** Платёж несёт ключ, выведенный из того, что
оплачивается (счёт + сумма + валюта), поэтому второе подтверждение **находит первый платёж**, а не
создаёт второй. Ключ не зависит от идентификатора запроса — значит защищает и от двух сессий,
подготовивших одно и то же независимо друг от друга. Оплатить поставщика дважды из-за повторного
запроса браузера — ровно та ошибка, которую это исключает.

Ещё решения:
- **схема требует, чтобы у `SKIPPED` не было решающего**: пропуск — не решение, и записывать против
  него чью-то подпись значило бы приписать человеку решение, которого он не принимал;
- **проверка прав «fail closed»**: правило, не называющее ни роль, ни право, иначе пропускало бы всех,
  потому что оба условия становятся «нет требований». Базовое право — `finance.approve`;
- **отказ на одной ступени останавливает платёж** и помечает остальные ступени пропущенными, а не
  оставляет платёж ждать остальных;
- **четыре глаза означают две разные персоны**, и вторая проверяется по уже записанным решениям;
- **пороги, роли и число ступеней берутся из правил арендатора** — ни одно финансовое правило не
  выдумано; автоматическое исполнение в базовой конфигурации **выключено**, и это проверяется тестом.

**Найденные дефекты:**
1. `payment_approval_rules.name` — jsonb, а не строка (локализованное имя), четвёртый такой случай;
2. **проверка прав пропускала всех**, когда правило не называло ни роль, ни право — «fail open».
   Исправлено на «fail closed» с базовым правом;
3. **схема требует, чтобы `SKIPPED` не имел решающего** — мой код записывал его, и вставка падала;
   это не придирка схемы, а содержательное правило;
4. мой тест выдумывал `invoice_id`, и внешний ключ справедливо отклонил вставку;
5. мой тест искал в сообщении «berechtigt**e** Person», тогда как сообщение говорит
   «berechtigt**en** Person» — проверка опиралась на падеж одного слова вместо поведения.

**Проверено:** `ApprovalFlowIT` — **8 сценариев** (подготовленный платёж ждёт и не исполняется;
одобрение подтверждает и только тогда исполняет; без права — отказ; ниже порога правило не
применяется, но человек всё равно нужен; четыре глаза требуют двух персон; отказ останавливает платёж;
решённую ступень нельзя решить дважды; автоматическое исполнение выключено и порог не выдуман) и

отклонена).

### D-005 · E-Rechnung: XRechnung und ZUGFeRD — DONE

Реализовано: `EInvoiceParser` (UBL и CII), `ZugferdExtractor`.

**PDF без XML — не электронная реклама-счёт.** Приёмка выполнена буквально: PDF, несущий только
печатное представление, — это картинка счёта, а не счёт. Платформа, которая приняла бы любой PDF за
E-Rechnung, молча потеряла бы машиночитаемую половину — ту самую, ради которой электронный счёт и
нужен.

**Исходный XML сохраняется неизменным** (проверено побайтовым сравнением в тесте): читается то, что
есть, ничего не переписывается.

Оба синтаксиса одного европейского стандарта: **UBL** (XRechnung) и **CII** (ZUGFeRD/Factur-X).
Синтаксис определяется **корневым элементом**, а не именем файла.

Ключевые решения:
- **поиск по локальным именам, а не по URI пространства имён**: стандарт пересматривался, и
  пространства имён переезжали; привязка к URI означала бы отказ от совершенно корректных файлов
  другой минорной версии. Корневой элемент при этом проверяется, поэтому посторонний XML получает
  честный ответ «не электронная реклама-счёт», а не полупрочитанный результат;
- **DTD, внешние сущности и схемы отключены**: счёт поставщика — недоверенный ввод, и чтение его не
  должно становиться способом прочитать файлы сервера (проверено тестом с `file:///etc/passwd`);
- **непрочитанные элементы называются**, а не отбрасываются: пользователь, сверяющий запись с файлом,
  должен видеть, что именно платформа не смотрела;
- **отсутствующее поле остаётся отсутствующим**: `missingRequiredFields()` называет, чего не хватает,
  и ни одно значение не выдумывается;
- вложения ZUGFeRD определяются **по содержимому**, а не по имени файла: поставщик может назвать
  вложение как угодно, а имя «invoice.xml» с посторонним содержимым счётом не является.

**Найденные дефекты (все — мои):**
1. `null` в varargs пути элементов — падение при разборе;
2. **`text(...)` ходит по пути, а я использовал его как «любое из имён»** для `InvoicedQuantity` /
   `CreditedQuantity`; поле молча оставалось пустым. Добавлен отдельный помощник — разница между «путь»
   и «альтернатива» неочевидна, и это стоило отдельной ошибки;
3. атрибуты (`unitCode`) читаются ещё и по локальному имени: у одного и того же атрибута
   квалифицированное имя различается между ревизиями;
4. обход вложенных файлов переписан на API PDFBox 3 (`getNames()` возвращает `Map` и бросает
   `IOException`).

**Проверено:** `XRechnungParseTest` — **12 тестов**, `ZugferdExtractTest` — **5 тестов**,
`EInvoiceValidationTest` — **10 тестов** (в том числе ветка CII, у которой до этого не было теста:

### D-006 · Исходящие счета — DONE

Реализовано: `InvoiceNumberSequence` + репозиторий, `InvoiceNumberService`,
`PartialPaymentService`, `InvoicePdfRenderer`.

**Нумерация без пропусков и дублей** — оба свойства из одного решения: номер берётся **внутри
транзакции**, создающей счёт, а строка последовательности блокируется `FOR UPDATE`.

| Свойство | Как достигается |
|---|---|
| Без дублей | Блокировка строки: два одновременных счёта получают разные номера |
| Без пропусков | Счётчик — **строка таблицы, а не последовательность PostgreSQL**: последовательность не откатывается, и неудавшийся счёт оставил бы дыру |

Дыра в ряду номеров — не косметика: аудитор спрашивает о пропущенных номерах, и «транзакция упала» —
ответ, который платформа должна делать ненужным. Метода «зарезервировать» **намеренно нет**: либо счёт
записывается в той же транзакции, либо номер не берётся.

**Настоящий дефект, найденный тестом:** `recordExternalPayment` принимал `null` вместо пользователя,
поэтому **исполненный платёж можно было записать без подтвердившего лица**. Схема отказала — она
требует, чтобы у исполненного платежа был подтвердивший, — но с непонятным сообщением об ограничении.
Это то же правило, что в D-004 («нет платежа без человека»), и оно было достижимо через путь D-006.
Теперь отказ явный, с сообщением, называющим правило.

Остальные решения:
- **состояние оплаты выводится из сумм**, а не задаётся вызывающим: статус, который можно выставить
  независимо от денег, рано или поздно будет неверным;
- **переплата фиксируется как переплата**, а не как «оплачено»: кредит, о котором клиент спросит, —
  не закрытый счёт;
- **подготовленный платёж не меняет оплаченное**; валюта, отличная от валюты счёта, отклоняется —
  платформа не пересчитывает курсы;
- **неоплаченный счёт сохраняет более информативный статус**, чем «не оплачен» (это верно почти для
  всего);
- **PDF печатает то, что записано, и ничего не вычисляет**: рендерер, пересчитывающий итог, был бы
  второй реализацией арифметики, и однажды они разошлись бы — в документе, который получает клиент.
  Сторнированный счёт **помечается**, а не скрывается; частично оплаченный показывает остаток.

### D-007 · Банковские данные и сверка — DONE

Реализовано: `CamtParser` (CAMT.053), `PaymentMatchingService`.

**Неоднозначное сопоставление не проводится автоматически** — и это определяет всю конструкцию.
Сопоставление делается само **только когда возможен ровно один партнёр**: один счёт с таким номером,
или один открытый счёт с точно такой суммой, когда номер не указан. Как только подойти могут два
счёта, платформа **предлагает, а решает человек** — потому что неверно сверенный платёж хуже
несверенного: он закрывает счёт, который ещё открыт, и прячет тот, который действительно оплатили.

**Знак платежа** — то место, где такие парсеры ломаются чаще всего. CAMT указывает сумму всегда
положительной, а направление — отдельным признаком `CRDT`/`DBIT`. Читатель, игнорирующий признак,
превращает каждый исходящий платёж в доход. Признак решает знак, и это покрыто тестом.

**Банковские креденшелы не хранятся открыто**: схема держит **ссылку** (`credential_ref`) на секрет,
лежащий вне платформы, и сервис отказывает тому, что похоже на сам секрет, — правило в документе
никого не остановит от вставки пароля.

Остальные решения:
- **исходящее бронирование не сопоставляется со счётом клиента**: ушедшие деньги не закрывают счёт;
- **повторный импорт пересекающихся периодов не считает бронирование дважды**;
- **выписка для другого счёта отклоняется** — иначе сверялись бы не те деньги;
- **файл выписки сохраняется** как исходный документ: сверку, о которой спросят позже, нужно
  проверять по тому, что прислал банк.

**Найденные дефекты (все — мои):**
1. **эвристика креденшелов отвергла `vault://bank/main`** — то есть канонический формат ссылки. Правило,
   запрещающее правильный ответ, — не защита, а препятствие, которое подталкивает пользователя вставить
   пароль, то есть прямо противоположное приёмке. Теперь явная схема ссылки разрешена, а судится
   остальное;
2. **подтверждение предложения вставляло вторую запись** `payment_matches`, и уникальный ключ справедливо
   отказал; предложение теперь **становится** подтверждением;
3. `case when ?` получил UUID вместо boolean — PostgreSQL отказал («argument of CASE/WHEN must be type
   boolean»);
4. **две предпосылки в моих тестах были неверны**: тест отклонения предложения не создавал ситуации
   выбора (сопоставление проходило автоматически), а тест чужого счёта ожидал не тот тип исключения.

### D-008 · Отчёты и аналитика — DONE

Реализовано: `ReportService`. Метрики §26 для двух аудиторий — частных лиц и компаний.

**Каждая метрика несёт период и фильтры** — это свойство типа, а не намерение. `Metric` содержит
`period`, `filters` и `origin` (из каких таблиц значение посчитано), поэтому **вызывающий физически не
может отрисовать число без контекста, который делает его осмысленным**. «12 просроченных задач» без
указания, на какую дату и для кого, — не метрика, а слух.

**Приблизительные значения не выдаются за точные финансовые показатели.** Метрика объявляет, точная
она или нет, и если нет — **говорит почему, фразой, которую пользователь может прочитать**. Время
обработки измеряется по временным меткам платформы, а не по моменту, когда работа действительно
произошла (ответ по почте в него не входит), поэтому оно помечено как приблизительное. Записанные
денежные суммы — точная арифметика и **не помечаются**. Тест отдельно проверяет, что ни одна
приблизительная метрика не выражается в евро: приблизительное число в валюте — это и есть та самая
подмена, против которой написана спецификация.

**Данные разных арендаторов не смешиваются**, и за это отвечает RLS, а не код: тест спрашивает отчёт
одного арендатора, назвав идентификатор другого, и получает нули. Сравнения между арендаторами нет —
для него не существует параметра.

### E-001 · Integration Hub: ядро и хранилище токенов — DONE

Реализовано: `CredentialCipher`, `IntegrationService`.

**Токены хранятся зашифрованными.** AES-256-GCM, ключ из конфигурации. Тест читает **байты в базе**, а
не спрашивает сервис, зашифровал ли он: платформа, которая заявила бы о шифровании и не делала его,
прошла бы любую проверку, доверяющую её собственному ответу, — а это ровно тот случай, когда доверять
заявляющему и есть ошибка. Проверяется, что секрет не встречается ни в открытом виде, ни в base64.

**Отключённая интеграция не выполняет синхронизацию** — и проверка стоит в **единственном** методе,
который запускает прогон, а не в каждом вызывающем: охрана, о которой должны помнить вызывающие, будет
забыта. Отключённая интеграция **не выдаёт и свои креденшелы** — иначе «отключена» означала бы лишь
«не запланирована».

Два решения о шифровании:
- **ключ обязателен и не имеет значения по умолчанию.** Запасной ключ зашифровал бы секреты всех
  развёртываний одним известным значением, и никто бы не заметил, пока это не станет важно;
- **шифротекст привязан к месту.** Идентификаторы арендатора и интеграции используются как associated
  data, поэтому украденную полезную нагрузку **нельзя переставить в строку другого арендатора и
  расшифровать там**. Шифрование без такой привязки защищает байты, но не их смысл;
- **nonce свежий для каждого шифрования**: повтор nonce в GCM не ослабляет шифрование, а ломает его;
- **все поля креденшела едут одной нагрузкой**: токен осмыслен только вместе с refresh-токеном, и
  раздельные строки позволили бы повернуть половину.

**Найденные дефекты — и это восьмой раз, когда схема поправила мой словарь:**

**Я проверил имена колонок — и не проверил значения enum.** После прошлого раунда я записал «проверять
каждое имя, которое пишу, включая внутри SQL» и применил это к именам. Но `integration_sync_runs.status`
допускает `RUNNING/SUCCESS/PARTIAL/FAILED/CANCELLED`, а я написал `STARTED` и `COMPLETED`; `run_type`
допускает `FULL/INCREMENTAL/WEBHOOK/MANUAL/RETRY`, а я написал `SCHEDULED`. **Ограничение CHECK — это
тоже схема, и его значения надо читать так же, как имена колонок.**

Ещё:
- `describe()` выпускал `EmptyResultDataAccessException` вместо «не найдено» — реальный пробел: вызывающий
  получал исключение базы вместо понятного ответа;
- мои тесты ждали camelCase там, где карта — проекция строки БД с именами колонок;
- моё утверждение о привязке шифротекста было неверным: расшифровка с чужим идентификатором интеграции
  должна **падать**, а не возвращать другое значение — именно это привязка и означает.

**Проверено:** `CredentialEncryptionTest` — **9 тестов** (сохранённые байты не содержат секрета ни в
каком кодировании; секрет возвращается неизменным; шифротекст привязан к арендатору **и** к интеграции;

### E-002 · Почтовый центр и отправка — DONE

Реализовано: `DeliverySemantics`, `OutboundMessageService`, `OutboundSender` + `SmtpOutboundSender`.

**Письмо не отправляется автоматически в ответ на входящее без подтверждения.** Это самая
соблазнительная автоматизация во всём продукте и самая разрушительная: ответ, ушедший без того, чтобы
человек его прочитал, может связать компанию. Пути от черновика к отправке, минуя подтверждение, нет, и
подтверждение записывает, кто его дал. Тест строит именно тот случай, который хочется отправить
автоматически — черновик с темой «Re: …», — и проверяет, что он **не уходит**, а письмо в тестовом
SMTP-сервере не появляется.

**Факт передачи провайдеру не выдаётся за вручение.** Отправка записывает `ACCEPTED_BY_PROVIDER` с
`proves_delivery = false` и оставляет сообщение в `SENT`; дальше его двигает только событие, доказывающее
доставку. Схема говорит то же самое своим ограничением (`NOT proves_delivery OR event_type IN
('DELIVERED','READ','REPLIED')`), и код с ней согласован — платформа не может даже попытаться записать
то, что схема отвергла бы.

Ключевые решения:
- **формулировки — часть контракта.** Для `SENT` описание говорит «an den Dienst übergeben; eine
  Zustellung ist damit nicht bestätigt», и тест проверяет, что слово «zugestellt» там **не появляется**.
  Платформа, показавшая «доставлено» в момент передачи, сказала бы пользователю то, чего не знает, — и
  пользователь перестал бы выяснять судьбу письма, которое не дошло;
- **`provesDelivery` выводится, а не передаётся**: вызывающий, который мог бы его задать, рано или
  поздно задал бы неверно;
- **доказанная доставка не понижается** последующим событием: отскок, пришедший после подтверждения
  доставки, относится к чему-то другому, и возврат статуса назад потерял бы факт, что письмо дошло;
- **сохраняется финальная версия, а не черновик**: отправленное письмо — доказательство, и то, что
  ушло, должно восстанавливаться ровно таким, каким ушло. Тест проверяет, что черновик и финальная
  версия хранятся раздельно;
- **повторная передача невозможна**: получатель не должен получить письмо дважды;
- **юридическая доставка не утверждается никогда**: `supportsLegalServiceClaim` возвращает `false` для
  любого статуса. Это метод, а не отсутствие метода, — чтобы вызывающий, задавший вопрос, получил ответ,
  а не выдумал свой.

**Найденные дефекты:**
1. **защита от понижения статуса стояла только в одной ветке** — отскок после доказанной доставки всё
   равно откатывал сообщение назад. Настоящая ошибка: правило общее, а не частное;
2. `describe()` выпускал исключение базы вместо «не найдено» — исправлено на `ApiException`, как в E-001;
3. мой тест не типизировал карту (`Map<?, ?>` не принимает строковые ключи в `containsEntry`);
4. знакомый сбой: `maven-clean-plugin` не смог удалить `target` — потребовалась ручная очистка.

**Проверено:** `DeliveryStatusSemanticsTest` — **12 тестов** (принятие провайдером не доставка; ровно три
события доказывают доставку, как в схеме; передача оставляет `SENT` и формулировка говорит о
неподтверждённости; только доказывающее событие переводит в доставлено; **доставка не понижается**;
отскок и сбой различимы; **ответ не уходит без человека**; отправка защищена; юридическая доставка не
утверждается ни для одного статуса; смысл каждого события доступен; у каждого статуса есть читаемая
формулировка; повтор возвращает в очередь) и `OutboundSendIT` — **10 тестов** с реальным GreenMail
(ответ не уходит без подтверждения и письмо не появляется; одобренное действительно доходит до сервера;
**передача не отчитывается как доставка**; событие передачи не доказывает доставку; отчёт провайдера
переводит в доставлено; дважды не отправляется; подтверждение без человека отклонено; **финальная
версия сохранена отдельно от черновика**; черновики в списке; чужой арендатор не видит).

**Итог:** `./mvnw -B clean verify` → **BUILD SUCCESS**, тестов **496** (233 unit + 263 integration).

### B-013 · Приём документов из внешних источников (API/webhook) — DONE

Реализовано: `WebhookSignature`, `IngestService`.

**Повтор с тем же ключом не создаёт дубликат.** Уникальность обеспечивает **само ограничение**
`UNIQUE (tenant_id, idempotency_key)`, а не чтение-затем-запись в коде: два одновременных повтора оба
прошли бы проверку, а ограничение пропустит только один. Возврат существующего документа при повторе —
не побочный эффект, а суть: отправитель, повторивший запрос после тайм-аута, **не должен получить второй
документ**, иначе один и тот же счёт оплатят дважды.

**Неверная подпись → 401.** HMAC-SHA256 над `timestamp + "." + тело`. Тело и метка времени покрыты,
поэтому перехваченный запрос нельзя воспроизвести с другой нагрузкой; сравнение — **за постоянное
время**: сравнение, останавливающееся на первом различии, выдаёт, сколько байт угадано, и секрет
восстанавливается по достаточному числу ответов. Это единственное место в платформе, где обычный
`equals` был бы настоящей уязвимостью, а не вопросом стиля. Просроченная подпись отклоняется, **хотя она
подлинная**: старый запрос — это повтор.

Ещё: токен показывается один раз и хранится только хешем; ограничение частоты берётся из строки самого
токена, а не из глобальной константы; подпись проверяется **до** чтения тела, поэтому неудачная проверка
не оставляет следа частичного приёма.

**Дефекты — девятая серия исправлений от схемы, и она дала самое точное правило:**

| Что я написал | Что оказалось |
|---|---|
| `documents.has_attachments` | колонки нет вообще |
| `api_token_usages` | **таблицы не существует**; счётчик живёт в `rate_limit_counters` |
| — | `UNIQUE (tenant_id, content_hash)` — **уникальный индекс, а не ограничение**, поэтому его нет в `pg_constraint`, и искать надо в `pg_indexes` |
| — | индекс **частичный**: дубликаты определяются по содержимому, кроме помеченных `DUPLICATE` |
| `content_hash` = «hash-1» | требуется `^[0-9a-f]{64}$` |
| `Instant` в `timestamptz` | драйвер тип не выводит; нужен `Timestamp` |

**Правило:** не писать в SQL **ни одного идентификатора**, не прочитанного из базы в этой сессии,
включая имена таблиц, и читать **все** ограничения таблицы — CHECK, UNIQUE, **уникальные индексы** — до
вставки. «Проверить схему» было слишком слабой формулировкой: каждый раз я проверял одну её часть и
считал, что проверил всю.

### B-014 · Почтовый приём (IMAP + адаптеры M365/Gmail) — DONE

Реализовано: `MailAccountService`, `ImapMailIngester` (протокол IMAP).

**Письмо с вложением создаёт документ**, и путь намеренно тот же, что у загрузки: вложение становится
документом с **хешем собственных байтов**, поэтому существующее обнаружение дубликатов работает и для
почты. Вторая копия того же счёта, пришедшая письмом, отклоняется тем же уникальным индексом, что и
вторая загрузка — тест это проверяет: два письма с одинаковым вложением дают **один** документ.

**Пароли ящиков не хранятся открыто**: пароль проходит через тот же `CredentialCipher`, что и в
интеграциях (E-001), привязанный к арендатору и к почтовому ящику, поэтому украденную нагрузку нельзя
переставить в другую строку и расшифровать. Тест читает **сохранённую колонку**, а не спрашивает сервис.

Ещё решения:
- **ящик открывается только для чтения**: платформа читает почту, но не помечает письма прочитанными
  за владельца — это изменило бы то, что он видит в своём почтовом клиенте;
- **повторное чтение ящика — норма, а не ошибка**: уже сохранённое письмо пропускается;
- **пустой ящик и недоступный ящик — разные вещи**, и пользователь должен их различать;
- **проверка имени хоста TLS настраиваема**: по умолчанию **включена** (пароль, идущий к
  непроверенному серверу, — именно то, что нужно атакующему в сети), но у self-hosted серверов бывают
  сертификаты без нужного имени. Ослабляет её тест, явно, а не весь продукт по умолчанию.

**Найденные дефекты — и два из них содержательные:**

1. **Запись о неудаче откатывалась вместе с транзакцией.** Ошибка фиксировалась изнутри той же
   транзакции, которая затем падала, поэтому **сломанный ящик выглядел как никогда не пытавшийся**.
   Исправлено `REQUIRES_NEW`: отчёт о неудаче обязан пережить неудачу. Это тот класс ошибок, который в
   эксплуатации читается как «всё в порядке, просто пусто»;
2. **`connect()` вызывался без учётных данных** — хост и порт были настроены, а пароль не передан,
   поэтому соединение всегда падало с «no password specified»;
3. **MIME-тип не нормализовался**: серверы пишут его заглавными, и один и тот же тип появлялся в двух
   формах;
4. моя замена в файле **удалила конструктор**, оставив поля без присваивания;
5. `count == null ? 0 : count` имеет тип `Long`, а метод объявляет `int` — та же моя ошибка, что и в
   прошлом раунде.

### B-016 · Политики хранения, legal hold, архив — DONE

### E-005 · Абстракция AI-провайдера — DONE

Реализовано: `AiProvider` (порт), `AiLogRedaction`, `AiOrchestrator`.

**Отказ провайдера не ломает систему.** Каждый вызов идёт через circuit breaker и перебор
провайдеров: провайдер, отказавший подряд, **не вызывается снова** какое-то время, и пробуется следующий.
Если не ответил никто, задача помечается `FAILED` с кодом, и платформа продолжает работу —
**документ, который не удалось пересказать, это документ, который не удалось пересказать, а не сбой**.

**Ключи только на backend.** Они живут внутри реализации провайдера; ничто в оркестраторе **не может
их получить**, поэтому ничто ниже по потоку не может их выдать.

**В логах нет содержимого документов.** Это **нельзя** обеспечить тем, чтобы «помнить и не логировать»:
каждый промпт здесь строится из материалов дела, поэтому всё, что логирует промпт, логирует чьи-то дела.
Пишется задача, модель, длительность и стоимость; вход сводится к длине и хешу — достаточно, чтобы
различить два запроса при разборе сбоя, и бесполезно для чтения чужой почты.

**Бюджет проверяется до отправки**: узнать, что бюджет кончился, уже заплатив за ответ, — это не бюджет.
Спецификация требует отключаемости внешнего AI, и «выключено» означает, что **задача не происходит**, а
не что она тихо происходит в другом месте.

**Найденные дефекты — и первый стоил двух раундов:**

1. **Настройка читалась глобально, а не по арендатору.** Один арендатор, выключивший внешний AI,
   выключал его всем. В тестах же **оставшаяся глобальная строка от прошлого неудачного прогона**
   заставляла все последующие тесты возвращать `SKIPPED_DISABLED`. Это выглядело как «`recordRun` не
   сохраняет» — записи прогона были в порядке, оркестратор просто не доходил до них. **Я искал причину
   в коде сохранения, а она была в тестовой базе;**
2. **`Authorization: Basic <credential>`** — шаблон совпадал только до первого пробела и **оставлял
   учётные данные в логе**;
3. правило длины было примешано к `offendingFields`, который отвечает на другой вопрос, и сообщало о
   поле, не содержащем искомого текста вовсе;
4. `priority` — **integer**, а я написал слово `NORMAL`; `input` — **jsonb**, а я передал строку;
5. `on conflict (do nothing)` — синтаксис без скобок;
6. multi-catch двух исключений, одно из которых подкласс другого;
7. `SettingsService` только читает, и настройка глобальная — я предполагал и то, и другое иначе;
8. мой тест искал «Budget» с заглавной в сообщении «Monatsbudget» со строчной.

**Урок:** загрязнение общего состояния в тестах **переживает прогон** и выглядит как дефект кода. Тест,
пишущий глобальную строку, портит все последующие прогоны — и симптом указывает не туда.

**Проверено:** `AiProviderFailoverTest` — **8 тестов**, `AiBudgetLimitTest` — **5 тестов**,
`AiLogRedactionTest` — **9 тестов**.

### E-006 · Защита от prompt injection и безопасные инструменты — DONE

Реализовано: `UntrustedContent`, `InjectionDetector`, `ToolPolicy`, миграция **V22** (`ai_tool_settings`).

**Инструкции внутри документа не приводят к вызовам инструментов или раскрытию данных.** Это
**нельзя** обеспечить, попросив модель игнорировать их: промпт — это просьба, и вся проблема в том, что
модель можно убедить. Обеспечивается это решением **вне** модели: инструмент, имеющий эффект, **не
запускается по инициативе содержимого**, что бы в нём ни было написано и как бы убедительно это ни
выглядело. Четыре шлюза, каждый — отказ, а не предупреждение:

1. **происхождение** — read-only инструменты можно применять к документам (в этом смысл платформы),
   инструменты с эффектом — никогда по инициативе содержимого;
2. **allowlist** — инструмента нет в списке арендатора, значит его не существует; «не настроено» —
   это не «разрешено»: без строки доступны только безопасные инструменты;
3. **право** — модель, действующая за пользователя, действует **его правами и никакими другими**;
4. **подтверждение** — рискованное действие предлагает модель, выполняет человек.

**Детектор — не фильтр, и разница важна.** Молча вырезанный из документа текст — это текст, о котором
никто не знает: модель читает изменённый документ, пользователь видит неизменённый, а **факт попытки
теряется**. Содержимое передаётся без изменений, а находка сообщается — кодом, серьёзностью и короткой
выдержкой (≤120 символов: журнал, цитирующий абзац письма, хранит документы).

**Найденные дефекты — два содержательных:**

1. **Нейтрализация разделителя воспроизводила сам разделитель**: я заменял маркер на строку, которая
   его содержит, поэтому документ всё равно мог закрыть блок и продолжить «от имени платформы». Это
   ровно та атака, против которой разделитель и вводился;
2. **Шаблон эксфильтрации ловил только один порядок слов**: «Send the API key…» не находилось, потому

4. **RLS справедливо отклонил вставку** в `ai_tool_settings`: тесты не устанавливали контекст

**E-007** — AI-ассистент как интерфейс управления.

### E-007 · AI-ассистент как интерфейс управления — DONE

Реализовано: `AssistantService` (история — в существующих `ai_jobs`/`ai_model_runs`, миграция не нужна).

**Ассистент не видит данные чужих арендаторов.** Это обеспечивает не этот класс, а **RLS**, и сервис не
даёт способа её обойти: запрос чужого документа возвращает «не найдено» — **тот же ответ, что для
несуществующего**, потому что ассистент, различающий эти случаи, сообщает своему пользователю то, что
есть у другого арендатора. Параметра, которым можно назвать другой арендатор, не существует.

**Отправка, платёж и расторжение требуют явного подтверждения.** Ассистент **читает и предлагает**, но
не действует: инструмент с эффектом не выполняется по ходу разговора, он порождает **предложение с
идентификатором и предпросмотром**, а применение — **отдельный акт того же человека**. Проверяются три
условия, потому что каждое — способ обойти правило: подтверждает **тот же** человек (иначе один
действовал бы правами другого), **один раз** (иначе действие выполнится дважды), **в том же арендаторе**.

**История** хранит модель и версию инструкции, поэтому ход воспроизводим. Разговора она не хранит:
разговор — это документ.

**Найденные дефекты — и схема поправила не словарь, а два проектных решения:**

1. **`ai_jobs.job_type` называет вид работы** (`CHAT`, `SUMMARIZE`, `EXTRACT`) и **не может хранить имя
   инструмента** — CHECK отказал. Инструмент переехал во `input`, где и живёт остальной запрос. Это
   ошибка проектирования, а не подбор имени;
2. **я использовал `error_message` для хранения состояния** («ожидает подтверждения»). Это поле для

**E-008** — RAG: поиск и цитирование.

### E-008 · RAG: поиск и цитирование — DONE

Реализовано: `RetrievalService`, `RagService`.

**При отсутствии релевантных фрагментов ассистент сообщает об отсутствии данных.** Это критерий,
решающий, можно ли доверять всей функции. Модель, которую просят ответить без документов, **ответит
всё равно** — из обучения, из формулировки вопроса, из ничего, — и результат **читается точно так же,
как ответ из собственных дел**. Поэтому платформа **не спрашивает**: при пустом результате выше порога
релевантности она возвращает «не найдено», указывая, **что именно искала**, чтобы пользователь отличал
«такого документа нет» от «я не понял вопрос».

**Цитата обязана указывать на фрагмент, который действительно был найден.** Ответ с выдуманными
источниками хуже отсутствия ответа: он **проверяем в принципе и неверен по факту**. Каждая цитата
сопоставляется с результатом поиска до того, как ответ покинет класс; несовпавшая **удаляется и
считается** (`rejectedCitations`), а не отбрасывается молча.

Два источника: **текст страниц** (`document_pages`, с номером страницы — то, что человек прочитает) и
**извлечённые поля** (`document_extractions`, с фрагментом и страницей, откуда извлечение пришло).
Поэтому цитата из поля так же проверяема, как из текста.

**Порог релевантности** — именованная константа, а не магическое число: это суждение о том, когда
попадание перестаёт быть доказательством, и оно должно быть видимым и оспоримым. Поиск, который всегда
что-то возвращает, позволяет построить ответ **ни на чём**.

**Найденные дефекты:**
1. **порядок параметров в SQL**: `plainto_tsquery('german', ?)` стоит внутри cross join, то есть
   **первым**, а я передавал арендатора первым — PostgreSQL искал
   `plainto_tsquery(unknown, uuid)`, которой не существует. Мой вспомогательный `reorder` был костылём
   поверх этой ошибки и удалён вместе с ней;
2. **`document_pages.version_id` обязателен**: страница принадлежит версии документа, а версия —
   **блоку в хранилище**, и внешние ключи это требуют. Три уровня, которые я не предусмотрел;
3. **`document_extractions_provenance_chk`**: автоматически извлечённое значение **обязано нести
   фрагмент-источник** (`extractor <> 'MANUAL'` требует `source_snippet`). Это правило происхождения из
   B-009, и мой тест его нарушал. Схема здесь защищает ту же честность, что и весь RAG;
4. в моей правке число значений превысило число колонок — `source_snippet` не был добавлен в список.

**Проверено:** `RagCitationTest` — **9 тестов** (фрагмент найден и цитируется со страницей; **неверная
страница отклонена**; **документ вне результата поиска отклонён**; утверждение без источника не
поддержано; существующая, но не найденная страница не поддерживает утверждение; извлечённое поле
цитируется с фрагментом и страницей; результат поиска объясняет, что искали и что нашли; выдержка
ограничена; чужое поле не является источником) и `RagNoAnswerTest` — **9 тестов** (**нет совпадений —

### E-009 · Подготовка ответов и заявлений — DONE

Реализовано: `DraftValidation` (чистая библиотека).

**Документ с неподтверждёнными фактами помечается и требует проверки до отправки.** В этом весь смысл
класса: письмо, написанное по пересказу модели, **читается точно так же, как письмо, написанное по
документу**, и различить их может только платформа — потому что только она знает, какие предложения
пришли из документа.

**Платформа не выдумывает реквизиты.** Что должно быть в письме — это отчасти право, отчасти практика
конторы, и **ни того, ни другого код знать не может**. Поэтому тип документа **объявляет** свои
обязательные реквизиты, и чек-лист проверяет **их**. Платформа даёт механизм и один структурный
минимум — письму нужен адресат и предмет, — и это утверждение о переписке, а не о праве. Тест проверяет
буквально, что `structuralRequisites()` содержит ровно эти два пункта и ничего больше.

**Утверждение считается подтверждённым, когда его можно проследить** до документа или до человека.
Утверждение, которое породила модель, **не подтверждено, как бы правдоподобно оно ни выглядело**, и
**одного такого утверждения достаточно, чтобы остановить письмо**.

**Найденный дефект — и он был настоящим пробелом:** `Fact` — запись с **публичным каноническим
конструктором**, поэтому вызывающий мог создать утверждение модели с `confirmed = true`. Правило,
которое можно уговорить, — не правило. Теперь **источник решает, а не вызывающий**: компактный
конструктор записи принудительно снимает подтверждение с утверждения модели.

**Проверено:** `DraftValidationTest` — **15 тестов** (прослеживаемый черновик готов; **утверждение

### G-003 · Импорт из папки и сетевого каталога — DONE

Реализовано: `FileStability`, `FolderImportService`.

**Файл, дописываемый в момент импорта, не попадает в систему частично.** Полуимпортированный скан хуже
отсутствующего: **он выглядит как документ**, получает хеш, может быть классифицирован и подшит, и
**никто не замечает недостающей страницы**.

Спросить у файла, дописан ли он, невозможно. Наблюдаемо другое — что он **перестал меняться**, и это
делает класс:

| Правило | Почему |
|---|---|
| **Два наблюдения** | Одного взгляда недостаточно: он не отличает законченный файл от того, который вот-вот вырастет |
| **Пауза между ними** | Сканеры и сетевые каталоги сбрасывают данные рывками; файл может не меняться мгновение **посреди записи** |
| **Пустой файл никогда не готов** | Существующий пустой файл — это файл, запись в который ещё не началась; импорт создал бы пустой документ, который человеку потом искать и удалять |
| **Сверка после чтения** | Писатель может замолчать дольше паузы, и файл тогда **выглядит** законченным. Чтение со сравнением снимка до и после ловит этот случай, и импорт **отменяется**, а не делается наполовину |

**Повторный импорт того же содержимого не создаёт второй документ**: решает хеш содержимого, а власть —
уникальный индекс на таблице документов. Происхождение записывается в `document_sources`, поэтому на
вопрос «откуда это взялось» есть ответ.

**Платформа ничего не удаляет и не перемещает.** Она читает папку; решать, что делать с файлом дальше, —
дело того, кто папку настроил, и watcher, перемещающий файлы, — это watcher, чьи сбои их теряют.

1. **Я сравнивал снимок файла сам с собой**, что всегда даёт `READY`, поэтому **второе наблюдение не
   происходило вовсе** и файл, который писали, импортировался. Класс обещал два наблюдения с паузой, а код

2. **два публичных конструктора** оставили Spring без возможности выбрать: контекст не поднимался вовсе,

**G-001** — реестр устройств и защищённый канал.

### G-001 · Реестр устройств и защищённый канал — DONE

Реализовано: `DeviceService`.

Устройства — единственная часть платформы, которая **стоит вне её**, на чьём-то столе или в копировальной,
и достигается она **опросом**: устройство спрашивает работу, к нему ничто не подключается. Спецификация
требует отсутствия открытых портов на устройстве, и это определяет конструкцию — платформа не может
позвонить устройству, поэтому устройство обязано **каждый раз себя называть**.

**Регистрация устройства — не его авторизация.** Только что появившееся устройство имеет статус
`PENDING` и **не получает ничего**, пока человек его не активирует. Сканер, зарегистрировавший себя, —
**всё ещё незнакомая машина в здании**, а задания несут в себе документы.

**Отозванное устройство теряет доступ немедленно.** Не при следующем обновлении токена и не в конце
сессии: ключ проверяется на **каждом** запросе, и отозванное устройство получает отказ на **следующем
же** запросе. Для устройства, которое могло быть украдено, это единственный осмысленный смысл отзыва.

Ещё решения:
- **ключ показывается один раз и хранится только хешем** — платформа, хранящая ключ, выдала бы личность
  устройства из собственной базы;
- **статус спрашивается повторно при выдаче задания**, а не только при аутентификации: устройство могло
  быть отозвано между двумя шагами (это отдельный тест);
- **отзыв освобождает захваченные задания**: работа, назначенная машине, которая больше не может
  работать, — это работа, которая иначе не будет сделана никогда;
- **задание выдаётся один раз**: обновление статуса в том же запросе, что и выбор, поэтому два устройства,
  спросившие одновременно, не получат один документ;
- **задание, у которого истёк срок, не выдаётся**: работа, которая больше не нужна, не должна начинаться.

доступ немедленно**; отзыв освобождает захваченные задания; неизвестный ключ; отсутствующий ключ;
