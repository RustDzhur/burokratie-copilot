# Bürokratie-Copilot — Implementation Plan (микрозадачи)

**Источник требований:** [`docs/task.md`](task.md) (ТЗ v1.0, 2281 строка).
**Назначение файла:** единственный план работ и журнал прогресса. Обновляется после каждой завершённой микрозадачи.

## Как читать этот файл

- `ID` — стабильный идентификатор задачи (`<ЭТАП>-<номер>`). ID не переиспользуется.
- `Статус` — `TODO` | `IN_PROGRESS` | `BLOCKED` | `DONE`.
- `DONE` ставится **только** после успешного прохождения указанных тестов/проверок. Факт проверки фиксируется в разделе «Журнал прогресса».
- `BLOCKED` означает внешнюю зависимость (ключ, подписка, устройство, договор). Всё, что можно реализовать без неё, реализуется; причина блокировки пишется в задаче.

| ADR-05 | Аутентификация: серверные сессии (httpOnly cookie) для web + API-токены (PAT) для интеграций; OIDC-адаптер подключаемый | ТЗ §7.4, §21.3 |
| ADR-06 | Объектное хранилище: интерфейс `BlobStore` с реализациями S3/MinIO (prod) и LocalFs (dev/offline) | ТЗ §2.1, §30 |
| ADR-07 | Event Bus: transactional outbox в PostgreSQL + диспетчер; внешний брокер — подключаемый адаптер | ТЗ §2.1, §16.3 |
| ADR-08 | Frontend: Next.js (App Router) + TypeScript strict + собственная дизайн-система на CSS-переменных (токены) | ТЗ §2.1, §5, §33 |
| ADR-09 | Конфигурируемые бизнес-правила (налоги, сроки хранения, правовые сроки, таксономия) — данные в БД с версионированием, а не константы в коде | ТЗ §1.2, §12.3, §22, §31 |
| ADR-10 | Локализация: `de` (основной, наиболее полный), `en`, `ru`; ICU MessageFormat с pluralization | ТЗ §24 |

## Противоречия, ограничения и внешние зависимости (обязательный раздел по требованию задания)

| № | Пункт ТЗ | Проблема | Принятое решение |
|---|----------|----------|------------------|
| Q-01 | §28.1 Testcontainers | В текущем окружении **нет Docker**, Testcontainers физически не запускается | Интеграционные тесты выполняются против **реального локального PostgreSQL 17** (не H2/in-memory). Конфигурация Testcontainers добавлена как профиль `testcontainers` для окружений с Docker |
| Q-02 | §8.2 Desktop Bridge | TWAIN/WIA требуют Windows SDK и драйверов; SANE требует Linux-устройства. Полная поддержка всех драйверов невозможна | Отдельный модуль `apps/desktop-bridge` с рабочим сценарием (SANE `scanimage` + импорт из папки), конфигурацией, документацией и тестами. TWAIN/WIA — документированный внешний блокер |
| Q-03 | §7.2 M365/Gmail OAuth | Требуются client_id/secret от владельца системы (регистрация приложения в Azure AD / Google Cloud) | Полноценные OAuth-адаптеры + IMAP-адаптер, работающий без внешней регистрации приложения. Статус подключения честно отображается в UI |
| Q-04 | §14.4 Банки | Прямой доступ к PSD2/FinTS требует лицензии/договора с провайдером | Адаптер + офлайн-импорт CAMT.053/MT940/CSV, который работает без провайдера |
| Q-05 | §9.2 OCR | Качество/наличие Tesseract и языковых пакетов зависит от окружения | Адаптер OCR с проверкой доступности движка и честным статусом `OCR_UNAVAILABLE`, не фальсифицируем результат |
| Q-06 | §10.5 pgvector | Расширение `pgvector` может отсутствовать в целевом PostgreSQL | Миграция создаёт расширение при наличии; при отсутствии — деградация до FTS с явным флагом, семантический поиск помечается как недоступный |
| Q-07 | §6.1 MSG/архивы | Парсер MSG и безопасная распаковка архивов — отдельные внешние зависимости | MSG помечается `UNSUPPORTED` с понятным сообщением, пока не подключён парсер; архивы — безопасный процесс с лимитами |
| Q-08 | §12.3, §14.2, §22 | Юридические сроки, налоговые ставки, сроки хранения **не определены** в ТЗ | Не выдумываются. Реализуется конфигурируемый версионируемый реестр правил со статусом `REQUIRES_VERIFICATION` и обязательным подтверждением специалистом |
| Q-09 | §17.4 Public Sector | Правовые ограничения на автоматические решения | Реализуется как архитектурная конфигурация без автоматических юридически значимых решений |
| Q-10 | §34 «E2E-тесты проходят» | Без Docker полный контейнерный E2E невозможен | E2E-прогон выполняется против локально запущенных api+web+PostgreSQL; результаты фиксируются в отчёте тестирования |

## Легенда этапов

- **Этап A** — фундамент (репозиторий, PostgreSQL, безопасность, ядро, дизайн-система).
- **Этап B** — документы (приём, OCR, извлечение, классификация, проверка, поиск).
- **Этап C** — дела, задачи, сроки, уведомления.
- **Этап D** — договоры, финансы, E-Rechnung, банк, отчёты.
- **Этап E** — коммуникации, шаблоны, AI-слой, RAG.
- **Этап F** — workflow engine и автоматизации.
- **Этап G** — устройства, сканеры, интеграции.
- **Этап H** — специализированные режимы.
- **Этап I** — проверка, hardening, выпуск.

### A-010 · Event Bus: transactional outbox + диспетчер
- **Результат:** запись доменных событий в `outbox_events` в одной транзакции с бизнес-изменением; диспетчер с at-least-once, ретраями и идемпотентностью потребителей.
- **Зависимости:** A-004
- **Действия:** `DomainEvent`/`OutboxWriter`/`OutboxDispatcher`; блокировка `FOR UPDATE SKIP LOCKED`; dead-letter.
- **Приёмка:** событие не теряется при откате транзакции; повторная доставка не дублирует эффект.
- **Тесты:** `OutboxAtomicityIT`, `OutboxRedeliveryIT`.
- **Статус:** DONE

### Дефекты, найденные и исправленные в этой сессии

1. jsonb-литералы из `VALUES`-подзапросов требовали явного приведения типа (V12).
2. RLS-политика падала на `''::uuid` — PostgreSQL не гарантирует short-circuit; введена функция `current_tenant_id()`.
3. 30 таблиц не имели tenant-индекса — миграция `V15`.
4. `inet`-колонки нельзя мапить как `String` — используется `@JdbcTypeCode(SqlTypes.INET)`.
5. `DefaultEmailSender` с самоссылающимся `@ConditionalOnMissingBean` не регистрировался.
6. **Фильтр сессий нельзя делать `@Component`**: Spring Boot регистрирует `Filter`-бин ещё и в сервлет-цепочке, и `OncePerRequestFilter` пропускает второе выполнение — авторизация молча не работала.
7. **Фильтр должен идти ПОСЛЕ `SecurityContextHolderFilter`**, иначе контекст безопасности перезаписывается пустым.
8. **Проверка пароля и учёт неудачных попыток должны быть в разных транзакциях**: исключение откатывало счётчик блокировки.
9. **V14 падала на чистой БД при установленном pgvector**: колонка `vector` без размерности + HNSW-индекс → ошибка и откат всей миграции. Индекс теперь не создаётся до выбора модели, размерность не выдумывается.
10. **`GET /api/v1/auth/csrf` не отдавал cookie** (204 без `Set-Cookie`) → SPA не могла выполнить ни одного изменяющего запроса. Токен теперь выпускается явно через `CsrfTokenRepository`.
11. **Профиль `worker` не стартовал**: `SecurityConfiguration` требовала `HttpSecurity`, а `PasswordEncoder` и `CsrfTokenRepository` жили в web-зависимой конфигурации. Разделено на `PasswordEncoderConfiguration`, web-условную `SecurityConfiguration` и web-условный `AuthController`.
12. `apps/web/next.config.ts` не содержал `output: "standalone"`, который требует контейнер web.

- **доставка**: событие доходит до потребителя, статус становится `PUBLISHED`;
- **ровно один эффект**: повторная доставка того же события не вызывает потребителя второй раз

- **ретраи и dead letter**: временный сбой приводит к `FAILED` с экспоненциальной задержкой и
  последующим успехом; постоянный — к `DEAD_LETTER` после исчерпания бюджета попыток;
- **событие без потребителя** парковкой в `DEAD_LETTER`, а не бесконечными ретраями;
- **tenant-контекст**: потребитель выполняется внутри tenant события (проверено захватом
  `RequestContext`), то есть фоновые задания подчиняются тем же RLS-политикам, что и запросы;
- **захват батча** через `FOR UPDATE SKIP LOCKED` — несколько worker-инстансов работают параллельно;
- **восстановление после сбоя**: зависшие блокировки старше 10 минут освобождаются планировщиком.

Побочный эффект: у профиля `worker` появился реальный цикл работы. Раньше он стартовал и сразу
завершался, потому что нечего было выполнять.

### A-011 · Идемпотентность небезопасных операций — DONE

Реализовано: `IdempotencyFilter` (заголовок `Idempotency-Key`), `IdempotencyService`,
`IdempotencyRecord`, `CachedBodyRequest`.

Поведение и что именно проверено (`IdempotencyIT` — **5 тестов, зелёные**):
- повтор с тем же ключом и тем же телом **не выполняет операцию второй раз** и возвращает
  сохранённый ответ (проверяется счётчик фактических вызовов эндпоинта, а не только HTTP-статус);
- тот же ключ с другим телом → **409**, а не воспроизведение чужого результата;
- без заголовка каждый запрос выполняется — идемпотентность включается осознанно;
- **неудачная попытка освобождает ключ**, поэтому клиент может исправить ввод и повторить;
- некорректный ключ → 400 с понятным сообщением.

Ключевые решения:
- захват ключа — атомарный `INSERT ... ON CONFLICT DO NOTHING` по уникальному индексу
  `(tenant_id, idempotency_key)`, поэтому двойной клик физически не может создать два объекта;
- каждый шаг (claim/complete/release) — в **отдельной транзакции**: иначе откат бизнес-транзакции
  либо навсегда блокировал бы ключ, либо допускал дубликат при повторе;
- «зависший» захват старше 2 минут перехватывается, чтобы умерший запрос не блокировал клиента;
- область действия осознанно ограничена: аутентифицированные запросы с небольшим (до 1 МиБ)
  не-multipart телом. Буферизовать 100 МиБ загрузку ради отпечатка нарушило бы требование
  потоковой обработки §27, а дубликаты документов решаются хешем содержимого (задача B-004).

### Дополнительно исправлено: миграция V16

`ddl-auto: validate` выявил реальное расхождение: колонки с фиксированной длиной `character(n)`
(например `idempotency_records.request_hash`) против `varchar` в сущностях. PostgreSQL дополняет
`char(n)` пробелами, что даёт скрытые различия при сравнении строк. Миграция `V16` переводит все
такие колонки в `varchar(n)`; CHECK-ограничения на формат хешей, кодов стран и валют сохраняются.

   автоматически (`MigrationTestDatabase`).
3. Фиксированный e-mail в `AuditServiceIT` конфликтовал с предыдущим запуском на переиспользуемой
   базе — заменён на уникальный.

### B-003 · Безопасность загружаемых файлов — DONE

Реализовано: `FileSecurityScanner`, `FileScanResult`; проверка встроена в приём документа
(`DocumentService.receive`) до создания документа; диагностика сохраняется в
`document_blobs.scan_details`.

Что проверяется:
- **формат по содержимому, а не по заявлению**: тип определяется по magic bytes и сравнивается с
  заявленным; PDF, переименованный в картинку, или скрипт, переименованный в PDF, отклоняются;
- **исполняемое содержимое запрещено**: PE, ELF, Mach-O, Java class и скрипты с shebang отклоняются
  безусловно;
- **архивы**: разбирается центральный каталог ZIP — число записей, суммарный распакованный размер и
  коэффициент сжатия; бомба (200 МиБ из ~200 КиБ) помечается `SUSPICIOUS` и уходит на ручную проверку;
- **правдоподобие контейнера**: архив, названный .docx, обязан содержать части Word-документа,
  иначе отклоняется;
- **непроверяемое не выдаётся за проверенное**: без антивируса состояние блоба записывается как
  `SKIPPED` («не проверено на malware»), а структурный вердикт хранится отдельно;
- отклонённый файл удаляется из объектного хранилища, событие фиксируется в аудите.

Проверено: `FileSecurityScannerTest` — **12 тестов**, `DocumentUploadIT` — **6 тестов**
(включая отказ скрипту с именем .pdf и пустой Inbox после отказа).
Полный прогон: `./mvnw -B verify` → **BUILD SUCCESS**, тестов **70** (28 unit + 42 integration).

**Антивирус — реализован и проверен на реальном ClamAV.**

`MalwareScanner` — интерфейс с реализациями `ClamAvCliMalwareScanner` (ClamAV CLI) и
`NoOpMalwareScanner` (когда движок не настроен). Выбор через
`burokratie.security.malware-scanner.type = none | clamav-cli`.

Правила честности, зашитые в код:
- без движка файл помечается `NOT_CHECKED` → в БД `SKIPPED`, **никогда** `CLEAN`;
- если движок настроен, но не запускается, приложение **не стартует** с понятной ошибкой —
  нерабочий антивирус не должен превращаться в молчаливые отказы при загрузке;
- если проверка не удалась (таймаут, ошибка), состояние `FAILED`, файл остаётся в карантине;
- обнаруженный malware: файл удаляется из хранилища, документ не создаётся, в аудит пишется
  событие уровня `CRITICAL` с названием сигнатуры;
- в `document_blobs.scan_details` сохраняются оба вердикта (структурный и антивирусный) и имя движка.

Проверено `ClamAvCliMalwareScannerTest` — **5 тестов на настоящем ClamAV 1.5.4** (установлен через
Homebrew, база `daily.cvd` загружена): обнаружение тестовой сигнатуры EICAR, чистый PDF как `CLEAN`,
недоступный движок как `FAILED`, разбор строки вывода, удаление временного файла после проверки.
Тесты пропускаются там, где ClamAV не установлен, — платформа обязана работать и без него.

**Что осталось за рамками B-003:** рекурсивная проверка вложений внутри архивов и изоляция
парсеров в отдельном процессе.

### B-005 · Конвейер обработки и его состояния — DONE

Реализовано: `DocumentProcessingStep` (+ репозиторий), `ProcessingStepHandler`,
`DocumentProcessingPipeline`, `FormatDetectStepHandler`.

Ключевые свойства (проверено `DocumentPipelineIT` — **4 теста**):
- **каждый шаг записывается**: попытка, длительность, диагностика, ошибка. Ответ на «почему документ
  завис» — это запрос, а не расследование;
- **отсутствующий обработчик не имитируется**: если для следующего шага нет реализации, конвейер
  останавливается и сообщает, на каком шаге и почему. Шаг остаётся `PENDING` («ждёт реализации»), а
  не `SUCCEEDED` — необработанный документ не выглядит обработанным;
- **идемпотентность**: повторный запуск ничего не меняет, завершённый шаг не выполняется второй раз
  (проверяется счётчиком попыток) — это то, что делает вызов из фонового worker безопасным после
  перезапуска;
- **повтор только для упавшего шага**: `retryStep` отказывает, если шаг не в состоянии `FAILED`, —
  перезапуск не может переиграть уже успешные этапы;
- **загрузка документа сама записывает три шага**, которые реально выполнила (`SECURITY_SCAN`,
  `HASH`, `DUPLICATE_CHECK`), поэтому история конвейера начинается с правды, а не с пробела.

Обработчик `FORMAT_DETECT` — настоящий: он сверяет записанный при проверке безопасности тип
содержимого с метаданными, убеждается, что блоб допущен к обработке, и фиксирует, какой парсер
понадобится на следующем этапе (`pdfbox`, `poi-docx`, `ocr-required`, …). Документ переходит
`RECEIVED → QUARANTINED` — единственный разрешённый переход в этой точке.

**Что ещё не реализовано и потому честно помечается как ожидающее:** `TEXT_EXTRACT` (B-006),
`OCR` (B-007), `LANGUAGE_DETECT`/`CLASSIFY` (B-008), `FIELD_EXTRACT` (B-009), `MATCHING` (B-010).

### Почему CI падал за 0 секунд (найдено и исправлено)

Каждый пуш создавал run, падавший за 0 с без единого job'а с сообщением

1. **`hashFiles()` в `jobs.<job_id>.if`** (job `frontend`). Функция доступна только в `if`/`with`

   есть, и фронтенд-гейты обязаны выполняться, а не молча пропускаться.
2. **Контекст `env` в `jobs.<job_id>.services.<id>.image`** (`postgres:${{ env.POSTGRES_VERSION }}`).
   Там допустимы `github`, `inputs`, `needs`, `strategy`, `matrix`, `vars`. Тег выписан литералом
   с комментарием, почему переменную здесь использовать нельзя.

Оба случая — одна и та же ошибка проектирования: контекст использован там, где GitHub его не
предоставляет, и валидатор PyYAML её не видит. Поэтому локальная проверка YAML не заменяет прогон CI.
