## 0. Вердикт

**Проект на 80–90% готов как набор модулей и пока не готов как работающий продукт для человека у экрана.**

Бэкенд и фронтенд по отдельности собираются и проходят свои тесты. Но **они не говорят на одном
протоколе**: войти из браузера, судя по коду, нельзя, а 45 из 72 вызовов интерфейса не имеют маршрута на
сервере. Ни один тест этого не ловит, потому что сквозных тестов нет (`tests/e2e/` пуст). ТЗ §34 прямо
говорит: *«Проект не считается готовым только потому, что страницы отображаются»* и требует *«Регистрация и
авторизация работают»*, *«Нет критических неработающих кнопок»*, *«Сквозные тесты проходят»* — **эти три
пункта не выполнены.**

Главная причина — **неверная метрика готовности**. Проект измерял «сервис упомянут в контроллере» (осталось
3) и «тест зелёный». Он не измерял «вызов, который делает экран, попадает в существующий маршрут». Поэтому
в `docs/implementation-plan.md` написано «осталось три эндпоинта», а фактически не хватает порядка **30
эндпоинтов и ~16 переименований/адаптаций**.

## 1. Находки по серьёзности

### CRITICAL — продукт нельзя использовать

**C1. Контракт UI ↔ API разорван: 45 из 72 вызовов интерфейса без маршрута на сервере.**
Сопоставлены `apps/web/src/lib/api/resources.ts` и все `@*Mapping` в 40 контроллерах (скрипт, регулярные
выражения; уверенность 0,95, единичные ложные срабатывания возможны — точный счёт даст контрактный тест из
шага 2 плана).
- Совпадают только 27 вызовов. Остальные — либо **другое имя** (`/auth/session` ↔ `/auth/me`, `/audit` ↔
  `/audit/events`, `/users` ↔ `/members`, `/document-processing/review` ↔ `/reviews`, `/integrations/{id}/disconnect`
  ↔ `/disable`, `PATCH /tasks/{id}` ↔ `POST /tasks/{id}/status`, `PUT /notifications/preferences` ↔ `POST`),
  либо **эндпоинта нет вообще**: `/contacts`, `/calendar/events`, `/dashboard/summary`, `/settings/security`,
  `/settings/accessibility`, `/documents/archive`, `GET /invoices`, `GET /payments`, `GET /mail`,
  `GET/PUT /templates/{id}`, `/ai/assistant/query`, экспорты, `read-all`, `reprocess`, `history`.
- **Формы не совпадают даже на первом пути пользователя.** Регистрация: фронтенд шлёт `fullName`, бэкенд
  ждёт `displayName`. Подтверждение почты: фронтенд `{email, code}`, бэкенд `{token}`
  (`AuthController.java:73`). Вход: бэкенд отвечает `{userId, tenantId, displayName, locale, timeZone, roles}`
  (`AuthController.java:79`), фронтенд ждёт `SessionUser {id, name, email, workspaceId, workspaceName,
  workspaceType…}` (`types.ts:329`).

**C2. Браузер, судя по коду, не может выполнить ни одного изменяющего запроса, включая вход (CSRF).**
Бэкенд включает CSRF с двойной отправкой: cookie `XSRF-TOKEN` → заголовок `X-XSRF-TOKEN`; `/auth/login`
в исключения не входит (`SecurityConfiguration.java:102-109`, документировано в `:39-41`). В `apps/web/src`
слов `csrf`/`xsrf` **нет вообще**, и `/auth/csrf` никто не вызывает. Итог: `POST /auth/login` получает 403.
Уверенность 0,9 (вывод из кода; в браузере не воспроизводился — это и есть пропуск, который закрыл бы e2e).

**C3. Адрес API в документации, Docker и CI противоречит клиенту.**
Клиент склеивает `NEXT_PUBLIC_API_BASE_URL + '/auth/login'` и по умолчанию использует `/api/v1`
(`client.ts:157`, `apps/web/.env.example:4`). Но `README.md:113`, `docs/runbook.md:70`, `infra/.env.example:227`,
`infra/docker/web.Dockerfile:36`, `.github/workflows/ci.yml:276,667` задают `http://localhost:8080` **без**
`/api/v1`. В собранном по этим инструкциям образе все запросы уйдут на `http://localhost:8080/auth/login` →
404 (сервер отдаёт `/api/v1/auth/login`), к тому же это другой origin при `SameSite=Strict` и CORS на единственный
`public-base-url`. Уверенность 0,9.

### HIGH

**H1. В продакшн-образе нет ни OCR, ни антивируса, а умолчания молча их выключают.**
`api.Dockerfile:108-111` ставит только `curl` и `dumb-init`; в `infra/` нет ни `tesseract`, ни `clamav`.
`application.yml:136` → `malware-scanner: none`, `:161` → `ocr.enabled: false`. `ProductionConfigurationGuard`
проверяет ключ шифрования, cookie, ИИ и S3 (`:45-84`) — **но не сканер и не OCR**. Следствие: в проде файлы
**не проверяются до обработки**, а сканы/изображения не распознаются — нарушены §34 «Файлы проверяются до
обработки» и «OCR … работают через настроенный движок». Плюс `infra/.env.example` не содержит 4 переменных
сканера (`BC_MALWARE_SCANNER`, `BC_CLAMAV_PATH`, `BC_MALWARE_SCAN_SPOOL`, `BC_MALWARE_SCAN_TIMEOUT`).
Уверенность 0,85.

**H2. Сквозных тестов нет.** `tests/e2e/` пуст (`check-structure.sh` сам печатает PENDING). Фронтенд-тесты
подменяют сеть, бэкенд-тесты ходят через MockMvc. Поэтому C1–C3 при «зелёном CI на каждом коммите» остались
незамеченными. §34 «Сквозные тесты проходят» — не выполнено. Уверенность 0,9.

**H3. Бэкенд-функции без HTTP-поверхности.** `AssistantService`, `RagService`, `GeneratedDocumentExportService`
(ассистент и RAG — ядро §10, на которое опирается экран «Ассистент»); нет контроллера для контактов, событий
календаря, сводки дашборда, настроек безопасности/доступности. Это та часть C1, которую проект считал
закрытой.

## 2. Диагноз архитектуры

Единый корень: **граница между фронтендом и бэкендом никем не владеет и ничем не проверяется.**

```
 UI (resources.ts) ──x── нет общего контракта ──x── Controllers (@*Mapping)
        │                                                  │
   тесты с подменой fetch                       MockMvc + csrf() в тестах
        └─────────── оба зелёные, сшивка не проверена ─────┘
```

- Контракт описан дважды вручную (TypeScript-типы и Java-records) и разошёлся.
- Единственный механизм, который мог это поймать (e2e/контрактный тест), не построен.
- Метрики готовности (число тестов, число микрозадач DONE, «сервисов без контроллера») измеряют
  внутреннюю полноту, а не достижимость.
- Вторичный слой: документы превратились в журнал самооправданий; цифры в них пишутся по памяти и
  расходятся (M1). Это тот же класс ошибки, который сам проект называет «помнил, а не смотрел».

## 3. План доведения (по порядку: сначала код, потом документы)

### Шаг 0 — Среда (≈ полдня, делать первым)
1. **Вынести репозиторий из iCloud** (например `~/dev/burokratie-copilot`) или исключить `node_modules`,
   `.next`, `target` (`.nosync`). Без этого любая проверка ниже непредсказуемо зависает.
2. **Закрепить JDK 21**: `.sdkmanrc`/`.tool-versions` + `maven-enforcer-plugin` (`requireJavaVersion [21,22)`),
   либо поднять JaCoCo до версии с поддержкой используемого JDK.
3. **Решить судьбу `button.tsx` + `button-class.ts`** (коммит парой или откат обоих) — не оставлять половину.
4. Удалить влитые `wip/*` ветки (локально и на origin).

### Шаг 1 — Один сквозной срез: «зарегистрироваться → войти → увидеть дашборд» (S–M)
Цель — сначала заставить работать **вход**, потому что без него остальное недостижимо.
1. **Единый адрес API:** `NEXT_PUBLIC_API_BASE_URL=/api/v1` в `README`, `runbook`, `infra/.env.example`,
   `web.Dockerfile`, `ci.yml` (оба места). В dev — `rewrites` в `next.config.ts` на `http://localhost:8080`,
   чтобы origin был один (cookie, CSRF, CORS).
2. **CSRF в клиенте:** перед первым небезопасным запросом вызвать `GET /auth/csrf`, читать cookie `XSRF-TOKEN`,
   слать `X-XSRF-TOKEN` на POST/PUT/PATCH/DELETE (`client.ts`). Тест на клиенте.
3. **Выровнять auth-DTO:** `displayName/tenantName/accountType`, `verify-email {token}`, вход → затем
   `GET /auth/me` (+ `GET /account`) и сборка `SessionUser` в адаптере. Валидация пароля ≥12, экран
   «новый пароль по токену» (`/auth/password-reset/confirm`).
4. **Первый Playwright-тест на реальном стеке** (compose: postgres + api + web): регистрация → вход →
   дашборд. Он должен падать на текущем `main` — это и есть доказательство, что он что-то проверяет.

### Шаг 2 — Контракт как источник истины (M)
1. Включить экспорт OpenAPI (`/api-docs` уже есть через springdoc) и **контрактный тест в CI**: каждая пара
   метод+путь из `resources.ts` обязана существовать в OpenAPI, а типы ответов — совпадать. Заготовка —
   скрипт сопоставления из этого аудита. Лучше — генерировать TS-типы из OpenAPI.
2. **Принять решение по каждому из 45 вызовов** (таблица ниже) и править сторону, где дешевле.
3. Привести пагинацию к одному виду (`totalElements` → `totalItems`, либо `PageSerializationMode.VIA_DTO`).
