## 3. Распознавание текста — подробный аудит

### 3.1. Что работает

- **Детект формата по magic bytes** и allow-list (`FileSecurityScanner.ALLOWED_TYPES`); расхождение
  заявленного типа и реального — `422 FILE_REJECTED`, blob удаляется.
- **Экстракторы:** PDF (PDFBox 3.0.5, `PDFTextStripper`, **постранично**), DOCX (POI XWPF, абзацы и
  таблицы), XLSX/XLS (лист = секция, `Locale.GERMANY`), TXT/CSV (BOM, UTF-8, CP1252), XML (без DTD/XXE),
  EML (заголовки, text/plain, HTML-strip), изображения → страница под OCR.
- **Пайплайн:** `TEXT_EXTRACT` → если `needsOcr()` → `OCR_PENDING`, иначе `EXTRACTING`; OCR — Tesseract CLI,
  рендер 300 dpi, поворот 90/180/270, языковой fallback.
- **Атомарность:** сбой извлечения не сохраняет частичный результат — страницы версии заменяются
  атомарно (`TextExtractionService.java:93-122`).
- **Постраничное хранение** с `ocr_used`, `ocr_engine`, `ocr_language`, `ocr_confidence`, `error_message`.
- **Честная маршрутизация:** нет движка → `SKIPPED` + `REVIEW_REQUIRED`; OCR ничего не нашёл →
  `REVIEW_REQUIRED`; все страницы упали → `FAILED`; пустой текст не классифицируется по имени файла.
- **Confidence OCR** считается из TSV Tesseract (среднее по словам с `conf >= 0`).

### 3.2. Что не работает или отсутствует

- **OCR по умолчанию выключен** (`BC_OCR_ENABLED: false`); в Docker включён, но в конфигурации по
  умолчанию — нет.
- **`ocr_confidence` и `error_message` не доходят до API и UI.** `/documents/{id}/pages` отдаёт только
  `ocrUsed/engine/language/empty`; UI этот эндпоинт вообще не вызывает. `pageCount` отсутствует в
  `DocumentResponse` → в интерфейсе «страницы: unknown».
- **`text_blocks` (координаты блоков) в схеме есть, но не пишется** — блоки Tesseract выбрасываются.
- **Уверенность OCR ни на что не влияет**: `FieldExtractionService` ставит `0.75`/`0.90` константой.
- **OCR-текст склеивается без переносов строк**, а `findAfterLabel` ищет конец строки → для
  `REFERENCE`/`TEXT` значением становится весь остаток страницы, для `AMOUNT`/`DATE` — часто не то число.
- **Битый PDF**: `IOException` → `IllegalStateException` → шаг `FAILED`, документ остаётся в прежнем
  статусе (обычно `QUARANTINED`) — **вечное зависание без внятной причины**.
- **Паролезащищённые PDF не поддержаны** — пароль не запрашивается.
- **Нет OCR для PDF с мусорным текстовым слоем**: `needsOcr` = **все** страницы пусты. Одна «пустая»
  страница с глифами считается успешным текстовым слоем.
- **Пустые DOCX/XLSX/XML уходят в OCR** и рендерятся как PDF → `Loader.loadPDF` на DOCX → `FAILED`.
- **Multi-page TIFF читается как одна страница** — остальные кадры теряются.
- **`.doc`, `.rtf`, HTML не поддержаны**; `webp/bmp/gif` есть в экстракторе, но не в allow-list.
- **Таймаут Tesseract не работает** (`readAllBytes()` до `waitFor(timeout)`); до 5 проходов на страницу,
  **OCR выполняется внутри транзакции БД и потока outbox**.
- **Страницы читаются по `document_id`, а не по `version_id`** — при версии 2+ смешение страниц.
- **Частичный сбой OCR не эскалируется**: 1 страница ок, 1 упала, 1 пустая → шаг `SUCCEEDED`, review нет,
  `error_message` не виден.

### 3.3. Где система может «соврать»

Это самое важное для доверия к продукту:

1. `OcrStepHandler.java:71-75` — если экстрактор вернул **0 страниц**, шаг помечается `SUCCEEDED` с
   причиной *«Every page carries a text layer»*. Текста нет вообще, а система сообщает об успехе.
2. `OcrStepHandler.java:161-171` — **частичный сбой** OCR (1 ок, 1 упала, 1 пустая) → `SUCCEEDED`, review
   нет, `error_message` страницы не виден в API.
3. `TextExtractionService.java:114-127` — **молчаливое обрезание** текста на 5 000 000 символов.
4. `OcrStepHandler.java:107` vs `124-126` — diagnostics пишет **запрошенные** языки, страница —
   **фактический**; при отсутствии `deu` молча падает на `eng`.
5. `FieldExtractionService.java:198-200` — OCR-значение получает `0.75`/`0.90`; **уверенность OCR ни на
   что не влияет**.
6. `ClassificationService.java:200-215` — имя файла **добавляется к тексту**; защита «не классифицировать
   по имени» работает только при полностью пустом тексте. Одного символа достаточно, чтобы правило по
   имени файла сработало.
7. `ImageTextExtractor.java:35` — картинке ставится метод `TEXT_LAYER`, хотя текста нет.
8. `OcrStepHandler.java:124-126` — `ocr_used = true` ставится и **упавшей** странице: в API это выглядит как
   «прочитано».

### 3.4. Тесты распознавания

**Покрыто:** `TextExtractorTest` (10 тестов, реальные сгенерированные PDF/DOCX/XLSX/EML/XML, постраничность,
кодировки, XXE), `TesseractOcrEngineTest` (7), `PhotoOcrIT` (4, сквозной upload→pipeline, только при
установленном Tesseract), `DocumentPipelineIT` (5), `TextExtractionControllerIT` (7),
`FileSecurityScannerTest` (allow-list, подмена типа, zip-bomb).

**Не покрыто:** `OcrStepHandler` (частичный сбой, пустой результат, 0 страниц), `TextExtractionService`
(unsupported, запись, truncation), паролезащищённые и битые PDF, пустые файлы, multi-page TIFF, confidence
в API/UI, версии 2+, порядок страниц, **реальные сканы, фото и почерк**. В `src/test/resources` **нет ни
одного бинарного файла** — все фикстуры генерируются. Eval-наборы (37 + 21) — только `.txt`, качество
PDF/OCR **не измеряется**.

### 3.5. Вывод по распознаванию

**Цифровые PDF, DOCX, XLSX, TXT и EML — рабочий, аккуратно спроектированный слой.** OCR-ветка
функциональна, **но доверять её результатам без правок нельзя.**

**Критично исправить (в порядке приоритета):**
1. **Сохранять переносы строк** в OCR-тексте (брать `par`/`line` из TSV) и пересмотреть `findAfterLabel`.
2. **Связать `ocr_confidence` с полями и review**; отдавать `ocrConfidence`/`errorMessage`/`ocrUsed` в API
   и UI.
3. **Не отправлять DOCX/XLSX/XML/EML в `PdfPageRenderer`**; для пустых и 0-страничных документов — отдельный
   статус, а не «Every page carries a text layer».
4. **Паролезащищённые и битые PDF** — явная ошибка/review вместо вечного `QUARANTINED`; тесты.
5. **Multi-page TIFF** — все кадры или явный отказ.
6. **Частичный сбой OCR → review**; страницы читать по `version_id`.
7. **Таймаут и процесс Tesseract**, лимит страниц и времени, **OCR вне долгой транзакции и outbox**.

## 6. Распределение по разделам (классификация) — аудит

### 6.1. Что работает

- **`document_types` — справочник из 189 типов в 9 категориях**; засеяны миграциями V12, V37, V40, V64;
  **49 типов требуют проверки человеком** (`requires_review`).
- **718 активных системных правил** на 186 типов: `KEYWORD`, `REGEX`, `SENDER_DOMAIN`, `FILENAME`.
  Тенантские правила добавляются через `TaxonomyAdminService` (право `taxonomy.manage`).
- Работают: `RuleBasedClassifier`, `ClassificationService`, `ClassifyStepHandler`, `DocumentResortService`,
  `MatchingService`, `ReviewService`.
- **Ручной выбор защищён:** `DocumentResortService.setByPerson` считает выбор человека (`keptByPerson`) и
  **не перезаписывает** его при пересортировке.
- **При отсутствии правил или текста тип не выдумывается** — документ уходит в `REVIEW_REQUIRED`.

### 6.2. Как принимается решение

1. Ранний review при `language = "ru"` или пустом тексте.
2. Вход классификатора: извлечённый текст **+ имя файла + отправитель + e-mail**. Умлауты и `ß`
   нормализуются.
3. `KEYWORD` — подстрока; `REGEX` — первые 200 000 символов; `SENDER_DOMAIN` — домен; совпадение в первых
   600 символах даёт +25 % к весу.
4. Счёт типа — `1 − Π(1 − w)`; победитель + альтернатива.
5. **Проверка человеком**, если тип помечен `requires_review`, **или уверенность < 0.85**, **или** совпало
   меньше двух правил, **или** «близкий вызов» (второй тип ≥ 0.5, разрыв < 0.08 и **другая категория**).
6. При review тип в документе **не ставится**, но запись классификации сохраняется.

### 6.3. Что не работает

- **AI-классификации нет** — единственная реализация `DocumentClassifier` это `RuleBasedClassifier`
  (`method = "RULE"`).
- **Настройка `review_threshold` (0.60) — мёртвый код**: читается в переменную и **нигде не используется**.
  Трёхзонное решение фактически двухзонное, а эндпоинт `/documents/classification/review-threshold`
  рекламирует неработающую настройку.
- **Иерархии типов нет**: `parent_id` есть, но не заполнен.
- **3 типа без правил** (`familienkommunikation`, `unbekannt`, `eigentumsunterlagen`), **7 без сценариев**.
- **Тенантские правила не переопределяют системные**: используется сумма обоих, системное правило нельзя
  отключить на арендатора.
- **Дефект в `TaxonomyAdminService.addRule`**: пишет `String.valueOf(requiresAll)` (`"true"`/`"false"`) в
  `jsonb`, где ожидается `List<String>` — **1 119 таких строк** в тестовой БД; путь не тестируется.
- **`BUSINESS`-тип через API не создать** — `TaxonomyAdminService.CATEGORIES` не содержит эту категорию.
- **Ручная правка неотличима от правила**: `correctManually` обещает метод `MANUAL`, а записывается
  `RULE`.
- **`documents.classification_confidence` не заполняется нигде** — колонка-метрика мертва.
- **Обратной связи нет**: исправления человека **не меняют веса и правила**; калибровки нет.
- **Matching**: счёт (`INVOICE`) **не сопоставляется** — тип есть в enum, но `MatchingService` его не
  строит; предложения ниже 0.60 отбрасываются **молча**; review «не удалось сопоставить» нет.

### 6.4. Где может ошибиться молча

1. **«Близкий вызов» игнорирует типы одной категории.** `Rechnung`, `Mahnung`, `Zahlungserinnerung`,
   `Inkasso` — все `FINANCE`. Письмо с «Rechnungsnummer», «Rechnungsbetrag», «Zahlbar bis» может дать
   **~0.99 `rechnung`** и **~0.90 `mahnung`**; разрыв > 0.08, обе в FINANCE → **автопринятие `rechnung` без
   проверки**. Инцидент уже был зафиксирован (V35: договор с «Kündigungsfrist» → `kuendigung` с 98 %);
   исправлены только веса, **механизм остался**.
2. **`KEYWORD` — подстрока без границ слова**: «angebot» ловится в «Leistungsangebot».
3. **Имя файла входит в текст классификации**, а в eval-наборах имена часто содержат ответ (`Rechnung_…`,
   `Mahnung_…`) — это **завышает измеренную точность**.
4. **«Уверенность» — не вероятность**: веса расставлены вручную, коррелирующие правила считаются
   независимыми, системные и тенантские дубли усиливают друг друга. **8 365 классификаций ≥ 0.85**, и UI
   показывает 85 % как «высокую уверенность».
5. **Проверка языка только `ru`**; **25 091 документ с `language IS NULL`** — английский и другой текст не
   блокируется.
6. **Тай-брейк недетерминирован**: `findEffectiveRules` без `ORDER BY`; при равном счёте и одной
   категории выбирается **произвольный тип без review**.
7. **Тип, переданный при загрузке, не помечается выбором человека** и может быть снят пересортировкой.

### 6.5. Тесты и измеренное качество

**Покрыто:** `RuleBasedClassifierTest` (unit, `combine`/веса/`fold`), `ClassificationIT` (реальный pipeline
на синтетических PDF), `FilenameOnlyClassificationIT`, `DocumentResortIT`, `DocumentTypeChangeIT`,
`ReviewCentreIT`, `TaxonomyAdminServiceIT`, `EvaluationHarnessIT`.

**Не покрыто:** `closeCall`, `singleFeature`, реальные пороги, `requires_all`, `BUSINESS`, не-русские языки,
**реальные сканы**.

**Измеренное качество (`docs/testing/test-strategy.md`):** 37 dev + 21 holdout + 24 owner-кейса, **58
документов**, синтетика. До настройки — 78.8 % верных типов и **22.2 % неверных среди автоматически
принятых**; после настройки dev — 100 %, holdout — 94.7 %, 0 неверных автоматических. **Честная оценка —
89.5 % на holdout до настройки**, а dev-набор подбирался под систему.

### 6.6. Вывод по классификации

**Архитектура честная:** без правил тип не выдумывается, review с причиной, выбор человека защищён,
сопоставление показывает основания. **Но для автономной раскладки система не готова.**

**Критично:**
1. Реализовать `review_threshold` и трёхзонность **или убрать настройку**.
2. **Не автопринимать типы внутри одной категории**, если от типа зависит сценарий или задача.
3. **Проверить на реальных немецких документах**, а не на 58 синтетических.
4. Починить `requires_all`, `BUSINESS`, переопределение системных правил и метку `MANUAL`.
5. Убрать имя файла, язык и некалиброванную уверенность как источники завышенной уверенности.

**До этого `0.85` — не «уверенность», а эвристика; безопаснее режим «сначала проверка».**

## 7. Цепочка «документ → срок → задача → уведомление» — аудит

### 7.1. Что работает

- Пайплайн выполняет 10 шагов и публикует `document.processing_completed`; `DocumentProcessedHandler`
  вызывает `CaseOrchestrator.orchestrate()`.
- **`CaseOrchestrator` создаёт задачу, чек-лист и срок из `document_extractions`** по сценарию типа
  документа (`document_type_scenarios`: `creates_task`, `task_title`, `lead_days`, `legal_deadline`).
  Связь документ→задача: `tasks.source_document_id` + `case_documents`.
- `DeadlineCalculator`: DAYS/WEEKS с рабочими днями пропускают выходные и праздники.
- **Внутрисистемные уведомления работают**: `notifications` + `notification_deliveries`, `IN_APP` всегда
  `SENT`.
- `OrchestrationWatchdog` (`@Scheduled`, 60 с) напоминает по `tasks.remind_at`, сообщает о просрочке
  (`tasks.due_at`) и о нераспределённых задачах.
- Задача без исполнителя остаётся `assignment_pending` и через сутки попадает в очередь распределения.
- **ICS-фид даёт напоминание за 3 дня** для `DEADLINE` (`-P2DT15H`) и за 15/8 часов для
  `REMINDER`/`APPOINTMENT`.

### 7.2. Где обрыв

**1. Юридические сроки не считаются автоматически.** Реестр `deadline_rules` **пуст** (`DeadlineRuleIT`
проверяет, что он стартует пустым); правила вводятся только вручную через `POST /deadline-rules`, **UI для
них нет**. `startEvent` не используется, `documentTypeId`/`caseTypeId` для выбора правила не применяются,
`valid_from`/`valid_to` игнорируются.

**2. Но срок из документа создаётся и без правила.** `CaseOrchestrator` строит `TaskDeadline` напрямую из
извлечённых данных. Поэтому прежнее утверждение «нет правила — нет срока» **неверно глобально**: срок из
документа есть, срок **из права** — нет.

**3. `deriveAppointments` даёт только календарь** — ни задачи, ни срока, ни уведомления. И вызывается
**только если не было раннего выхода**: при `DUPLICATE`, `REVIEW_REQUIRED`, упавшем или пропущенном шаге
**не вызывается вообще**; исключения проглатываются.

**4. Уведомления о сроке не доставляются:**
- **PUSH жёстко недоступен** — `NotificationConfiguration.pushNotificationAdapter: available = false`;
- **EMAIL не работает**: `CaseOrchestrator.notifyPeople` и `OwnerNotifier.tell` передают
  `recipientAddress = null`, а `EmailAdapter.send` при `null` бросает `EmailDeliveryException` — **даже
  при настроенном SMTP**;
- **планировщика по `task_deadlines` нет** — «за N дней до срока» отправляет только ICS-фид.

**5. Календарь течёт по видимости.** `CalendarEventService.events()` берёт `calendar_events` **по
`tenant_id` без фильтра по пользователю, делу и конфиденциальности** — вся ручная запись и автозаписи
**видны всем пользователям арендатора** и попадают в их ICS-фид. Конфиденциальность не помечается: в фиде
маскировка смотрит только на `task_id`.

**6. `requires_verification` означает не то, что кажется:** это «не подтверждено человеком», а не «правило не
проверено». Из 3 454 таких сроков **3 066 — `INTERNAL`/`DOCUMENT_DATE`**, а `/deadlines/pending-verification`
выдаёт их как «ждут правила».

### 7.3. Дефекты в только что добавленном `DateClassifier` (найдены аудитом)

**Это мой код, и это ошибка — фиксирую честно.**

1. **Правила проверяются в фиксированном порядке, а не по близости к дате.** Следствие:
   - `«Termin am 12.11.2026, Zahlung bis 30.11.2026»` → **обе даты получают `PAYMENT_DEADLINE` 0.9**;
   - реалистичное `«Mahnung / Datum: 12.10.2026»` → **дата письма получает `PAYMENT_DEADLINE` 0.9** и
     автоматически попадает в календарь.
   Мой тест `DateClassifierTest.NearestWins.separate` проверял **только отдельные предложения** и потому
   дефект не поймал.
2. **Прошедшие даты не фильтруются** — старый счёт может снова попасть в календарь вопреки V38 и
   `CaseOrchestrator`, который для архивных документов обещает «без календаря».
3. **Дублирование**: автозапись в календаре дублирует `TaskDeadline` того же документа.

**Обязательно исправить:** определять категорию по **ближайшему** маркеру, а не по первому совпавшему
правилу; отбрасывать даты в прошлом; не создавать запись, если для этого документа уже есть срок.

### 7.4. Что не реализовано

Нет seed/UI/автоподбора `DeadlineRule`; нет автоматического юридического расчёта; нет push-провайдера; нет
подстановки e-mail получателя; нет планировщика напоминаний по `task_deadlines`; нет задачи из
распознанной даты; нет уведомления о созданном сроке; нет `DEADLINE_APPROACHING` в текущем коде; нет
per-user видимости и конфиденциальности `calendar_events`; нет тестов нового автопути.

### 8.2. Автоприём внутри одной категории — **решено не менять**

Аудит предлагал отправлять на проверку «близкий вызов» даже внутри одной категории, потому что задача
выводится из **типа**, а не из категории. Я это реализовал — и **откатил**.

**Что получилось:** правило ломает два обещания продукта.

1. `DemoCabinetIT.familyDemoIsFilled` — демо-кабинет показывает 2 разобранных письма вместо 3.
2. `DeadlineProvenanceIT` — срок из документа **перестаёт создаваться**, потому что документ уходит в
   проверку, и оркестратор не запускается.

**Почему это важно.** Цена правки — **любое письмо с близким альтернативным типом уходит в проверку**, а
значит «сфотографировал → появился срок» перестаёт работать до ручного разбора. Это **основная ценность
продукта**, и обменять её на защиту от `Rechnung`/`Mahnung` — плохая сделка.

**Что оставлено вместо этого:** альтернативный тип **сохраняется** в `document_classifications`, то есть
человек видит второй вариант и может исправить; review уже срабатывает при уверенности < 0.85 и при
разных категориях.

**Если возвращаться к этому позже**, правильный путь — не «больше проверок», а:
- **отдельный признак** в `document_type_scenarios`, что типы различаются только оттенком (Mahnung —
  частный случай Rechnung), и тогда принимать;
- **калибровка** уверенности на реальных документах;
- **обратная связь** от исправлений человека, которой сейчас нет вообще.

**Это записано как осознанный отказ, а не как забытая задача.**

**2. §14 — исходящие счета.** ~~`InvoicePdfRenderer` не подключён ни к одному эндпоинту (мёртвый код с

**5. §10.4 — ассистент только читает.** **Исправлено частично, и найден дефект серьёзнее исходного.**
`create_task` был зарегистрирован в политике как `WRITE` и **отсутствовал в диспетчере**. Хуже: `confirm()`
**помечал задание выполненным, писал `confirmed: true` и возвращал «предложение подтверждено и выполнено» —
не выполняя ничего**. Все подтверждённые действия в истории продукта были сообщением об успехе без работы.
Теперь подтверждение читает сохранённые параметры и **исполняет инструмент**; `create_task` создаёт задачу
с исполнителем-заявителем (`AssistantConfirmationTest`, 10 тестов, 85 в AI-пакетах).

**6. §9.1 — пять шагов конвейера не выполняются.** ~~Объявлены в enum, ноль ссылок в коде.~~
**Сделано явным и проверяемым:** `DocumentProcessingStep.NOT_IMPLEMENTED` перечисляет пять шагов, а
`DocumentProcessingStepCoverageTest` (4 теста) падает, если enum-значение не выполнено и не перечислено.
Пробел стал **решением, которое видно**, а не умолчанием.

перспективы, поворота и повышения контраста**.

**9. §22 — архив.** ~~Хеш хранится, но не проверяется.~~ **Исправлено:** `GET /documents/{id}/integrity`
