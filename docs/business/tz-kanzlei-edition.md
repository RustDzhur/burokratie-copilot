# Техническое задание: редакция «Kanzlei» для Bürokratie-Copilot

**Версия:** 1.2 · 22.10.2026 — изменения: (1.1) лишний код **удаляется**, а не прячется (§4.3);
(1.2) добавлен модуль §5.2 «Zuordnung zu Mandanten» — маршрутизация документов по мандантам.
**Заказчик:** владелец продукта. **Исполнитель:** владелец продукта (или команда).
**Язык ТЗ:** русский. **Язык интерфейса:** немецкий (термины бухгалтера, глоссарий в §7).

---

## 1. Цель

Переделать Bürokratie-Copilot из «платформы для всех» в **рабочий инструмент канцелярии
(Steuerberater / Buchhaltungsbüro, 3–20 сотрудников)**: входящие документы становятся
готовыми к проводке данными без ручного ввода, сроки не пропускаются, экспорт в DATEV
делается одной кнопкой.

**Критерий успеха одним предложением:** бухгалтер, впервые открывший программу, без
обучения и без документации за 10 минут загружает 10 документов, видит извлечённые поля,
видит срок и формирует файл для DATEV.

**Что НЕ входит в эту редакцию (не делать):**
- налоговые расчёты, декларации, отчётность — территория DATEV и закона;
- Buchung внутри программы — мы готовим данные, канцелярия бухтирует в DATEV;
- портал для мандантов (переносится в P2);
- семейный/частный режим — **удаляется из кода** (§4.3);
- банковские интеграции, ИИ-советник, «умные агенты».

## 2. Кто пользователь и что его цепляет

### Персоны

| Персона | Кто это | Главная боль | Что должно зацепить |
|---|---|---|---|
| **Buchhalter/in** (основная) | сотрудник, разбирающий входящую почту и Belege | ручное сортирование, перепечатывание полей, догонялки за мандантами | открыл Posteingang — и всё уже разобрано: тип, мандант, поля, срок |
| **Steuerberater/in** (владелец) | принимает решение о покупке | пропущенный срок = деньги и ответственность; часы сотрудников на бумагах | экран Fristen, где ничего не теряется; отчёт «сколько часов сэкономлено» |
| **Fachangestellte/r** | помощник, готовит ответы | непонятные письма от ведомств | черновик ответа, который шеф только проверяет |
| **Mandant** (косвенно) | клиент канцелярии | его дёргают за документами | канцелярия перестаёт его дёргать вручную (P1–P2) |

### Формула интереса (что продаём на демо)

`Бросил документ → тип и мандант определены → поля извлечены → срок поставлен → файл для DATEV`

Пять кликов от загрузки до экспорта. Всё, что мешает этой цепочке, — удаляется.

## 3. Принципы интерфейса (обязательные)

1. **Домашний экран = Posteingang.** Не дашборд со статистикой, а очередь работы.
   Бухгалтер утром открывает программу и видит: что пришло, что готово, что горит.
2. **Три вопроса на каждый документ:** Was ist das? · Wem gehört es? · Bis wann?
   (Что это? Чей документ? Какой срок?) — программа отвечает на все три автоматически,
   человек только проверяет и жмёт «дальше».
3. **Язык бухгалтера, не программиста.** Не «Invoice», а «Beleg». Не «Contact», а
   «Mandant». Не «Future», а «Fristen». Ни одного английского термина, ни одного
   «системного» слова (глоссарий §7).
4. **Ноль настройки на старте.** Первый запуск — мастер на 3 шага (§6.1). Все
   продвинутые настройки — в одном разделе «Einstellungen», не рассыпаны по меню.
5. **Человек всегда в контуре.** Программа готовит и предлагает, человек подтверждает.
   Каждая кнопка «готово» = явная Freigabe. Это и для доверия, и для закона.
6. **Не больше 12 пунктов меню в 3 группах.** Остального в меню нет: лишний код
   удалён, а не спрятан (§4.3).

### 4.3. Удаление лишнего кода (решение: удалять, не прятать)

Всё, что не входит в навигацию Kanzlei и не является инфраструктурой, **удаляется из
кода и из базы данных**. Git хранит всю историю — вернуть модуль = revert одного
коммита, поэтому удаление безопасно.

| Модуль (пакет/экран/сущность) | Вердикт | Почему |
|---|---|---|
| `family` (пакет, экран, план «Familie», вид workspace) | удалить | не для канцелярии |
| `radar` + `memory` | удалить | ИИ-кластер без работающего ИИ; вернётся из git, если понадобится |
| `autopilot` | удалить | то же |
| `contracts` | удалить | договоры клиентов — работа CRM/DATEV канцелярии, не наша |
| `payments` (частичные платежи, экран) | удалить | сверка платежей — банк и DATEV |
| `assistant` (экраны, контроллеры запросов/инструментов) | удалить | AI-слой не реализован, только сбивает с толку |
| `banking` | удалить | банковские интеграции — P2/никогда |
| `publicstats` | удалить | модуль маркетинга платформы |
| `devices` | удалить | агенты устройств не нужны |
| `printing` | удалить | вернуть из git, если клиент захочет бумажные письма |
| `employees` (экран) | удалить | внутренний HR-экран |
| `company` (экран-кокпит) | удалить | администрирование переезжает в Einstellungen |
| `parties` | удалить | объединяется с `contacts` → Mandanten |
| `onboarding` (старый поток) | удалить | заменяется мастером §6.1 |
| `future` (экран) | удалить | у канцелярии есть Fristen |
| механизм `audience`/`minTier` в `screens.ts` | упростить | после удаления остаётся один режим — навигация становится простым списком |

**Оставить как инфраструктуру (не трогать, это не «лишнее»):**
identity (auth, RLS, MFA, OIDC), audit, billing (тарифы: остаётся один план для
канцелярий, семейный/частный удаляются), notifications, privacy/deletion (DSGVO),
i18n/design-system, OCR-конвейер (`documents`), mail (приём и отправка),
templates + generated-documents + responses + legal (движок писем),
archive, security, calendar/dates/dateMarkers, approvals, cases/tasks, contacts,
advisor, einvoicing, invoices, reports, integrations, importer/ingest/orchestration,
bridge + scan (сканер — путь приёма документов в Posteingang).

**Порядок удаления (по одному модулю, отдельный коммит на модуль):**

1. Выписать все ссылки на модуль: `rg` по пакету, экранам, роутам, тестам, i18n-ключам.
2. Удалить код: пакет бэкенда, страницы, пункты меню, роуты, i18n-ключи, тесты.
3. Flyway-миграция `V<n>__drop_kanzlei_unused.sql`: `DROP TABLE IF EXISTS ... CASCADE`
   для таблиц удалённых модулей + очистка перечислений (виды workspace, тарифы).
4. `./mvnw verify` + `pnpm typecheck && pnpm lint && pnpm test` — зелёные.
5. Коммит с сообщением вида `chore(kanzlei): remove family module`.
6. Следующий модуль. Не удалять несколько модулей одним коммитом.

Результат: в коде не остаётся «спрятанного» — только то, что работает и продаётся.

## 5. Функциональные требования по модулям

Приоритеты: **P0** — без этого не продавать; **P1** — первая итерация после первого
клиента; **P2** — потом.

### 5.1. Posteingang (P0) — главный экран

- **Лента-очередь** всех входящих документов из всех источников (загрузка, e-mail, скан).
  Одна лента, сортировка: сначала «горит срок», потом новые.
- **Карточка в ленте:** иконка типа, название, мандант, извлечённые поля (Betrag, Datum,
  Lieferant), статус, бейдж срока. Красный бейдж — срок < 3 дней.
- **Счётчики сверху:** Neu · Offen · Zu prüfen · Ohne Mandant · Exportiert · Fehler.
- **Фильтры:** статус, тип, мандант, срок, поиск (включая OCR-текст — поиск по содержимому).
- **Приём:** drag&drop PDF/JPEG, кнопка «Einscannen», e-mail-ящик (переиспользовать
  MailIngestController). Фотография с телефона через PWA — уже есть.
- **Пакетные действия:** отметить несколько → «als geprüft», «an Mandant zurück»,
  «exportieren».
- **Пустое состояние:** «Keine neuen Dokumente. Gut so.» + кнопка «Demo ansehen».
- **Demo-Modus:** кнопка «Demo-Kanzlei ansehen» — workspace с 20 фейковыми Belegen и
  сроками и парой документов «Ohne Mandant» (пакет `demo` в бэкенде уже существует —
  дособрать). Это то, что показывают бухгалтеру на первой встрече: система не угадывает
  манданта вслепую — сомнительное она честно показывает как неразобранное.

### 5.2. Zuordnung zu Mandanten (P0 — критический модуль)

Одна канцелярия = один почтовый ящик + десятки мандантов. Система обязана определить,
чьей бухгалтерии принадлежит каждый входящий документ, и **никогда не приписать его
чужому манданту молча**.

- **Сигналы для определения манданта (по силе):**
  1. адресный блок письма (получатель) — письмо приходит на адрес манданта или в
     канцелярию с указанием манданта внутри;
  2. e-mail: отправитель (если это мандант), тема, вложения;
  3. содержимое: IBAN, USt-IdNr., Steuernummer, название фирмы, адрес;
  4. запомненный шаблон: «этот отправитель/макет всегда принадлежит манданту X».
- **Правило безопасности (главное):** если уверенность ниже порога — мандант
  **не назначается**. Документ попадает в Posteingang со статусом «Ohne Mandant» и
  подсветкой. Молчаливая ошибка запрещена: лучше спросить человека, чем отправить
  данные клиента А в бухгалтерию клиента Б.
- **Назначение человеком:** в карточке документа — поле «Mandant» с поиском по списку.
  Один клик. Пере-назначение (был А, стал Б) возможно и обязательно пишется в аудит:
  кто, когда, с какого на какой мандант (append-only audit уже есть).
- **Обучение на исправлениях:** каждая ручная правка манданта запоминается как правило
  (отправитель/макет/ключевые слова → мандант). Следующий похожий документ
  определяется автоматически. Правила видны в Einstellungen → Zuordnung и удаляются
  одной кнопкой.
- **Один документ = один мандант.** Письмо, касающееся двух мандантов, разбивается
  вручную (копия документа на второго манданта) — система не «делит» документ сама.
- **Экспорт:** Beleg без подтверждённого манданта в пакет DATEV не попадает (§5.6).
  Пакет всегда формируется по одному манданту.
- **Метрика модуля:** доля авто-назначений с правильным мандантом и доля
  «Ohne Mandant» — выводятся в Berichte.

### 5.3. Beleg-карточка (P0)

Открывается из ленты. Две колонки:

- **Слева:** превью документа (PDF/изображение), кнопки поворота/увеличения.
- **Справа:** извлечённые поля: Lieferant, Rechnungsnummer, Rechnungsdatum, Leistungsdatum,
  Nettobetrag, USt-Satz, Bruttobetrag, Zahlungsziel. Каждое поле редактируется; рядом —
  индикатор уверенности распознавания.
- **Исправление учит систему:** сохранённая правка запоминается как правило для такого
  типа документа и поставщика (уже есть DocumentExtraction + правила — расширить).
- **Действия (кнопки):**
  - `Geprüft` → Beleg переходит в Freigaben;
  - `An Mandant` → открыть Anfrage (P1);
  - `In DATEV exportieren` → добавить в пакет экспорта;
  - `Archivieren`, `Zurück an Posteingang`.
- **Статусы Beleg** (расширить существующий `DocumentStatusMachine`):
  `Neu → Offen → Zu prüfen → Exportiert`, плюс `Fehler` (не прочитан, дубликат, нет манданта).
- **Аудит:** кто и когда менял поле, кто экспортировал (append-only audit уже есть — подключить).

### 5.4. Fristen (P0)

- **Список сроков:** мандант, документ, тип срока, дата, сколько осталось.
  Типы: Widerspruchsfrist, Einspruchsfrist, Zahlungsziel, Mahnfrist, Antragsfrist,
  Abgabefrist — берутся из письма автоматически (`DetectedDateService` уже это умеет —
  вывести на экран).
- **Цвет:** осталось >14 дней — спокойно; 7–14 — жёлтый; <7 — красный.
- **Напоминания** за 7/3/1 день (notifications есть).
- **Кнопка «erledigt»** только с подтверждением: «Frist als erledigt markieren?» —
  потому что пропущенный срок — это ответственность канцелярии.

### 5.5. Mandanten (P0)

- **Список:** имя, тип, сколько документов в работе, сколько сроков горит, чего не хватает.
- **Карточка манданта:** Vorgänge, документы, сроки, история запросов (P1).
- **Показатель «Gesundheit»:** «2 Belege fehlen» / «Frist läuft» — один взгляд, где беда.
- **Импорт списка мандантов из CSV** (или из экспорта DATEV Kontenbeschriftungen).

### 5.6. Exporte → DATEV (P0, ключевой модуль)

- **Экран:** список пакетов: дата, мандант, количество Belege, сумма, статус
  (Erstellt → Heruntergeladen → Importiert).
- **Формирование пакета:** выбрать период/манданта/Belege со статусом `Geprüft` →
  сгенерировать CSV → скачать.
- **Формат:** DATEV-Format CSV, Buchungsstapel (Import «Rechnungswesen-Daten» в DATEV).
  Точный профиль полей и кодировка согласуются с первой канцелярией и фиксируются
  в Приложении 1 к этому ТЗ (у каждой канцелярии возможны нюансы).
  Базовый набор полей: Buchungssatz, Sollkonto, Habenkonto, Belegdatum, Belegfeld 1,
  Belegfeld 2, Buchungstext, Betrag, Steuerschlüssel.
- **Konto-Mapping:** таблица «Lieferant/Kategorie → Sollkonto/Habenkonto», ведётся в
  Einstellungen, импортируется из DATEV (файл Kontenbeschriftungen — тоже CSV).
  Один раз настроил — дальше экспорт без вопросов.
- **Честность:** кнопка экспорта показывает: «12 Belege · 8.431,20 € · 3 ohne Konto-Zuordnung»
  — и не даёт экспортировать то, что без конто-привязки, а показывает список.
- В коде DATEV отсутствует полностью — модуль пишется с нуля (оценка 1–2 недели).

### 5.7. Anfragen / Belegebeschaffung (P1)

- Из карточки Beleg: «An Mandant» → шаблон письма с автозаполнением:
  «Sehr geehrte/r Frau/Herr …, für die Buchung der Rechnung vom … fehlt uns: …».
- Рассылка через почту (EmailSender есть), история запроса сохраняется у манданта.
- Напоминание через 7 дней, если ответа нет (notifications есть).

### 5.8. Briefe (P1)

- Шаблоны: Anfrage, Antwort auf Behördenschreiben (Erklärung + Entwurf), Mahnung.
- **Правило «erklären, nicht beraten»:** черновик письма всегда с пометкой
  «Entwurf — Freigabe durch Steuerberater», финально отправляет только канцелярия.
- Генератор: поля документа → текст шаблона (templates + GeneratedDocumentController есть).

### 5.9. Berichte (P2)

- Три цифры: обработано Belege, сэкономлено часов (по норме 3–5 мин/Beleg), сроки спасены.
- Одна страница, для разговора с владельцем канцелярии о продлении/расширении.

### 5.10. Портал манданта (P2, за границами первой итерации)

- Личный кабинет манданта: загрузить Beleg, увидеть запросы, ответить.
- Только после того, как 5 канцелярий работают с Posteingang.

## 6. Онбординг и пустые состояния

### 6.1. Мастер первого запуска (3 шага, 5 минут)

1. **«Wer sind Sie?»** — имя канцелярии. Всё. Больше ничего не спрашиваем.
2. **«Ihre Mandanten»** — создать 3 мандантов вручную или импортировать CSV.
3. **«Erste Dokumente»** — «Бросьте сюда 20 документов — или посмотрите Demo-Kanzlei».

После шага 3 пользователь попадает в Posteingang с уже разобранными документами.

### 6.2. Пустые состояния (обязательные)

- Posteingang пуст: «Keine neuen Dokumente. Gut so.» + подсказка «E-Mail-Weiterleitung
  einrichten» (кнопка).
- Нет мандантов: «Legen Sie Ihren ersten Mandanten an» — кнопка сразу.
- Нет сроков: «Keine Fristen. Wir prüfen jede neue Post automatisch.»

### 6.3. Что пользователь НЕ видит

- никаких слов «API», «Workflow», «Integration» на первом экране;
- никаких настроек, пока он их сам не открыл;
- никаких ошибок вида «403 FEATURE_DISABLED» — только по-человечески:
  «E-Mail-Anbindung ist noch nicht eingerichtet. [Anleitung]».

## 7. Глоссарий (обязательный для всех экранов)

| Сейчас (или по-умолчанию) | Должно быть | Заметка |
|---|---|---|
| Invoice / Rechnung | **Beleg** | входящий счёт = Beleg |

## 11. Критерии приёмки (Definition of Done)

1. **Тест нового пользователя:** бухгалтер, никогда не видевший программу, без подсказок
   за 10 минут: создаёт манданта → загружает 10 документов → видит извлечённые поля →
   видит срок → формирует DATEV-файл. Считается пройденным, если ни одного вопроса
   «а где тут…» не было.
2. **Пять кликов** от загрузки документа до его появления в пакете экспорта.
3. **Меню:** не больше 12 пунктов, 3 группы, ни одного «системного» термина.
4. **Экспорт:** файл открывается стандартным импортом DATEV (проверено с канцелярией
   на тестовом Mandanten).
5. **Аудит:** каждое изменение поля и каждый экспорт записаны (append-only).
6. **Удалённое отсутствует:** `rg` по удалённым пакетам и экранам возвращает 0
   упоминаний, миграции DROP применены, CI зелёный.
7. **Маршрутизация по мандантам:** тест: 100 документов 10 разных мандантов через
   один почтовый ящик → не менее 95 % назначены правильно, 100 % сомнительных попали
   в «Ohne Mandant», ни один документ не ушёл в экспорт без подтверждённого манданта.
