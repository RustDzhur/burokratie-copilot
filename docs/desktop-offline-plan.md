# Десктопные приложения с офлайн-режимом и двусторонней синхронизацией

**Статус: план, не реализация.** Ничего из описанного ниже не написано. Документ отвечает на вопрос
«как это сделать» и **называет то, что сделать нельзя** — потому что половина честного плана здесь
состоит из ограничений.

---

## 1. Что есть сейчас — измерено, а не по памяти

Все цифры получены запросами к схеме и файловой системе репозитория.

| Факт | Значение | Почему это важно для офлайна |
|---|---|---|
| Таблиц | **147** | объём работы по синхронизации |
| С `tenant_id` | **118** | мультитенантность надо тащить на клиент |
| **Все `id` — UUID** | **133 из 133** | ✅ клиент может создавать записи офлайн без коллизий |
| С `updated_at` | **75 из 147** | ⚠️ **у половины таблиц нет курсора изменений** |
| С `deleted_at` | **25 из 147** | ❌ **удаление в 122 таблицах невидимо для синхронизации** |
| С `version` | 12 | зачаток оптимистичных блокировок, но не система |
| `outbox_events` | **22 790 строк**, транзакционный | ✅ готовая основа журнала изменений |
| `audit_events` | **134 964 строки** | журнал есть, но он **не** полный change log |
| `idempotency_records` | есть | ✅ повторная отправка операции безопасна |
| `document_blobs` | 20 479 строк, 26 МБ | файлы — отдельная задача |
| **`storage_backend`** | **`local-fs`** | ❌ объектного хранилища нет — клиент файлы не получит |
| Триггеры | 75 | приём «менять схему через триггеры» уже в ходу |
| Миграции | 68 | локальная база должна применять **те же** |
| Бэкенд | Spring Boot 3.5 / Java 21, 460 файлов | |
| Фронтенд | Next.js 15, 222 файла | |
| Изоляция | RLS + `current_tenant_id()` | политику надо включить и на клиенте |
| Шифрование | приложение **отказывается стартовать** без `BC_ENCRYPTION_KEY` | ✅ правильное поведение, и его надо сохранить на клиенте |

**Три вывода из таблицы, и они определяют весь план:**

1. **UUID везде — это большая удача.** Офлайн-создание записей возможно без переделки схемы.
2. **`updated_at` есть только у 75 таблиц, `deleted_at` — у 25.** Значит, синхронизацию **нельзя** построить
   на «выбери всё, что новее». Половина схемы не имеет ни курсора, ни следа удаления.
3. **`outbox_events` уже существует и транзакционен.** Это лучшая отправная точка, чем что-либо, что
   пришлось бы строить с нуля.

## 2. Главное решение: что именно запускается на десктопе

Три варианта, и два из них я предлагаю отклонить.

**Вариант A — Electron/Tauri + локальный PostgreSQL + тот же Spring Boot бэкенд.**
На клиенте работает **тот же самый артефакт** (`services/api`) с профилем `desktop`, рядом локальный
PostgreSQL, UI общается с ним по `127.0.0.1`.

**Вариант B — Electron + SQLite + переписанная логика.** ❌ **Отклонить.** 147 таблиц, RLS,
`current_tenant_id()`, jsonb, 68 миграций, 68 контроллеров, 1864 теста. Переписать это — **не план, а
второй продукт**, и он **разойдётся** с первым на первой же новой функции. Каждая новая фича сервера
потребует двойной работы, и однажды они начнут отвечать по-разному на один вопрос — а это бухгалтерия и
право.

**Вариант C — только кэш в браузере (PWA + IndexedDB).** ❌ **Не подходит под требование.** Нет своей базы
в том смысле, о котором вы говорите, нет процесса, работающего в фоне, и браузер может выгрузить данные.

**Предлагаю A.** И у него есть подтверждение в самом коде: **тот же артефакт уже умеет работать вторым
профилем** — `--spring.profiles.active=worker`. То есть «один продукт, несколько режимов запуска» —
**уже принятая в этом проекте архитектура**, а не новая идея.

**Оболочка: Electron или Tauri.**

| | Electron | Tauri |
|---|---|---|
| Размер | ~150 МБ | ~10 МБ |
| Рендеринг | свой Chromium — **одинаковый** на Windows и macOS | системный WebView — **разный** |
| Язык | Node/TS | Rust |
| Автообновление | зрелое | есть |
| Подпись/нотаризация | отработано | есть |

**Предлагаю Electron** для первой версии: приложение сложное и обязано **выглядеть и вести себя
одинаково** на двух системах, а системный WebView на Windows (Edge) и macOS (Safari/WebKit) — это две
разные реализации CSS и JS, то есть **два места для разных багов** в одном продукте. Tauri — хороший
кандидат на вторую итерацию, когда стабильность важнее размера.

**Вес:** PostgreSQL ~250 МБ + JVM ~200 МБ + приложение = **~600–700 МБ на диске**. Это надо принять
осознанно; SQLite дал бы 50 МБ, но см. отклонённый вариант B.

## 3. Синхронизация — здесь вся сложность

### 3.1. Чего делать нельзя

**Нельзя «синхронизировать базу».** Нельзя сравнивать таблицы целиком, нельзя полагаться на `updated_at`
(есть у половины схемы) и нельзя полагаться на «кто последний, тот и прав» для денег.

### 3.2. Что предлагаю: сервер — источник истины, поток изменений — механизм

**Четыре части.**

**(1) Журнал изменений на сервере — `sync_changes`, заполняемый триггерами.**

```
sync_changes(
  revision      bigserial,        -- монотонная, НЕ время
  tenant_id     uuid,
  table_name    text,
  row_id        uuid,
  operation     text,             -- INSERT | UPDATE | DELETE
  changed_at    timestamptz,
  payload       jsonb             -- новая строка целиком, или только изменённые поля
)
```

Почему **триггер, а не сервис**: таблиц 147, и **ни один человек не будет поддерживать 147 вызовов
вручную** — забудут в первой же новой функции. В проекте **уже 75 триггеров**, приём в ходу.
Триггер можно сгенерировать миграцией по всем таблицам сразу — и **новая таблица автоматически попадёт в
синхронизацию**.

**(2) Монотонная ревизия на арендатора, а не время.** Клиент говорит: «дай всё после ревизии 41 882».
Это надёжнее отметок времени: часы на клиенте и сервере расходятся, а две записи в одну миллисекунду
теряются при выборке «строго больше».

**(3) Локальная очередь исходящих на клиенте — `local_outbox`.** Каждая запись локально **сначала идёт в
очередь**, потом применяется. Очередь переживает перезапуск, выключение и падение.

**(4) Отправка с ключом идемпотентности.** Каждая операция несёт `operation_id` (UUID, сгенерированный на
клиенте). Сервер **уже имеет `idempotency_records`** — повторная отправка после обрыва связи не создаст
вторую запись.

### 3.3. Конфликты: политика **на класс сущностей**, а не одна на всех

Это, на мой взгляд, самое важное место в плане. **Единая политика («сервер побеждает» или «последний
побеждает») обязательно приведёт к потере данных там, где это недопустимо.**

| Класс | Примеры | Политика |
|---|---|---|
| **Только добавление** | `audit_events`, `outbox_events`, платежи, письма | **объединение**, конфликта нет по построению |
| **Справочники и настройки** | типы документов, шаблоны, налоговые ставки, права | **побеждает сервер** — решает администратор аккаунта |
| **Рабочие объекты** | дела, задачи, документы, заметки | **поле-за-полем, побеждает поздняя правка + запись о конфликте** |
| **Деньги и нумерация** | счета, платежи, номера счетов | **никогда не сливать автоматически** — только к человеку |

Почему **поле-за-полем**, а не строка целиком: два человека офлайн правят **разные поля одного дела**.
«Строка целиком» молча выбросит чужую правку. При поэтапном слиянии обе сохранятся, а если правили **одно
поле** — только тогда создаётся конфликт и он идёт человеку.

**Запись о конфликте обязательна.** Молчаливое разрешение конфликта — это то, из-за чего в бухгалтерских
системах потом «не сходятся цифры», и никто не может сказать почему. Конфликт должен **быть виден** и
иметь кнопку «показать обе версии».

### 3.4. Файлы (blobs) — отдельная задача, и сейчас она не решена

Документы лежат в **`local-fs`**, то есть **на диске сервера**. Десктопный клиент их так не получит.
Что нужно:

1. **Перевести хранилище на объектное** (S3-совместимое, например MinIO в инфраструктуре) — код уже
   имеет абстракцию `BlobStore`, но используется локальный бэкенд.
2. Либо **эндпоинт передачи по хэшу**: `document_blobs.content_hash` **уже есть** ✅, значит синхронизация
   формулируется как «вот мои хэши, дай то, чего у меня нет» — и **повторная передача одного файла
   невозможна**.
3. **Скачивание заранее, а не по требованию.** Файл, который нужен офлайн, должен быть **уже скачан**.
   Значит нужна политика: что качать (все документы арендатора? за период? помеченные «в дорогу»?) —
   **и это вопрос к вам**, см. §6.

## 4. Что **не должно** работать офлайн — иначе появятся неправильные данные

Это не техническое ограничение, а **содержательное**, и его надо решить до начала работы.

**1. Номера счетов — нельзя выдавать офлайн.** `InvoiceNumberService` выдаёт **глобально уникальный
номер** и объявлен `@Transactional(MANDATORY)`: он **отказывается работать вне транзакции**, чтобы номер
не был израсходован при откате. **Два офлайн-клиента выдадут один и тот же `RE-2026-0042`.** Это уже
**не техническая проблема, а бухгалтерская**: пропуск или дубль в нумерации счетов — то, о чём спрашивает
аудитор.

Варианты: (а) **выдача номеров только онлайн**; (б) **резервирование блока номеров на устройство, пока
есть связь** (тогда пропуски в нумерации **неизбежны**, и это надо принять осознанно). **Я рекомендую (а)**
для первой версии: счёт — это то, что не стоит выставлять офлайн.

**2. Проверка E-Rechnung.** Правила публикует заказчик, и локальная копия набора правил **может быть
устаревшей**. Счёт, «прошедший проверку» по старому набору, **не является проверенным**. Значит:
проверка — **на сервере**, а офлайн счёт помечается как **непроверенный**, а не как корректный.

**3. Импорт банковских выписок (CAMT) и сопоставление платежей.** Сопоставление требует видеть **все**
поступления по счёту, а офлайн-клиент видит только свои. Совпадение, найденное офлайн, может быть
**неверным**, потому что платеж уже сопоставлен в другом месте.

**4. Второй фактор, приглашения, онбординг.** По природе своей требуют связи.

**5. Журнал аудита.** **Только в одну сторону.** Записи с клиента **добавляются** к журналу на сервере, но
**никогда не перезаписывают** его. Журнал, который клиент может править, — **не журнал**. Более того:
офлайн-действия записываются на клиенте с **локальным временем и меткой «подтверждено сервером позже»**,
иначе в журнале появятся записи, которых сервер не видел.

## 5. Безопасность: украденный ноутбук не должен стать копией документов

Здесь нельзя халтурить, потому что на клиенте окажется **вся база арендатора**.

1. **Шифрование локальной базы.** Полнодисковое шифрование — **недостаточно** (оно защищает выключенный
   ноутбук, но не работающий). Нужно шифрование данных (SQLCipher-подобное) или шифрованный том,
   разблокируемый при входе.
2. **Ключ — в хранилище ОС, не в файле.** macOS Keychain, Windows DPAPI/Credential Manager. Приложение
   **уже отказывается стартовать** без `BC_ENCRYPTION_KEY` — ✅ это правильное поведение, и его надо
   сохранить: **лучше не запуститься, чем хранить креденшелы открыто.**
3. **Вход офлайн — ограниченное окно.** После успешного входа онлайн выдаётся ключ, привязанный к
   устройству. Срок — **дни, не месяцы**. По истечении — только чтение. **Второй фактор офлайн
   невозможен**: это надо сказать пользователю прямо в интерфейсе, а не показывать непонятную ошибку.
4. **Изоляция арендатора на клиенте.** **Тот же RLS и `current_tenant_id()`**, потому что политика — это
   то, что защищает от ошибки в коде запроса. Либо **одна локальная база на арендатора** — тогда
   разделение физическое и самое надёжное.
5. **Права проверяются локально.** Если сотрудника уволили, а ноутбук офлайн — он **всё ещё имеет доступ**
   к скачанным данным. Это **неизбежное следствие** офлайн-режима, и это надо **записать** как принятый
   риск, а не сделать вид, что его нет. Смягчение: короткое окно + шифрование + журнал доступа.

## 6. Этапы — и что проверяется на каждом

**Этап 0. Проверка подхода на одной сущности (1–2 недели).**
Двусторонняя синхронизация **только `cases`**: журнал изменений, ревизия, локальная очередь,
идемпотентная отправка, конфликт поле-за-полем — **с тестами в обе стороны**.
**Зачем именно так:** если на одной таблице это не выйдет чисто, **весь подход неверен**, и узнать это
надо сейчас, а не после сборки установщиков.

**Этап 1. Клиентская сборка.** Локальный PostgreSQL + тот же бэкенд профилем `desktop`, те же 68 миграций,
RLS включён. Проверка: **одни и те же тесты проходят локально и на сервере.**

**Этап 2. Скачивание.** Журнал изменений триггерами, ревизия на арендатора, эндпоинт «дай после N».
Проверка: клиент, отключённый на сутки, после включения **получает ровно пропущенное** и ничего не теряет.

**Этап 3. Отправка.** Локальная очередь, `operation_id`, использование существующего
`idempotency_records`. Проверка: **обрыв связи посреди отправки не создаёт дублей** — это тест, который
обязан быть.

**Этап 4. Файлы.** Объектное хранилище или передача по хэшу. Проверка: офлайн-документ **открывается**,
потому что был скачан заранее.

**Этап 5. Конфликты.** Политики по классам из §3.3 + экран разрешения конфликтов. Проверка: два клиента
правят одно дело офлайн, обе правки **видны**, а не потеряны.

**Этап 6. Упаковка.** Установщики, **подпись и нотаризация** (macOS без нотаризации просто не запустится),
автообновление.

**Этап 7. Запреты из §4.** Интерфейс **честно говорит**, что нельзя офлайн, вместо непонятной ошибки.

## 7. Честная оценка и то, что мне нужно от вас

**Это месяцы работы, а не недели.** Основная сложность — **не десктопная оболочка** (её собрать
относительно просто), а **синхронизация 147 таблиц с корректным разрешением конфликтов**. Оболочка —
недели. Синхронизация — основное время.

**Четыре вопроса, без ответов на которые план неполон:**

1. **Что именно должно работать офлайн?** «Открыть и посмотреть» — **в разы дешевле**, чем «править
   офлайн». Если правки офлайн нужны **не для всех** сущностей, объём работы падает сильно.
2. **Сколько данных на клиенте?** Все документы арендатора за всё время — или, скажем, за последние
   12 месяцев и помеченные «в дорогу»? От этого зависит и диск, и время первой синхронизации.
3. **Сколько устройств на один аккаунт и правят ли они одно и то же?** Если у каждого сотрудника
   **свои** дела — конфликтов почти не будет, и план резко упрощается. Если **общие** — нужна вся
   машинерия конфликтов.
4. **Что важнее: работать без интернета вообще, или переживать короткие обрывы?** «Переживать обрывы» —
   на порядок проще: тогда можно требовать связь раз в несколько минут и не строить долгий офлайн.

**Что я предлагаю сделать прямо сейчас:** **Этап 0** — двусторонняя синхронизация одной сущности с
тестами. Он **дешёвый**, и он **отвечает на главный вопрос**: годится ли выбранный подход, прежде чем в
него вложатся месяцы.

**И одна вещь, которую надо решить до кода:** **номера счетов офлайн выдавать нельзя** (§4.1). Это не
техническая деталь, а вопрос корректности бухгалтерии. Если офлайн-выставление счетов требуется — это
нужно обсудить отдельно, потому что решение будет с последствиями, которые придётся принять осознанно.
