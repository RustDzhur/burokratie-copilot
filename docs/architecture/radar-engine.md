Источник требований: `docs/MASTER_SPEC_BUSINESS_MEMORY_RADAR.md` §6. Решения: D-07, D-10 (`decisions.md`). Зависит от Business Memory (факты, связи).

## Модель (RD-01)

Новые таблицы (вариант C — существующие уведомления не имеют жизненного цикла находки):

- `radar_findings`: поля ТЗ §6.3 + `finding_key` (устойчивый ключ), `rule_id`, `rule_version`, `ai_model_run_id` (для объяснения);
- `radar_finding_evidence`: `finding_id`, `document_id`, `page`, `snippet`, `fact_id` — **внешние ключи, не JSONB**;
- `radar_finding_events`: журнал переходов и повторных оценок.

Автомат статусов: `NEW → UNDER_REVIEW → CONFIRMED | DISMISSED | SNOOZED | RESOLVED`, `RESOLVED/DISMISSED → REOPENED` при новых существенных данных. Переходы разрешает только backend (по образцу `DocumentStatusMachine` и `CaseStatusMachine`).

## Правила (RD-03, RD-04)

Интерфейс `RadarRule`: необходимые данные, условие срабатывания, **серьёзность (вычисляется правилом)**, объяснение, допустимые действия, условия закрытия, условия повторного открытия, версия. Запуск: по событию `document.processing_completed` и по расписанию. AI не назначает серьёзность; он может объяснить находку (RD-10), результат хранится рядом с `ai_model_run_id`.

Первая поставка (RD-04): B1 изменение суммы относительно предыдущих счетов поставщика, B2 дубликат, B3 смена реквизитов, D1 просроченная задача, A1 приближение срока уведомления о расторжении, C1 нет обязательного документа. Для каждого — позитивный и негативный тест.

## Дедупликация (RD-02)

`UNIQUE(tenant_id, finding_key)`; повторное обнаружение обновляет `last_evaluated_at`; повторное открытие при новых данных; параллельная оценка не создаёт дубль (тест). Уведомление создаётся один раз на находку (канал доставки — существующий `notifications`).

## Что запрещено правилами проекта

Не рассчитывать юридические сроки; не объявлять расхождение ошибкой; не показывать неуверенный срок как подтверждённый юридический; не создавать находку на данных, недоступных tenant.
