# Архитектурные решения аудита ТЗ (D-01 … D-13)

Принятые при сопоставлении `docs/task.md` (ТЗ v1.0) и `docs/MASTER_SPEC_BUSINESS_MEMORY_RADAR.md` (ТЗ v2.0) с кодом. Основание — строки матрицы `docs/spec-reconciliation-matrix.md`. Решения принимались по правилам ТЗ v2.0 §21 п. 19: «при противоречии документировать проблему и выбирать совместимое решение, сохраняющее существующую функциональность».

**Что здесь не сказано:** эти решения — проектные, они не прошли проверку владельцем продукта. Всё, что требует решения владельца (тарифная видимость новых модулей, источники ключей, лимиты), вынесено в «Открытые вопросы» отчёта `docs/spec-reconciliation-report.md`.

Формат каждого решения: **проблема → затронутые пункты ТЗ → затронутый код → риск → решение → альтернативы → почему → подтверждающие тесты**.

**Тесты в строках «Подтверждение» — это тесты, которые должны появиться вместе с соответствующей задачей плана; кроме явно названных существующих (`MatchingIT`, `CaseLifecycleTest`, `PlatformAdminIT`, `TenantIsolationSuiteIT`, `contract.test.ts`, `UiContractIT`), их ещё нет.**

## D-01. Префикс API нового ТЗ

- **Проблема.** ТЗ v2.0 §14 пишет пути `/api/business-memory/...`, `/api/radar`, `/api/cases/...`; ТЗ v1.0 §20 и весь код используют `/api/v1/...`. ТЗ v2.0 в том же §14 разрешает «придерживаться существующей схемы».
- **Затронуто.** v1.0 §20; v2.0 §14.1–§14.5; строка S03-02.
- **Код.** все контроллеры `services/api/src/main/java/de/buerokratiecopilot/**/web/*Controller.java`; `apps/web/src/lib/api/resources.ts`; `UiContractIT`, `contract.test.ts`.
- **Риск.** второй префикс ломает проверку «каждый вызов UI имеет маршрут» и фильтры безопасности (`SubscriptionAccessPolicy`, `PlanFeatures` ориентируются на `/api/v1/…`).
- **Решение.** Все новые маршруты — под `/api/v1`: `/api/v1/memory/…` (вместо `/api/business-memory`), `/api/v1/radar/…`, `/api/v1/cases/{id}/plan…`, `/api/v1/approvals/…`.
- **Альтернативы.** (а) оставить пути как в v2.0 — отклонено: нарушает единый формат и версионирование; (б) `/api/v2` — отклонено: версия API не меняется из-за добавления функций.
- **Подтверждение.** `contract.test.ts` и `UiContractIT` для каждого нового вызова; `OpenAPI` описывает новые группы.

## D-02. Сущность BusinessEntity и связи BusinessRelationship

- **Проблема.** v2.0 §5.2 предлагает таблицы `BusinessEntity` и универсальную `BusinessRelationship(sourceType, sourceId, targetType, targetId)`. В v1.0 §19 прямо запрещено: «не создавай универсальные связи, позволяющие связать любой объект с любым другим, если они обходят целостность данных». В коде уже есть `contacts` (+адреса, роли поставщика/клиента/ведомства, `contact_relations`), `document_matches` (SUGGESTED/CONFIRMED/REJECTED, доказательства) и `document_relations`.
- **Затронуто.** v1.0 §19; v2.0 §5.2, §5.3, §13.3; строки S09-01, S09-02, S09-06, S09-07.
- **Код.** `V4__cases_and_contacts.sql`, `V3__documents.sql` (`document_relations`), миграции `document_matches`, `documents/matching/MatchingService`, `MatchingIT`.
- **Риск.** две системы контрагентов и две системы связей; обход внешних ключей; ошибочное слияние контрагентов по названию.
- **Решение.** (1) BusinessEntity = `contacts`; добавить `contact_identifiers` (VAT_ID, TAX_NUMBER, IBAN, EMAIL, DOMAIN, PHONE, EXTERNAL; нормализованное значение; уникальность в пределах tenant). Совпадение названий не является тождеством: слияние и предложения строятся по идентификаторам. (2) BusinessRelationship = `document_matches` (документ → дело/контакт/договор/счёт/обязательство/задача) + `document_relations` (документ ↔ документ) с добавленными `status`, `evidence`, `decided_by/at`; отношения «счёт → договор» и «договор → контрагент» — существующие внешние ключи.
- **Альтернативы.** универсальная таблица — отклонена из-за запрета v1.0 §19 и потери целостности; новая `business_entities` — отклонена как дубликат `contacts`.
- **Почему.** существующая модель покрывает статусы, доказательства и отклонение; не хватает идентификаторов и статуса у `document_relations`.
- **Подтверждение.** `ContactIdentifierIT` (два контакта с одним названием не сливаются), `MatchingIT` (повторный запуск не предлагает отклонённую пару), `TenantIsolationSuiteIT`.

## D-03. Дела: статусы, план, уровни автоматизации

- **Проблема (три конфликта).** (а) Статусы дела: v1.0 §11.2 — `NEW, IN_PROGRESS, WAITING_FOR_USER, WAITING_FOR_EXTERNAL_PARTY, WAITING_FOR_DOCUMENTS, WAITING_FOR_APPROVAL, ON_HOLD, COMPLETED, CLOSED, REOPENED` (они же в CHECK-ограничении `cases_status_chk`); v2.0 §7.2 — `OPEN, IN_PROGRESS, WAITING_FOR_USER, WAITING_FOR_EXTERNAL_RESPONSE, BLOCKED, COMPLETED, CANCELLED, REOPENED`. (б) План дела (v2.0 §7.3) дублирует workflow engine v1.0 §16. (в) Категории действий A/B/C (v2.0 §7.5) против четырёх уровней v1.0 §32.
- **Затронуто.** v1.0 §11.2, §16, §32; v2.0 §7.2–§7.6; строки S11-01, S11-03, S11-05, S11-10.
- **Код.** `V4__cases_and_contacts.sql`, `cases/CaseLifecycleService`, `CaseLifecycleTest`, `workflow/WorkflowEngine`, `workflow_runs.case_id`, `workflow_run_steps`, `approvals.automation_level`, `ai/security/ToolPolicy`.
- **Риск.** изменение применённой миграции запрещено (v2.0 §13.1); второй движок шагов и вторая система задач.
- **Решение.** (а) Каноничны статусы v1.0. Соответствие: `OPEN`→`NEW`; `WAITING_FOR_EXTERNAL_RESPONSE`→`WAITING_FOR_EXTERNAL_PARTY`; `BLOCKED`→`ON_HOLD` с причиной; `CANCELLED`→`CLOSED` с `close_reason=CANCELLED`. Текст v2.0 §7.2 заменён ссылкой. (б) План дела = `workflow_runs` с `case_id`; таблицу `case_steps` не создавать; добавить запрет запуска шага при невыполненных зависимостях и `evidence_required`. Шаг «создать задачу» порождает обычную `task`. (в) Каноничны 4 уровня: A = уровни 1–2 (чтение, рекомендация), B = уровень 3 (подготовка внутри системы), C = уровень 4 (исполнение/внешнее).
- **Альтернативы.** добавить статусы v2.0 новой миграцией — отклонено: два синонимичных набора усложняют отчёты и интерфейс; `case_steps` — отклонено как дубликат `workflow_run_steps` и `tasks`.
- **Подтверждение.** `CaseLifecycleTest` (граф переходов), `CasePlanIT` (зависимости шагов), `ApprovalContentBindingIT`.

## D-04. Факты и их история

- **Проблема.** v2.0 §5.2 `BusinessFact` требует историю значений, срок действия и замещение. В `document_extractions` одно значение на (документ, версия, поле) без истории.
- **Код.** `document_extractions` (`UNIQUE(document_id, version_id, field_key)`), `documents/fields/*`, `FieldExtractionIT`.
- **Риск.** правка факта уничтожает прежнее значение — нарушает критерий v2.0 §5.6 «изменение факта не уничтожает историю».
- **Решение.** факт остаётся строкой `document_extractions`; добавляются `fact_revisions` (прежнее значение, кто и когда изменил, причина, ссылка на замещающую ревизию), `subject_type/subject_id` (явные внешние ключи на контакт/договор) и столбец `verification` (`UNVERIFIED | USER_CONFIRMED | DERIVED | HYPOTHESIS`). Соответствие категориям происхождения v2.0 §5.2: оригинал документа — `source_kind=STRUCTURED/TEXT`; OCR — `OCR`; AI — `extractor=AI`; пользователь — `MANUAL` или `USER_CONFIRMED`; вывод системы — `DERIVED`; гипотеза — `HYPOTHESIS`.
- **Альтернативы.** отдельная таблица `business_facts` — отклонена: два источника правды о значении; снятие `UNIQUE` — отклонено: ломает извлечение по версии.
- **Подтверждение.** `FactRevisionIT`, `FieldExtractionIT`.

## D-05. События и хронология

- **Проблема.** v2.0 §5.2 `BusinessEvent` и §5.4 хронология. В коде шесть потоков: `case_events`, `contract_events`, `task_events`, `workflow_events`, `message_delivery_events`, `audit_events`.
- **Риск.** новая таблица событий потребует писать каждое событие дважды и разойдётся с аудитом.
- **Решение.** таблицу `business_events` не создавать; хронология — SQL-представление `v_business_timeline` над существующими потоками с полями `event_time` (когда произошло) и `recorded_at` (когда записано) и запросами по контрагенту, договору, делу.
- **Альтернативы.** отдельная таблица с проекцией — отклонена как дублирование; хранимая процедура — отклонена: представление проще проверять.
- **Подтверждение.** `TimelineIT` (включая права и изоляцию tenant).

## D-06. Обязательства

- **Проблема.** v2.0 §13.3 перечисляет «obligations». В коде `contract_obligations` (только для договора, `contract_id NOT NULL`) и срочные задачи документов.
- **Решение.** общую таблицу не создавать. Обязательство договора = `contract_obligations`; срочное действие по документу = `tasks` + `task_deadlines`; связь — `tasks.obligation_id`. Radar читает оба источника.
- **Подтверждение.** `ObligationLinkIT`.

## D-07. Шкалы серьёзности и приоритета

- **Проблема.** В коде четыре шкалы: приоритет задач (CRITICAL/HIGH/NORMAL/LOW/INFORMATIONAL), серьёзность уведомлений и аудита (INFO/NOTICE/WARNING/CRITICAL), `InvoiceValidation.Severity` (INFO/WARNING/BLOCKING); ТЗ v2.0 вводит пятую (INFO/LOW/MEDIUM/HIGH/CRITICAL) и требует детерминированного вычисления.
- **Решение.** Серьёзность находки (Radar) — шкала v2.0; приоритет задачи — отдельное понятие («что делать первым»). Соответствия: серьёзность → серьёзность уведомления: INFO, LOW → INFO; MEDIUM → NOTICE; HIGH → WARNING; CRITICAL → CRITICAL. `InvoiceValidation.BLOCKING` порождает находку не ниже HIGH; WARNING → MEDIUM; INFO → INFO. Серьёзность находки вычисляется только правилом; AI её не назначает.
- **Подтверждение.** `RadarEngineTest` (серьёзность не зависит от текста AI), таблица соответствия — тестом.

## D-08. Пространство администратора платформы

- **Контекст.** Не описано в ТЗ. Решение принято в коде: адрес из `BC_PLATFORM_ADMINS` (подтверждённый по почте) — администратор; его пространство бессрочно, не блокируется и не удаляется (`PlatformAdminResolver`, `PlatformAdminKeeper`, `TenantPurgeService`).
- **Риск, если не записать.** будущие изменения тарифов/жизненного цикла подписок могут молча вернуть срок.
- **Подтверждение.** `PlatformAdminIT` (бессрочность, запрет блокировки и удаления).

## D-09. Привязка согласований к содержимому

- **Проблема.** v2.0 §7.5/§14.4: подтверждение привязано к действию, получателю, содержимому и версии; изменение после подтверждения требует повторного согласования. В `approvals` есть `action_token` (идемпотентность), но нет версии и хеша; письма защищены неизменяемостью после утверждения.
- **Риск (`SECURITY_GAP`).** платёж или значимое действие исполняется по подтверждению, выданному для другого содержимого.
- **Решение.** `approvals.subject_version` и `content_hash`; исполнение сверяет хеш; при несовпадении согласование получает статус `EXPIRED`, создаётся новая заявка; ссылки на согласование и хеш пишутся в `audit_events.changes`.
- **Подтверждение.** `ApprovalContentBindingIT`, `PaymentIdempotencyIT`.

## D-10. Записи AI-обработки

- **Проблема.** v2.0 §13.3 перечисляет `AI processing records`.
- **Решение.** это `ai_jobs` + `ai_model_runs` (модель, версия и хеш инструкции, токены, стоимость, структурированный ответ, предупреждения, вопросы, подтверждение человеком). Новую таблицу не создавать; новые сущности (находки, факты, объяснения) ссылаются на `ai_model_run_id`. Типы задач (`ai_jobs_type_chk`) расширяются: `PLAN`, `EXPLAIN`, `EXPLAIN_FINDING`.
- **Подтверждение.** `FindingExplanationTest`, `DocumentExplanationIT`.

## D-11. Структура документации и единый источник статусов

- **Проблема.** Три документа делают одно и то же с разными шкалами: `docs/requirements-matrix.md` (по ТЗ v1.0, шкала РЕАЛИЗОВАНО/ЧАСТИЧНО), `docs/completion-audit.md` и требуемый v2.0 §3.2 `docs/feature-gap-analysis.md` (IMPLEMENTED_AND_TESTED…).
- **Решение.** Единый источник статусов — `docs/spec-reconciliation-matrix.md`. `docs/requirements-matrix.md` остаётся как исторический документ с пометкой «заменена»; числа в документах берутся из `scripts/facts.sh`. Структура: `docs/task.md` (общие требования), `docs/MASTER_SPEC_BUSINESS_MEMORY_RADAR.md` (новое направление), `docs/spec-reconciliation-matrix.md` (соответствие), `docs/implementation-plan.md` (задачи), `docs/architecture/` (проектные решения), `docs/diagrams/` (диаграммы), `docs/testing/` (стратегия), существующие `docs/runbook.md`, `docs/deployment.md` (эксплуатация — не переносятся в `docs/operations/`, чтобы не ломать ссылки).
- **Альтернатива.** создать `docs/feature-gap-analysis.md` как третий документ — отклонено: ещё одна шкала и ещё один источник расхождений.
- **Подтверждение.** `scripts/check-doc-references.sh` проходит для обновлённых документов.

## D-12. Нумерация этапов

- **Проблема.** v1.0 §35: этапы A–I (все помечены DONE в плане); v2.0 §18: фазы 0–7.
- **Решение.** Этапы A–I остаются; новые задачи получают префиксы `R` (согласование), `BM` (Business Memory), `RD` (Radar), `CA` (Case Autopilot), `TR` (Übersetzer), `SM` (Simulator), `UI`, `HD` (hardening). Фазы v2.0: 0→`R`, 1→`BM`, 2→`RD`, 3→`CA`, 4→`BM-UI`/`RD-07`/`RD-08`/`CA-07`/`CA-08`, 5→`TR`, 6→`SM`, 7→`HD`.

## D-13. Старшинство документов

- **Проблема.** ТЗ v2.0 не пересказывает v1.0 (OIDC, сканеры, печать, банки, отчёты и т. д.); без явной оговорки это можно прочитать как отмену.
- **Решение.** `docs/task.md` нормативен для всего, что ТЗ v2.0 не переопределяет явно; при расхождении действуют решения D-01…D-12. Оговорка вписана в раздел 0 ТЗ v2.0 и в шапку `docs/task.md`.
