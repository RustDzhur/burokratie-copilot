## 2. Почему модульный монолит

ТЗ §2.1 требует модульный монолит с чёткими границами и запрещает «микросервис на каждый экран».
Отдельные процессы выделяются только там, где это обосновано нагрузкой. Реализация:

- **Один артефакт** `services/api` с жёсткими границами пакетов-модулей
  (`de.buerokratiecopilot.<module>.{domain,application,web,infrastructure}`).
- **Worker — тот же артефакт** с профилем `worker` (`spring.main.web-application-type: none`).
  Он выполняет outbox-диспетчер, обработку документов, OCR/AI-задачи и задачи хранения.
  Это даёт отдельный runtime-компонент без дублирования доменного кода: тяжелая обработка
  масштабируется независимо от API.
- Зависимости между модулями — только «вниз»: `web → application → domain → shared`.
  Циклические зависимости запрещены; совместная работа идёт через доменные события в outbox.

Если в будущем понадобится физическое разделение, границы уже проведены: например
`documents` + worker можно вынести в `services/document-worker`, не меняя домен.

## 3. Слои и правила

| Слой | Ответственность | Правило |
|---|---|---|
| `web` | HTTP, DTO, валидация входа, статусы | Бизнес-логики нет; сущности JPA не сериализуются наружу (ТЗ §33) |
| `application` | Use-case, транзакции, права, аудит | Каждый метод — одна законченная операция |
| `domain` | Сущности, инварианты, состояния | Без зависимости от Spring/HTTP |
| `infrastructure` | JPA-репозитории, адаптеры интеграций, хранилище | Замена внешнего сервиса не затрагивает домен |

## 4. Мультитенантность и изоляция

Требование ТЗ §3.2 — «невозможно получить документы другого клиента изменением ID в URL» —
реализовано **тремя независимыми слоями**:

1. **Определение tenant из сессии.** `SessionAuthenticationFilter` читает серверную сессию и
   кладёт `tenantId` и `userId` в `RequestContext`. Значение из тела запроса, query-параметра или
   заголовка не принимается никогда.
2. **Серверная авторизация.** Права вычисляются из эффективных ролей членства
   (`membership_roles` → `role_permissions`), публикуются как authorities Spring Security и
   проверяются `@PreAuthorize`. Просроченные и отозванные членства не дают прав.
3. **PostgreSQL Row Level Security.** `TenantAwareDataSource` при **каждом** взятии соединения из
   пула выполняет `SET app.tenant_id = '<uuid>'` (или `''` для системного контекста).
   Политики на 60+ таблицах пропускают только строки своего tenant; `WITH CHECK` запрещает
   записать строку чужого tenant. Это защищает даже от ошибки в новом запросе.

Дополнительно: `sessions`, приглашения и одноразовые токены хранятся **только в виде хеша**;
пароли — Argon2id; ключи шифрования — вне репозитория.

## 5. Данные

- PostgreSQL 17, UUID-первичные ключи, `timestamptz` в UTC, часовой пояс места хранится рядом
  со сроком (ТЗ §19).
- Изменяемые бизнес-правила — **данные, а не код**: таксономия документов, правила сроков,
  сроки хранения, налоговые ставки, правила согласования, пороги уверенности, workflow.
  У каждого правила есть версия, автор, дата и признак `requires_verification`.
- Бинарные файлы не хранятся в БД: только метаданные, связи, извлечённый текст и ссылка на
  объектное хранилище.
- Полнотекстовый поиск — `tsvector` с немецкой конфигурацией; семантический поиск — опциональный
  `pgvector` с честной деградацией до FTS, если расширение недоступно.

### Ключевые инварианты, закреплённые в схеме

| Инвариант | Где закреплён |
|---|---|
| Платёж нельзя пометить исполненным без подтвердившего пользователя | `payments_executed_chk` |
| Дело нельзя закрыть без даты закрытия | `cases_closed_consistency_chk` |
| «Доставлено» нельзя заявить по событию «передано провайдеру» | `message_delivery_events_proof_chk` |
| Юридически подтверждённый срок невозможен без подтверждения человеком | `task_deadlines_legal_chk` |
| Извлечённое значение обязано иметь источник | `document_extractions_provenance_chk` |
| Аудит нельзя изменить или удалить | триггер `forbid_append_only_mutation` |
| Дубликат документа в рамках tenant невозможен | `documents_tenant_hash_key` |

## 6. События, надёжность, идемпотентность

- **Transactional outbox** (`outbox_events`): доменное событие пишется в одной транзакции с
  бизнес-изменением. Диспетчер забирает пачку через `FOR UPDATE SKIP LOCKED`, повторяет доставку
  и переводит «отравленные» события в `DEAD_LETTER`.
- **Идемпотентность потребителей** — `outbox_consumptions` (ключ `consumer + event_id`), поэтому
  at-least-once доставка не приводит к повторной отправке письма или повторному платежу.
- **Идемпотентность API** — заголовок `Idempotency-Key` и таблица `idempotency_records`.
- **Retry, таймауты, circuit breaker** — на уровне адаптеров внешних сервисов.
- **Graceful shutdown**, health checks `/actuator/health`, метрики Micrometer/Prometheus,
  структурные JSON-логи с correlation ID.

## 7. ИИ как компонент, а не источник истины

- Провайдер за абстракцией: облако/локально/выключено полностью (`burokratie.ai.enabled`).
- Структурированные ответы по JSON-схеме; у каждого значения — источник и уверенность.
- Самооценка модели **не** трактуется как калиброванная вероятность: порог автоматизации —
  настройка, проверяемая на размеченных данных.
- Содержимое документов и писем — **недоверенные данные**: системные инструкции отделены,
  инструменты работают по allowlist, права на инструмент проверяются, рискованные действия
  требуют подтверждения, все вызовы журналируются.
- Каждое ИИ-решение сохраняет использованные данные, версию модели, версию инструкции,
  результат, источник фактов, подтверждение пользователя и итог операции (ТЗ §32).

## 8. Границы автоматизации (ТЗ §32)

| Уровень | Что делает система | Требование |
|---|---|---|
| 1 | Извлечение текста, классификация, поиск дубликатов, связывание | Автоматически, с объяснением |
| 2 | Рекомендация приоритета, срока, исполнителя | С указанием основания |
| 3 | Подготовка черновика письма, заявления, платёжной задачи | Проверка человеком до исполнения |
| 4 | Отправка, платёж, расторжение, подпись | Явное подтверждение уполномоченного пользователя |

Уровень 4 технически невозможно выполнить без записи `approvals` с решением пользователя.

## 9. Безопасность

- Аутентификация: серверные сессии, `HttpOnly` + `SameSite` cookie, Argon2id, подтверждение
  e-mail, блокировка после N неудачных попыток, CSRF (double-submit), ограничение частоты.
- Авторизация: RBAC (10 базовых ролей, 74 права) с расширением до ABAC; проверка на сервере;
  доступ к конкретным делам; временный доступ с автоматическим истечением.
- Файлы: проверка MIME по содержимому, лимиты, защита от path traversal и zip-бомб, карантин до
  проверки, запрет исполняемого содержимого.
- Данные: шифрование при передаче (TLS терминируется на прокси) и при хранении (AES-GCM для
  секретов интеграций), управление ключами, журнал доступа, политики хранения, legal hold.
- Секреты: только через переменные окружения; prod-старт без ключа шифрования и без secure-cookie
  **отклоняется** (`ProductionConfigurationGuard`).
- Логи: пароли, токены, IBAN и адреса маскируются (`LogSanitizer`), покрыто тестами.

## 10. Чего система не делает (сознательно)

- Не выводит юридические сроки, налоговые ставки и сроки хранения «по умолчанию» — только
  конфигурируемые, версионируемые, подтверждаемые правила.
- Не выполняет платежи автоматически: подготовка и подтверждение разделены.
- Не утверждает, что письмо доставлено, если провайдер подтвердил только приём.
- Не выдаёт подключённую интеграцию за работающую: у каждой есть статус и указание, что именно
  требуется от владельца системы.
- Не заявляет о соответствии DSGVO/GoBD/BFSG: подготовлены технические механизмы, но правовая
  оценка конкретного использования требует независимой проверки.
