# Качество распознавания документов — синтетический стенд

Стенд: синтетический корпус → реальный конвейер приложения (загрузка → OCR Tesseract → язык → классификация → извлечение полей) → метрики. Отчёт генерируется скриптом `scripts/quality/report.py` из JSON-результатов прогона; вручную цифры не правятся.

## 1. Коротко

- Корпус: **133 документов** (80 dev, 53 holdout), **35 типов** документов, 8 категорий сложности, два языка (немецкий и русский перевод).
- Точность типа (top-1, немецкие): **97.2 % (70/72)** на dev и **100.0 % (48/48)** на holdout.
- Ошибочная автоматическая сортировка: **0** из 48 автоматически принятых.
- Не распознано (нет типа): **2** на dev, **0** на holdout; оба случая — сознательно испорченные изображения (см. §6).
- Поля (доля найденных от ожидаемых): номер **93.3 % (28/30)**, дата **90.0 % (54/60)**, сумма **93.6 % (44/47)**, поставщик **90.3 % (65/72)** на dev; на holdout — 90.9 % (20/22), 90.0 % (36/40), 96.9 % (31/32), 95.8 % (46/48).
- Русский перевод: при OCR-языках `deu+eng` **0/13** документов определены как русские, один даже принят автоматически; при `deu+eng+rus` — **13/13** определены как `ru`, **0** автоматически принято, все ушли на человека. Это конфигурационное условие стенда, а не правило классификации.

## 2. Что именно измерялось

| Понятие | Определение |
|---|---|
| Тип документа (top-1) | `document_classifications` текущего документа; допускаются явно перечисленные в манифесте близкие типы (например, `betriebskostenabrechnung`/`nebenkostenabrechnung`). |
| Категория документа | категория распознанного типа в таксономии (`FINANCE`, `GOVERNMENT`, …). |
| Категория расходов | отдельно: существующий агент `expense-sort` на строке счёта; см. §5a. |
| Автоматически принято | у документа заполнен `documents.document_type_id` после классификации; более позднее «на проверку» из-за matching/полей не отменяет факт автоматической классификации. |
| Ошибочная автоматизация | автоматически принятый тип неверен (самая опасная метрика). |
| Не распознано | текущей классификации нет (тип `null`). |
| Поле найдено | среди извлечённых полей есть значение (нормализованное или исходное), равное ожидаемому; для поставщика — `documents.sender` содержит ожидаемое название. |
| Ключевое поле | поле из манифеста под своим ключом типа (например, `Rechnungsnummer`), значение совпало. |

Метрики типов считаются только по немецким документам (`language=de` в манифесте). Русские документы вынесены в отдельный раздел: политика платформы — не сортировать не-немецкие документы автоматически.

### Почему остались эти ошибки

- `dev-rechnung-degraded-blur-01` — суммарное размытие + motion blur: Tesseract выдаёт «eeee …», текста для правил нет. Это честный предел OCR, а не правило классификации.
- `dev-kontoauszug-degraded-combo-09` — blur + шум + тень одновременно; OCR даёт кириллический шум с уверенностью 0.40. Такой документ должен уходить человеку, что и происходит.
- `dev-vertrag-degraded-rotated-04` — наклон ~7° и перспектива; после выпрямления часть строк («Beginn», «Kosten») теряется, тип при этом верен. Слабое место — геометрия/качество OCR, не правила.
- Поставщик: `SenderRecognizer` раньше принимал контактную строку с `verwaltung@…` за название; после правки 65/72. Остальные промахи — обрезанный/повёрнутый верхний колонтитул.
- `holdout-quittung_kassenbon-clean-03`: OCR разложил подписи и значения квитанции в две колонки; «Datum:» осталось без значения на своей строке. Это ограничение построчного извлечения, не ошибка типа.
- `holdout-rechnung-stamped-paid-01`: штамп «BEZAHLT» лёг на строку «Bruttobetrag» и закрыл сумму. Для бумаги это нормальная ситуация; поле остаётся пустым, а не выдумывается.

## 7. Русский перевод

| Условие | Документов | Определён `ru` | Автоматически принято | На проверке |
|---|---:|---:|---:|---:|
| OCR `deu+eng` (до) | 13 | 0 | 1 | 13 |
| OCR `deu+eng+rus` (стенд) | 13 | 13 | 0 | 13 |

Политика платформы (решение владельца, V55): не-немецкий документ не сортируется автоматически, а уходит человеку. Проблема была не в политике, а в том, что при `deu+eng` русский текст вообще не читался: язык оставался `null`, и правило «не немецкий» не срабатывало. Для стенда включены данные `rus`; в пилоте стоит либо добавить `rus` в `BC_OCR_LANGUAGES`, либо определять кириллицу до классификации. Это конфигурационное изменение, не изменение API.

## 8. Что изменено

1. **V82** (`services/api/src/main/resources/db/migration/V82__corpus_quality_tuning.sql`):
   - `zahlungsbeleg`/`zahlungsbestaetigung`: точный заголовок «Zahlungsbestätigung» теперь ведёт к подтверждению оплаты, а не к платёжному документу;
   - `widerspruch`: фраза «Widerspruch gegen den Bescheid» и «Widerspruch einlegen»; вес `behoerdenbescheid` на слово «widerspruch» снижен;
   - `krankmeldung`: варианты без умлаутов (`arbeitsunfahig…`), которые даёт OCR;
   - подсказки полей: `Angebotsnummer`, `Belegnummer`, `Nettobetrag`, `Miete`, `Neues Entgelt`, `Festgesetzte Steuer`, `Nachzahlung`, `Schreibendatum`, `Rechnungsdatum`, `Bescheiddatum`, `Kita-Beitrag` и др.
2. **`FieldExtractionService`**: если первое вхождение метки — заголовок («Miete und Betriebskosten», «Vertragsbeginn und Laufzeit», «Gutschrift / Stornorechnung»), поиск продолжается до значения, проходящего проверку типа. Раньше поле считалось отсутствующим на всей странице.
3. **`SenderRecognizer`**: контактная строка с e-mail (`verwaltung@…`) больше не принимается за название отправителя. Это подняло полноту поставщика.

API, схема БД и пороги классификации (`0.85`/`0.60`) не менялись. Изменения правил — только платформенные (`tenant_id IS NULL`), без правки клиентских настроек.

## 9. Воспроизведение

```bash
# 1. сгенерировать корпус (детерминированно, seed=20261026)
python3 scripts/quality/generate_corpus.py --split all --clean

# 2. прогнать конвейер и собрать отчёт
scripts/quality/run-corpus.sh
```

`run-corpus.sh` собирает чистую копию `services/api` без случайных файлов `* 2.*` (они уже лежат в рабочем дереве и ломают компиляцию/Flyway), поднимает отдельную БД `burokratie_quality`, запускает `DocumentCorpusQualityIT` для dev и holdout, затем русский эксперимент с `deu+eng+rus`.

Результаты: `tests/corpus/results/*.json`; отчёт пересобирается командой:

```bash
python3 scripts/quality/report.py --results-dir tests/corpus/results \
    --out docs/quality/DOCUMENT_QUALITY.md
```

### Проверка сборки и тестов

- `services/api`: `./mvnw -q test` на JDK 21 и свежей PostgreSQL — **1248 тестов, 0 failures, 0 errors, 1 skipped**.
- `EvaluationHarnessIT` (прежний текстовый набор) — зелёный; регрессии правил нет.
- `FieldExtractionIT` — зелёный, включая новый тест «заголовок с меткой не скрывает значение».

## 10. Ограничения

- Корпус синтетический; шрифты и вёрстка ограничены Arial/Times/Arial Narrow, реальные сканы имеют другую полиграфию. Это стенд для сравнения правил, а не сертификация.
- Holdout написан другими названиями и вёрсткой, но тем же автором; он не заменяет реальную размеченную выборку. На dev правила настраивались, поэтому 100 % на нём — регрессионная планка.
- OCR запускался локальным Tesseract 5 с `deu+eng` (и `deu+eng+rus` для русского эксперимента); в пилоте OCR может быть выключен (`BC_ALLOW_NO_OCR`), тогда документы уходят на человека.
- AI-модель не участвовала; измерены только правила и извлечение.
